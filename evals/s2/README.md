Owner: Data Engineering · Corresponds to S-2 in `backend/backend-design.md` (agreement with human labels ≥ 90%; missed anchor violations 0) and section 3 of contract `contracts.md` v1.6 (Event, CheckResult, R1–R7) · Last updated: 2026-10-10

担当：データエンジニアリング · `backend/backend-design.md` の S-2（人手との一致率 ≥ 90%、アンカー違反の見逃し 0）と契約 `contracts.md` v1.6 第 3 節（Event、CheckResult、R1〜R7）に対応 · 最終更新：2026-10-10

What is tested is **steps 3 and 4** of the narrator pipeline (backend-design 2.4): the deterministic rules R1–R4 and R7, and the model checks R5 and R6. Extraction (step 2) and rewriting (step 5) are not tested: each item directly supplies one candidate event, and we see whether the self-check passes it and which rules it reports.

テスト対象はナレーターパイプラインの**第 3、4 ステップ**（backend-design 2.4）：決定的ルール R1〜R4、R7 とモデルチェック R5、R6。抽出（第 2 ステップ）と書き直し（第 5 ステップ）はテストしない。各項目は候補イベントを 1 つ直接与え、自己チェックが通すか通さないか、どのルールを報告するかを見る。

```json

 "setup": {"role": "role.shepherd-boy", "checkpoint": "sc.canon@t=4380", "place": "place.melos-home"},
 "turn": {"player": "外はまだ暗いから、この灯を持っていって",
          "act": {"kind": "give", "target": "char.melos", "params": {"item": "item.lantern"}}},
 "candidate": {"t": 4380, "actor": "player", "type": "action", "origin": "action", "dt": 5, "place": "place.melos-home",
               "summary": "牧童はメロスに灯を渡した", "causes": [],
               "effects": [{"op": "hold", "item": "item.lantern", "to": "char.melos", "from": "player"}]},
 "label": {"verdict": "fail", "failedRules": ["R7-capability"], "stage": "rules",
           "rationale": "item.lantern is in the player's hands only after the groom lends it (aid.groom.lend) ... / item.lantern は花婿が貸して（aid.groom.lend）から初めてプレイヤーの手に渡る……",
           "fix": "Reject (rejected, R7). Narration: 牧童は灯を探したが、手もとにはなかった。 / 拒否（rejected、R7）。叙述：牧童は灯を探したが、手もとにはなかった。",
           "refs": ["item.lantern", "aid.groom.lend"]},
 "tags": ["pair"]}
```

| Field / フィールド | Meaning / 意味 |
|---|---|
| `setup` | The starting point, written exactly as in eval cases (`role`, `checkpoint`, `place`, `events`; see "Case format" in `../README.md`). `eval_api` can use the setup directly / 開始点。評価ケースとまったく同じ書き方（`role`、`checkpoint`、`place`、`events`、`../README.md` の「ケース形式」を参照）。`eval_api` の setup としてそのまま使える |
| `turn` | What happens this turn: `player` (the player's exact words), `to` (addressee), `reply` (the character's answer; put here when the character answers wrongly); for an action, `act` (`kind`, `target`, `params`, with `affordance` when there is a matching situational action). No `to` means the player did it alone / このターンに起きたこと：`player`（プレイヤーの原文の発言）、`to`（宛先）、`reply`（人物の返答。人物が間違えた場合はここに書く）。アクションの場合は `act`（`kind`、`target`、`params`、対応する状況アクションがあれば `affordance` を付ける）。`to` がないものはプレイヤーが一人で行ったこと |
| `candidate` | The candidate event extracted by narrator step 2, a subset of the contract's Event: `t`, `actor`, `type`, `origin`, `dt`, `place`, `summary`, `causes`, `effects`, optionally `beneficiary`, `confirmed`. It has no `eventId`, `seq` or `check` yet, and a promise has no `promiseId` (assigned at commit) / ナレーターの第 2 ステップが抽出した候補イベント。契約 Event のサブセット：`t`、`actor`、`type`、`origin`、`dt`、`place`、`summary`、`causes`、`effects`、任意で `beneficiary`、`confirmed`。まだ `eventId`、`seq`、`check` はなく、約束には `promiseId` がない（コミット時に割り当てる） |
| `label.verdict` | Human verdict: `pass` (commit as is) / `fail` (a violation; rewrite, downgrade or reject) / 人手の判定：`pass`（そのままコミット）/ `fail`（違反あり。書き直し、降格、または拒否が必要） |
| `label.failedRules` | The violated rules, the first being the primary rule. The self-check must report at least one of them / 違反したルール。最初が主ルール。自己チェックはこのうち少なくとも 1 つを報告しなければならない |
| `label.acceptAlso` | Optional. Rules that are also reasonable (e.g. postponing a beat that has already happened: both R2 and R3 are right). Reporting these also counts as rule agreement / 任意。同じく妥当なルール（例：すでに起きたビートを延期する場合は R2 も R3 も正しい）。これらを報告してもルール一致とみなす |
| `label.stage` | For violations: `rules` = visible from the structured effects alone, so step 3 should stop it; `model` = visible only by understanding the summary, an improvised setting or a character's personality, so step 4 is needed / 違反の場合：`rules` = 構造化された effects だけで分かるので第 3 ステップで止めるべきもの。`model` = 要約、即興の設定、人物の性格を理解して初めて分かるので第 4 ステップが必要なもの |
| `label.rationale` | Why it was judged this way (in Chinese originally; now English and Japanese), citing world-model IDs and contract clauses / なぜそう判定したか。世界モデルの ID と契約の条文を引用する |
| `label.fix` | For violations: how to rewrite, downgrade or reject correctly. Not scored; for step 5 and reviewers / 違反の場合：どう書き直す、降格する、または拒否すれば正しいか。採点しない。第 5 ステップとレビュー用 |
| `label.refs` | IDs the basis uses (the self-check verifies that they all exist) / 根拠に使う ID（自己チェックがすべて存在することを確認する） |
| `tags` | `anchor-text` (the anchor violation appears only in the text), `improv`, `claim` (a statement by the player or a character, not a fact), `tricky-valid` (compliant but looks like a violation), `pair` (a violating and a compliant version of the same scene), etc. / `anchor-text`（アンカー違反が文章中にしか現れない）、`improv`、`claim`（プレイヤーや人物の主張で、事実ではない）、`tricky-valid`（違反に見える適合）、`pair`（同じ場面の違反版と適合版）など |

## How to run and score / 実行と採点の方法

1. For each item: start a game from `setup` (`eval_api`), call `check(candidate, turn, model_checks="all")` (api-contract section 7: check only, no commit; `turn` is context for the model checks; `all` = step 4 runs on every item rather than picking by the official scope), and record `status` (pass = `passed`; fail = the other three), `failedRules` and `reason`.
   各項目：`setup` からゲームを開始し（`eval_api`）、`check(candidate, turn, model_checks="all")` を呼ぶ（api-contract 第 7 節：チェックのみでコミットしない。`turn` はモデルチェックの文脈。`all` = 第 4 ステップを正式な範囲で選ばず全項目で実行する）。`status`（通過 = `passed`、不通過 = 残りの 3 種）、`failedRules`、`reason` を記録する。
2. Run each item 3 times, with the narrator's official model and thinking level (3.8-flash, MEDIUM). Cost is about 50 × 3 × $0.01 ≈ $1.5 (`cost/m2-model-budget.md`).
   各項目を 3 回実行する。モデルと思考レベルはナレーターの正式設定（3.8-flash、MEDIUM）。費用は約 50 × 3 × $0.01 ≈ $1.5（`cost/m2-model-budget.md`）。
3. Scoring:
   採点：
   - **Agreement rate** = number of items whose verdict (pass / fail) equals `label.verdict` ÷ 50, threshold ≥ 90% (at most 5 wrong). Compute it for each of the three runs and report the worst, plus the majority vote of the three.
     **一致率** = 判定（通過 / 不通過）が `label.verdict` と同じ件数 ÷ 50、基準は ≥ 90%（誤りは最大 5 件）。3 回それぞれで計算し、最悪の回を報告する。3 回の多数決も別に報告する。
   - **Missed anchors** = the number of times an item with R1 in `failedRules` is judged "pass"; threshold 0 (not allowed in any of the three runs).
     **アンカーの見逃し** = `failedRules` に R1 を含む項目が「通過」と判定された回数。基準は 0（3 回のどれでも不可）。
   - Reported without a threshold: rule agreement (when both sides judge fail, whether the reported rules intersect `failedRules ∪ acceptAlso`); how many compliant items were wrongly rejected and how many violations were missed, split by `stage`; items whose three results differ, listed separately; items once mentioned by category in public documents, listed separately (the list is in `data/evals/holdout/README.md` in the project folder, given by Data after the run) to see whether they differ from other items.
     基準なしで報告するもの：ルール一致（両方が不通過と判定したとき、報告されたルールが `failedRules ∪ acceptAlso` と交わるか）。適合なのに誤って拒否した件数と違反を見逃した件数を `stage` 別に。3 回の結果が異なる項目は別枠で。公開文書でカテゴリとして触れたことのある項目は別枠で（一覧はプロジェクトフォルダの `data/evals/holdout/README.md` にあり、実行後にデータが渡す）。他の項目と差があるかを見る。
4. The result is written as `report.json` (each item's verdict, rules, `reason` and trace ID per run) and a one-page `report.md`, handed to Data to check the labels: Data reviews each disagreeing item to decide whether the self-check or the label was wrong. If the label was wrong, change the generator, regenerate the measurement set, and state in the report which items changed.
   結果は `report.json`（各項目の各回の判定、ルール、`reason`、トレース ID）と 1 ページの `report.md` にまとめ、データにラベルの確認を依頼する。一致しなかった項目はデータが 1 件ずつ見て、自己チェックが誤りかラベルが誤りかを判断する。ラベルが誤りならジェネレーターを直して測定セットを再生成し、どの項目を変えたかをレポートに明記する。

## Scope of step 4 (decided, backend-design v1.0.9) / 第 4 ステップの範囲（決定済み、backend-design v1.0.9）

While labeling we found that under the original scope (model checks look only at events that affect a beat or a relationship), most violations that need understanding of meaning never reach the model, so "missed anchors 0" could not be achieved. The backend has widened it:

ラベル付けの際に分かったこと：元の範囲（モデルチェックはビートや関係に影響するイベントだけを見る）では、意味の理解が必要な違反の多くがモデルに届かず、「アンカーの見逃し 0」は達成できない。バックエンドは範囲を広げた：

- Step 4 runs on all candidate events that passed step 3 and have non-empty `effects` (including `improv`, `learn`, variables and character locations). Events that only advance the clock do not run.
  第 4 ステップは、第 3 ステップを通過し `effects` が空でない全候補イベント（`improv`、`learn`、変数、人物の所在地を含む）で実行する。時計を進めるだけのものは実行しない。
- The rule part of R6 (patterns for phone numbers, emails and addresses, Model Armor flags, and 8 consecutive identical characters with the original text) is placed in step 3 and runs on every summary and improvised setting.
  R6 のルール部分（電話番号、メール、住所のパターン、Model Armor のフラグ、原文との連続 8 文字一致）は第 3 ステップに置き、すべての要約と即興の設定で実行する。
- Net increase of about $0.03 per run (backend-design section 8; replaced by the S-5 measurement).
  純増は 1 プレイあたり約 $0.03（backend-design 第 8 節。S-5 の実測で置き換える）。

S-2 uses `model_checks="all"` and is unaffected by the scope. Which violations would be missed under the official scope is counted by `scope_gap()` in `s2_check.py` (violations with empty `effects`, labeled `model`, and not catchable by step-3 R6 patterns): both sets are currently 0.

S-2 は `model_checks="all"` を使うので範囲の影響を受けない。正式な範囲でどの違反を見逃すかは `s2_check.py` の `scope_gap()` が数える（`effects` が空で、`model` とラベルされ、第 3 ステップの R6 パターンでも捕まえられない違反）。現在は両セットとも 0。

R6 items are still labeled `stage: model`: step-3 patterns catch phone numbers, emails and copied original text, but not names, addresses and appropriateness; `judge()` also does not do R6.

R6 の項目は引き続き `stage: model` とラベルしている。第 3 ステップのパターンは電話番号、メール、原文の丸写しは捕まえられるが、名前、住所、さじ加減は捕まえきれない。`judge()` も R6 は行わない。

## Minimal judgment for deterministic rules (`judge()` in `s2_check.py`) / 決定的ルールの最小判定（`s2_check.py` の `judge()`）

Data uses it to check that the labels are self-consistent: for violations labeled `rules` it must report the primary rule; for compliant items and items labeled `model` it must report none. It is not the backend's implementation, but **whatever it can stop, the backend's step 3 must also stop**:

データはこれでラベルが自己矛盾していないかを確認する。`rules` とラベルされた違反では主ルールを報告しなければならず、適合の項目と `model` とラベルされた項目では 1 つも報告してはならない。これはバックエンドの実装ではないが、**これが止められるものは、バックエンドの第 3 ステップも必ず止めなければならない**：

| Rule / ルール | How it is judged / 判定方法 |
|---|---|
| R1 | An `op: beat` changes an anchor beat (`kind: anchor` or listed in `anchors`) and `to` is not `happened`; a `set` on a variable whose current value was written by a beat that already happened as an anchor and was not changed by any other beat since (e.g. `var.weather` after the heavy rain, `var.bridge` after the bridge washout) / `op: beat` がアンカービート（`kind: anchor` または `anchors` にある）を変更し、`to` が `happened` でない。変数への `set` で、その変数の現在値が既に起きたアンカービートによって書かれており、その後に他のビートが変更していないもの（例：大雨の後の `var.weather`、橋が流された後の `var.bridge`） |
| R2 | Changing a beat that already has an outcome; a candidate event that makes a beat `happened` (only system events at the due time write `happened`; to bring it earlier use `hastened`; W-1's `check_effects` reports the same); making a beat `altered` when its precondition or the previous beat in `requires` does not hold; changing an `executed` variable back to another value, or moving an executed hostage (rule.no-resurrection); setting a variable to a value that does not satisfy `StateVar.valueRequires` (contract 1.6, C-16: the king's heart depends on `var.king.trust` 40 / 70, and setting `var.river.crossing` to `bridge` requires the bridge still to exist; reads only the world model, using the reference implementation's `value_requires()`) / すでに結果のあるビートを変更する。候補イベントがビートを `happened` にする（期限に来たシステムイベントだけが `happened` を書く。早めるには `hastened` を使う。W-1 の `check_effects` も同様に報告する）。前提または `requires` の前のビートが成り立たないのにビートを `altered` にする。`executed` の変数を別の値に戻す、処刑済みの人質を移動する（rule.no-resurrection）。`StateVar.valueRequires` を満たさない値に変数を変更する（契約 1.6、C-16：王の心は `var.king.trust` の 40 / 70 で決まり、`var.river.crossing` を `bridge` にするには橋が残っている必要がある。世界モデルのみを読み、参考実装の `value_requires()` を使う） |
| R3 | The event's `t` is earlier than the current clock; for `relocate` or a player's change of place, the shortest distance by `places.adjacent` exceeds `dt` / イベントの `t` が現在の時計より前。`relocate` またはプレイヤーの場所移動で、`places.adjacent` による最短所要時間が `dt` を超える |
| R4 | `learn`: the fact is true at this moment (`trueFrom` has happened) and the actor knows it (characters by `knows` `since` and what they learned in this run; the player by the role's `initialKnowledge`); the `statement` of an `improv` does not contain `spoilerTerms` of a fact that character does not yet know / `learn`：その事実がこの時点で成り立っており（`trueFrom` が発生済み）、行為者がそれを知っている（人物は `knows` の `since` とこのプレイで学んだこと、プレイヤーは身分の `initialKnowledge`）。`improv` の `statement` に、その人物がこの時点でまだ知らない事実の `spoilerTerms` を含まない |
| R7 | A player's change of place must be in `access` or in a `conditionalAccess` that holds now; what the player hands over must be in the player's hands; handing it to a character requires being in the same place (or following him); a situational action's `place`, `roles`, `when` and required items must all be satisfied / プレイヤーの場所移動は `access` またはこの時点で成り立つ `conditionalAccess` に含まれていること。プレイヤーが渡す物はプレイヤーの手にあること。人物に渡すには同じ場所にいる（または彼について行っている）こと。状況アクションの `place`、`roles`、`when`、使う物がすべて満たされていること |

Three things met during labeling that the backend should note when implementing:

ラベル付けの際に分かった、バックエンドが実装時に注意すべき 3 点：

- **Act-4 travel times do not match the original's timing.** 「市へ続く野の道」 is a long stretch: in `places.adjacent`, spring to field road is 120 minutes and field road to execution ground is 62 minutes, but in the original `beat.21`→`beat.22` is only 60 minutes apart and `beat.23`→`beat.24` only 30. For characters following a schedule, R3 looks at the schedule; `adjacent` measures only the player's movement and `relocate` outside the schedule (decided in backend-design v1.0.9).
  **第四幕の所要時間が原作の時間と合わない。**「市へ続く野の道」は長い道のりで、`places.adjacent` では泉から野の道まで 120 分、野の道から刑場まで 62 分だが、原作の `beat.21`→`beat.22` はわずか 60 分、`beat.23`→`beat.24` はわずか 30 分しか離れていない。スケジュールに従って動く人物については R3 はスケジュールを見る。`adjacent` はプレイヤーの移動とスケジュール外の `relocate` だけを測る（backend-design v1.0.9 で決定済み）。
- **Two constraints written only in explanatory text are now data**: the king's trust thresholds (40 / 70) and "crossing the river by the bridge requires the bridge to exist", in `StateVar.valueRequires` of contract 1.6 (`../../docs/data/contracts.md` 2.6 "value conditions", C-16). `judge()` now reads it instead of hard-coding; the narrator's step 3 also reads only data. Both label sets were rechecked with the new `judge()` with 0 errors, so the labels need no change.
  **説明文にしか書かれていなかった 2 つの制約をデータにした**：王の信頼の閾値（40 / 70）と「橋を渡って川を越えるには橋が残っていること」。契約 1.6 の `StateVar.valueRequires`（`../../docs/data/contracts.md` 2.6「取りうる値の条件」、C-16）。`judge()` は固定値ではなくこれを読むよう変更し、ナレーターの第 3 ステップもデータだけを読む。2 つのラベルセットを新しい `judge()` で確認し、エラーは 0 で、ラベルの変更は不要。
- **A character saying the wrong thing ≠ the world changing.** When a character's reply itself is wrong (letting slip something not yet known, misstating their own background), the narrator extracting it as is would be wrong. The correct approach is not to commit, and to add a smoothing hint to that character's next situation note (contract section 3, "being vetoed and being corrected are two different things").
  **人物が間違ったことを言う ≠ 世界が変わった。**人物の返答自体が誤っている（まだ知らないことを口走る、自分の経歴を言い間違える）場合、ナレーターがそのまま抽出すると誤りになる。正しい対応は、コミットせず、その人物の次の状況説明に辻褄を合わせるヒントを加えること（契約第 3 節「却下と修正は別のこと」）。
