## Goal / 目標

Once this is done you can see:

完成すると次のことが確認できる：

1. A runner under `evals/`: it reads the 100 seed cases of E1–E8, runs every step through `zoujin_backend.eval_api`, performs deterministic checks, and produces a report.
   `evals/` の下にランナーがある：E1〜E8 の 100 個のシードケースを読み、`zoujin_backend.eval_api` を通して各ステップを最後まで実行し、決定的チェックを行い、レポートを 1 つ出す。
2. The result of each check in each case is one of: pass, fail, skipped (backend not implemented), skipped (needs real model); `replay` mode additionally has "replay missing or stale". Neither skips nor replay problems count as passes.
   各ケースの各チェックの結果は次のいずれか：合格、不合格、スキップ（バックエンド未実装）、スキップ（本物のモデルが必要）。`replay` モードではさらに「リプレイ欠落または期限切れ」がある。スキップもリプレイの問題も合格には数えない。
3. CI runs with the fake model: checks that can be decided by simulation alone must all pass; the results of the other checks are determined by the fake model's fixed outputs and compared with the expected snapshot in the tests, going red on any difference.
   CI は偽モデルで実行する：シミュレーションだけで判定できるチェックはすべて合格しなければならない。その他のチェックの結果は偽モデルの固定出力で決まり、テストの中の期待スナップショットと比べ、違えば赤になる。
4. `live` has only the switch and the exit: the guardrail parameters and "show zg the estimated cost first" are built; the real-model calls are wired in M2.
   `live` にはスイッチと終了しかない：ガードレールのパラメータと「まず zg に見積もり費用を見せる」は作っておき、本物のモデルの呼び出しは M2 でつなぐ。

## Scope / 範囲

### In scope / やること

**1. Reading and running cases**

**1. ケースを読み、実行する**

- Read `evals/seeds/E*.jsonl` (format in the README, already validated by `check_evals`). Each case repeats per `runs`: setup → execute step by step → check.
  `evals/seeds/E*.jsonl` を読む（形式は README を参照。`check_evals` で検証済み）。各ケースは `runs` に従って繰り返す：setup → 1 ステップずつ実行 → チェック。
- Setup is passed to `eval_api` exactly as in the case (`role`, `place`, `budgetTier`, `checkpoint` / `scenario` / `persona` + `seed`, `events`); the runner itself does not simulate or fill in fields.
  setup はケースのとおりそのまま `eval_api` に渡す（`role`、`place`、`budgetTier`、`checkpoint` / `scenario` / `persona` + `seed`、`events`）。ランナー自身はシミュレーションもフィールドの補完もしない。
- When `eval_api` raises `EvalNotImplemented("name")`, do not crash:
  `eval_api` が `EvalNotImplemented("名前")` を投げても、クラッシュしない：
  - raised by setup or a step: all checks in this case record "skipped: backend not implemented (name)";
    setup またはステップが投げた場合：このケースのすべてのチェックを「スキップ：バックエンド未実装（名前）」と記録する。
  - raised by a query: only the checks that use that query record a skip; the rest are judged as usual. E.g. `outcome` needs `ending()` and `memory` needs `memories()`, neither of which B-0 does.
    あるクエリが投げた場合：そのクエリを使うチェックだけをスキップと記録し、その他は通常どおり判定する。例：`outcome` には `ending()`、`memory` には `memories()` が必要で、B-0 はどちらもやらない。
- With B-0's current scope, 30 cases are skipped entirely: E7's 11 cases and E5-001 (simulated playthroughs with `persona` + `seed`), and the 18 cases with `act`, `propose`, `silence`, `deleteMemory`, `newPlaythrough` or `deletePlaythrough` steps. The report lists by name which ones were skipped.
  B-0 の現在の範囲では、ケースごとスキップされるのは 30 ケース：E7 の 11 ケースと E5-001（`persona` + `seed` の模擬プレイ）、そして `act`、`propose`、`silence`、`deleteMemory`、`newPlaythrough`、`deletePlaythrough` のステップを含む 18 ケース。レポートにはどれをスキップしたかを名前で列挙する。

**2. Deterministic checks**

**2. 決定的チェック**

- All types, as defined by `CHECK_TYPES` in `check_evals.py` (currently 28: `japanese`, `not_mention_fact`, `no_terms`, `beat`, `var`, `world_unchanged`, `no_event`, `replay_equal`, `t_monotonic`, `outcome_consistent`, `epilogue_cites_valid`, `no_verbatim_quotes`, `director_not_sole_cause`, `event`, `outcome`, `memory`, `no_pii`, `safety_card`, `act_plan`, `clock_advanced`, `terms_any`, `utterance_cleared`, `event_exists`, `followup_questions`, `schedule_shift`, `trust`, `db_absent`, `promise`).
  すべての種類。`check_evals.py` の `CHECK_TYPES` に従う（現在 28 種：`japanese`、`not_mention_fact`、`no_terms`、`beat`、`var`、`world_unchanged`、`no_event`、`replay_equal`、`t_monotonic`、`outcome_consistent`、`epilogue_cites_valid`、`no_verbatim_quotes`、`director_not_sole_cause`、`event`、`outcome`、`memory`、`no_pii`、`safety_card`、`act_plan`、`clock_advanced`、`terms_any`、`utterance_cleared`、`event_exists`、`followup_questions`、`schedule_shift`、`trust`、`db_absent`、`promise`）。
- An unknown type raises an error; it is never silently skipped.
  知らない種類に出会ったらエラーにし、黙ってスキップしない。
- Each kind of check has one small example that passes and one that fails (unit tests, not through `eval_api`), to make sure the check itself is written correctly.
  チェックの種類ごとに、合格する小さな例と不合格になる小さな例を 1 つずつ用意し（単体テスト、`eval_api` は通さない）、チェック自体の書き間違いがないことを確かめる。

**3. The two model modes and the `live` switch**

**3. モデルの 2 つのモードと `live` のスイッチ**

- `fake`: B-0's fake text model, the CI default.
  `fake`：B-0 の偽テキストモデル。CI の既定。
- `replay`: B-0's replay (`ZJ_MODEL=replay`, looked up by the hash of model, prompt version and request). When nothing is found, B-0 raises `ReplayMissing`, and the case records "replay missing or stale"; it is not treated as a pass, and does not fall back to the fake model.
  `replay`：B-0 のリプレイ（`ZJ_MODEL=replay`。モデル、プロンプトのバージョン、リクエストのハッシュで引く）。見つからなければ B-0 が `ReplayMissing` を投げ、このケースは「リプレイ欠落または期限切れ」と記録する。合格とは扱わず、偽モデルにも戻らない。
- `live`: B-0 does not write a real-model client (`ZJ_MODEL` accepts only `fake` and `replay`), so this card only builds the switch and the exit:
  `live`：B-0 は本物のモデルのクライアントを書かない（`ZJ_MODEL` は `fake` と `replay` だけを受け付ける）ので、このカードはスイッチと終了だけを作る：
  1. Without the switch on the Mac (an environment variable whose name this card decides), exit immediately and print the reason.
     Mac 上のスイッチ（環境変数。名前はこのカードで決める）がなければすぐに終了し、理由を表示する。
  2. Caps must be passed explicitly, with no defaults: `--max-item-usd` (per-item cap, both ledgers combined) and a total cap for each of the two ledgers, `--max-google-usd` and `--max-claude-usd`. If any one is missing, exit. zg has not yet set the development-phase model spending cap (dev-plan section 7, Z-8), so no number is hard-coded.
     上限は明示的に渡さなければならず、既定値はない：`--max-item-usd`（項目ごとの上限、2 つの台帳の合計）と、2 つの台帳それぞれの総額上限 `--max-google-usd`、`--max-claude-usd`。1 つでも欠けたら終了する。開発期間のモデル費用の上限（dev-plan 第 7 節 Z-8）は zg がまだ決めていないので、どんな数値もハードコードしない。
     (Changed 2026-10-10, decided by PM) Two ledgers: zg's Claude quota pays only for Claude calls. The product path (characters, narrator, endings) is charged to the Google ledger; the judge and the AI player are charged to the Claude ledger.
     （2026-10-10 変更、PM が決定）台帳を 2 つに分ける：zg の Claude の枠は Claude の呼び出しだけに使う。プロダクトの経路（登場人物、ナレーター、エンディング）は Google の台帳に、審査員と AI プレイヤーは Claude の台帳に記録する。
  3. Without `--confirm`: print the estimated cost for each of the two ledgers (number of cases × `runs` × number of steps × estimated price per step; the estimates live in `evals/config/live-cost.json`, with the Google part filled in from `docs/data/cost/m2-model-budget.md` and the Claude part from Anthropic's price list) and the full command, then exit. The coordinator shows these two things to zg, and only after zg agrees is it run again with `--confirm`.
     `--confirm` なし：2 つの台帳それぞれの見積もり費用（ケース数 × `runs` × ステップ数 × ステップごとの見積単価。見積単価は `evals/config/live-cost.json` に書き、Google の部分は `docs/data/cost/m2-model-budget.md`、Claude の部分は Anthropic の価格表に従って埋める）と完全なコマンドを表示して終了する。調整役がこの 2 つを zg に見せ、zg が同意してから `--confirm` を付けてもう一度実行する。
  4. With `--confirm`: exit, printing "the real-model client does not exist yet; it gets wired in M2".
     `--confirm` あり：「本物のモデルのクライアントはまだない。M2 でつなぐ」と表示して終了する。

**4. Judging (judge)**

**4. 採点（judge）**

Only the interface and report format are defined (rubric, pass condition, score). For now all judging records "skipped: needs real model".

インターフェースとレポートの形式（ルーブリック、合格条件、スコア）だけを決める。現時点ではすべての採点を「スキップ：本物のモデルが必要」と記録する。

**5. Report**

**5. レポート**

- `report.json`: the result of every check in every run of every case (one of the four, with the reason for skips), the reasons for failures, and trace IDs.
  `report.json`：各ケースの各回の各チェックの結果（4 種のいずれか。スキップは理由付き）、不合格の理由、trace ID。
- `report.md`: passes, failures and skips per suite (skips split by reason), compared against the merge bar and release bar in data-design 7.3; then the hard metrics outside the bars (e.g. "events written that violate an anchor = 0"). Skips are not in the pass-rate denominator, but are written on the same line, so that many skips do not make the pass rate look high.
  `report.md`：スイートごとの合格数、不合格数、スキップ数（スキップは理由別）を、data-design 7.3 のマージ基準、リリース基準と比べる。さらに基準以外の必須指標（例：「アンカーに反するイベントの書き込み = 0」）を挙げる。スキップは合格率の分母に入れないが、同じ行に書き出して、スキップが多いせいで合格率が高く見えることがないようにする。
- The report format is written into `evals/README.md`.
  レポートの形式は `evals/README.md` に書く。

**6. CI**

Run `--mode fake --deterministic-only`:

`--mode fake --deterministic-only` を実行する：

- The unit tests for the 28 checks all pass;
  28 種のチェックの単体テストがすべて通る。
- All 100 cases run without crashing;
  100 ケースがクラッシュせずに最後まで実行される。
- Checks that can be decided by simulation alone all pass (see the acceptance check);
  シミュレーションだけで判定できるチェックがすべて合格する（受け入れ確認を参照）。
- The whole `report.json` is field-for-field identical to the expected snapshot committed with the tests. If B-0 or the fake model changes its output, the snapshot is updated in the same PR and the diff is looked at during review.
  `report.json` 全体が、テストとともにコミットした期待スナップショットとフィールド単位で一致する。B-0 や偽モデルが出力を変えたら、同じ PR でスナップショットを更新し、レビューで差分を見る。

### Out of scope / やらないこと

- **E7 passing in full moves to M2.** E7's 11 cases and E5-001 need simulated playthroughs (an AI player plays on its own to an ending per persona + seed); B-0 does neither simulated playthroughs nor endings. Once M2 has simulated playthroughs and endings, "all of E7's deterministic checks pass" is added back to the acceptance check.
  **E7 の全合格は M2 に移す。** E7 の 11 ケースと E5-001 には模擬プレイ（AI プレイヤーが persona + seed に従って自分でエンディングまで遊ぶ）が必要だが、B-0 は模擬プレイもエンディングもやらない。M2 で模擬プレイとエンディングができたら、「E7 の決定的チェックがすべて合格」を受け入れ確認に戻す。
- **Real runs of `live`** (M2, when the real-model client is wired in). At that point all the guardrails of dev-plan 2.5 are required:
  **`live` の本番実行**（M2、本物のモデルのクライアントをつなぐときにやる）。そのときは dev-plan 2.5 のガードレールがすべて必要：
  - serial;
    直列で実行する。
  - a per-item cap plus two total ledgers (Google, Claude); each call records its cost by provider, and whichever ledger hits its cap stops the run;
    項目ごとの上限と 2 つの総額台帳（Google、Claude）。呼び出しごとにプロバイダー別に費用を記録し、どちらかの台帳が上限に達したら止まる。
  - stop on the first 429 (likewise Claude's 529 overload);
    最初の 429 で止まる（Claude の 529 過負荷も同様）。
  - the Claude client lives only in the evals package and the Mac batch scripts; the backend service package does not add this dependency, and there is no Claude in the product path's code;
    Claude のクライアントは evals パッケージと Mac のバッチ実行スクリプトにだけ置く。バックエンドのサービスパッケージにはこの依存を加えず、プロダクトの経路のコードに Claude はない。
  - the judge goes through Batch: first run the conversations through the product path and store the replies, then hand them to Claude in one batch for judging;
    審査員は Batch を使う：まずプロダクトの経路で会話を最後まで実行して返答を保存し、それをまとめて Claude に渡して判定させる。
  - judging is also stored as replays (`kind: "judge"`, with `provider` and `model` in the key), so later re-judging in CI costs nothing;
    採点もリプレイとして保存する（`kind: "judge"`、キーに `provider` と `model` を含む）。以後 CI で再採点してもお金がかからない。
  - only synthetic inputs are judged; real players' conversations are never handed to Claude;
    合成した入力だけを採点し、実際のプレイヤーの会話は Claude に渡さない。
  - `--resume` continues from where it last stopped (the lesson from S-068 breaking halfway);
    `--resume` で前回止まったところから続ける（S-068 が途中で止まった教訓）。
  - first print the estimated cost and the command for zg, and run only after zg agrees (already done in item 3);
    まず見積もり費用とコマンドを表示して zg に見せ、zg が同意してから実行する（第 3 項で実装済み）。
  - after the run, automatically save replays in the JSONL format B-0 defines (`key`, `kind`, `provider`, `model`, `promptVersion`, `request` (after redaction), `response`, `usage`, `costUsd`, `recordedAt`); record only synthetic inputs. `provider` is added to B-0's replay format by backend.
    実行後に自動でリプレイとして保存する。形式は B-0 が決めた JSONL（`key`、`kind`、`provider`、`model`、`promptVersion`、`request`（マスキング後）、`response`、`usage`、`costUsd`、`recordedAt`）。合成した入力だけを記録する。`provider` はバックエンドが B-0 のリプレイ形式に加える。
- Tuning the judging prompts (M2, done on the Mac).
  採点プロンプトの調整（M2、Mac で行う）。
- The AI player for simulated playthroughs (another card).
  模擬プレイの AI プレイヤー（別のカード）。

- Performance.

  28 種のチェックの合格 / 不合格の単体テストがすべて通る。
- In CI, `--mode fake` runs all 100 cases without crashing:
  CI で `--mode fake` が 100 ケースをクラッシュせずに最後まで実行する：
  - the 30 wholly skipped cases all record "skipped: backend not implemented", with the name;
    ケースごとスキップされる 30 ケースはすべて「スキップ：バックエンド未実装」と名前付きで記録される。

Their `outcome` needs `ending()`, and B-0 does not do endings, so for now it records "skipped: backend not implemented (ending)", and is judged in M2 once `ending()` exists;
    シミュレーションだけで判定できるチェックがすべて合格する：E5 の 12 個の `scenario` ケースと E5-006（`advance`）の `beat`、`var`（`check_evals` が参照実装で同じ期待値を確認済み）。それらの `outcome` には `ending()` が必要だが、B-0 はエンディングをやらないので、まず「スキップ：バックエンド未実装（ending）」と記録し、M2 で `ending()` ができてから判定する。

  リプレイ（B-0 の fixture、または同じ形式で手作りしたもの）を使って `--mode replay` を実行し、同じレポートを再現する。プロンプトのバージョンを変えると、そのケースは「リプレイ欠落または期限切れ」と記録される。
- `--mode live`: without the switch it exits and prints the reason; with a cap missing it exits; without `--confirm` it prints the estimated cost and the command, then exits.
