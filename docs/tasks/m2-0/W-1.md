1. 仓库里有一个纯 Python 包 `packages/worldsim`。叙事者、评测运行器和数据的工具都只用它，世界状态只有这一套规则在算。

**2. 增量接口**（后端提的，叙事者和 `eval_api` 用）

| 函数 | 做什么 |
|---|---|
| `initial_state(world, role_id)` | 这个身份开局前的状态：时钟 0，变量初值，`var.player.location` = 身份的 `startPlace`、`var.act.current` = `startAct`（契约 3.1），人物所在地，`holdings`（`Role.items`、`Character.items`），每个节拍的本局排定时间（没有改动时 = 原作）。调用方接着 `settle` 到身份的 `startT`，开局前到点的节拍也写成系统事件 |
| `apply(world, state, event)` | 对当前状态应用一个事件的 `effects`；时钟 = max(之前的时钟, `t` + `dt`)。8 种效果都做，见下表 |
| `settle(world, state, t2)` | 时钟走到 `t2`：按排定时间顺序结算排定时间 ≤ `t2` 的节拍和期限。返回系统事件的草稿（按先后）和结算后的状态 |
| `world_state(state)` | 转成契约 3.1 的 WorldState |
| `check_effects(world, state, effects, system=False)` | 效果本身合不合法：引用的 ID 存在；`set` 的值符合 StateVar 的 `type` 和 `values`；`inc` 只用于 `int`、`minutes`；`hold` 只用于 `portable` 的物品；`beat` 的 `to` 和 `minutes` 合法；`system=False`（叙事者的候选事件都是）时 `{op:"beat", to:"happened"}` 也报，叙事者在第 3 步按 R2 否决，不会走到 `apply` 才抛异常。（契约 1.6，C-16）`system=False` 时也查 `StateVar.valueRequires`，规则照参考实现的 `value_requires()`。返回问题列表。只查形状和引用；R1〜R7 是叙事者的（B-0 和 M2），`evals/s2_check.py` 的「最简判法」可以参考 |

`state` 是包自己的类型（例：`SimState`），能存成 JSON：WorldState 的全部字段，加上本局对节拍的改动（按先后，就是参考实现的 `sc.beats`）、节拍发生的时刻和用的变体。缓存 `SimState` 还是每次从事件日志重放，B-0 定。

8 种效果（契约第 3 节）：

| 效果 | 做什么 |
|---|---|
| `set`、`inc`、`relocate`、`hold` | 照参考实现的 `apply`。`inc` 按 StateVar 的 `min` / `max` 截断 |
| `learn` | 记进 `knowledge`（人物 → 学到的事实，不重复） |
| `improv` | 记进 `runFacts`（`factId` → 谁说的、那句话、`madeBy`） |
| `promise` | 记进 `promises`。`made` 建一条 `open`；`kept` / `broken` / `voided` 只能从 `open` 变，写 `resolvedBy` |
| `beat` | `origin: "schedule"` 的系统事件里：这是节拍的结果，`happened` / `altered` / `prevented` 记进 `beats`，`altered` 当场应用它带的 `outcomes`。其他事件里：这是本局的改动，`delayed` / `hastened` / `prevented` / `altered` 记进改动列表，重算还没结果的节拍的排定时间（同一个节拍再推迟或再提前，分钟相加；方向不同照参考实现 `arrival_delta` 的写法）；`altered` 的 `outcomes` 等到点时由系统事件应用。非系统事件里的 `to: "happened"` 契约 1.5 没定义，抛异常 |

`improv` 和 `promise` 要记 `madeBy` / `resolvedBy`，所以应用的事件要带 `eventId`。提交前的试算可以不带，但 `world_state()` 遇到没有事件 ID 的约定或即兴设定要报错。

数据已经定了的几条（契约 2.4.1 和参考实现一致）：

- **同一时刻的顺序**：先节拍（按排定时间，再按 `order`），再期限，最后事件。所以叙事者提交一轮后先 `settle` 到新的时钟，下一轮的事件排在这些节拍后面。
- **系统事件的草稿**照契约 2.4.1 第 2、3 条写：`actor: "system"`、`type: "beat"`、`origin: "schedule"`，`t` = 结算的时刻，`dt: 0`，`place` = 节拍的地点，附节拍 ID 或变体 ID（B-0 用它取 `summary`）。`effects` 的顺序：
  1. 参与人物的 `relocate`（参考实现在节拍发生时把参与人物移到节拍地点；重放只看 `effects`，所以要写出来）；
  2. `{op:"beat", to:"happened"}`，再加节拍的 `outcomes`；有变体时是 `{op:"beat", to:"altered", outcomes: 变体的 outcomes, note: 变体 ID}`，不再另加 outcomes。
- **前提不成立**：到 `window.latest` 为止每次 `settle` 都再查，成立了就在那一刻发生；过了 `latest` 写 `{op:"beat", to:"prevented"}`，草稿带原因（前提不成立，或「時間切れ」），B-0 写进 `check.reason`。有 `delays` / `hastens` 出边的节拍除外：到点前提不成立就当场 `prevented`，它的分钟按 2.5.1 退还给下游（参考实现 `run()` 里的 `auto`）。
- **期限**：时钟到 `clock.deadline.t` 时，`onDeadline` 里 `if` 成立的规则写成一个系统事件草稿（`type: "action"`、`origin: "schedule"`），`effects` 是那些规则的 `then`，所有 `if` 按期限那一刻的状态判断。
- **还没结果的节拍在 WorldState 里**：有推迟或提前的记 `delayed` / `hastened`，其余记 `pending`。登记了 `altered` 的节拍到点之前也是 `pending`，因为 `requires` 把 `altered` 当作「发生了」。
- **预测**（backend-design 2.5，契约 `keyMoment` 第 2、3 条）= 在状态的副本上 `settle` 到底再 `classify`。`arrival_delta` 也要能从增量状态算（改动列表就是参考实现的 `sc.beats`）。不另写一套。

**4. 测试**

- 黄金文件逐字段相等。
- `packages/worldsim/tests/test_value_requires.py` 的用例（契约 1.6，C-16）包也要过：39 被拒、40 能过；同一事件里顺序两种；系统事件不受限；桥不在时设 `bridge` 被拒；值没变不判。

- 从任一节拍 `resume` 续跑，和一口气跑到底的结果相同。
- 每个情景的 `expect`、`expectBeats`、`expectTimes`、`expectVariant`、`expectVars` 都符合。
- **逐事件 = 一口气**：24 次推演都用旅人（`startPlace`、`items`），两边身份相同。增量这边：`initial_state` → 情景的 `beats` 改动在时钟 0 作为一个事件应用 → `settle` 到 `startT` → 情景的 `events` 按 `t` 逐个先 `settle` 到它的 `t` 再 `apply` → 最后 `settle` 到所有节拍都有结果。比较节拍结果和时刻、变量、人物所在地、`holdings`、世界结局。参考实现的 `late`、`blocked` 和最后仍是 `precondition-failed` 的，都对应 `prevented`。
- **重放**：把 `settle` 返回的草稿依次 `apply` 到结算前的状态，结果和 `settle` 返回的状态完全相同；从 `initial_state` 加事件日志里的全部事件重放，和逐事件算出来的状态完全相同。
- **再查**：前提在排定时间不成立、之后在 `latest` 之前变成成立的节拍，在那一刻发生（自己造一个小情景，例：`sc.king-hardened` 里 `beat.26` 的前提事后被满足）。
- **再查的下游**：上游因为前提晚了在 t 才发生时，`requires` 它、已过排定时间在等的下游在同一刻 t 接着发生（按 `order`），原作里两者的间隔不保留。这是契约 2.4.1 第 3 条的字面行为：推迟、提前的偏移照 2.5.1 平移，等前提造成的晚不平移。测试把它定下来，例：`beat.05` 之后用一个事件把 `var.promise.made` 设回 false、1450 再设回 true，`beat.06` 和 `beat.07` 都在 1450 发生（原作 1410、1425；参考实现已核对）。要不要改成「上游晚多久，下游跟着晚多久」，R1 试玩后看，改就是契约的事。
