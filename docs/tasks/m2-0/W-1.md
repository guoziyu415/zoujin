**2. Incremental API** (proposed by backend, used by the narrator and `eval_api`)

**2. 差分インターフェース**（バックエンドの提案。ナレーターと `eval_api` が使う）

| Function / 関数 | What it does / 何をするか |
|---|---|
| `initial_state(world, role_id)` | The state before this role's playthrough starts: clock 0, initial variable values, `var.player.location` = the role's `startPlace`, `var.act.current` = `startAct` (contract 3.1), where characters are, `holdings` (`Role.items`, `Character.items`), and this playthrough's scheduled time for each beat (= the original story when nothing has changed). The caller then `settle`s up to the role's `startT`, and beats due before the start are also written as system events / この身分のプレイ開始前の状態：時計 0、変数の初期値、`var.player.location` = 身分の `startPlace`、`var.act.current` = `startAct`（契約 3.1）、登場人物の居場所、`holdings`（`Role.items`、`Character.items`）、各ビートのこのプレイでの予定時刻（変更がなければ = 原作）。呼び出し側はそれに続けて身分の `startT` まで `settle` し、開始前に時刻が来たビートもシステムイベントとして書く |
| `apply(world, state, event)` | Applies one event's `effects` to the current state; clock = max(previous clock, `t` + `dt`). All 8 kinds of effect are supported; see the table below / 現在の状態にイベント 1 つの `effects` を適用する。時計 = max(それまでの時計, `t` + `dt`)。8 種の効果すべてに対応する。下の表を参照 |
| `settle(world, state, t2)` | Advances the clock to `t2`: settles the beats and deadlines whose scheduled time ≤ `t2`, in order of scheduled time. Returns the system event drafts (in order) and the settled state / 時計を `t2` まで進める：予定時刻 ≤ `t2` のビートと期限を予定時刻の順に決済する。システムイベントの草稿（順番どおり）と決済後の状態を返す |
| `world_state(state)` | Converts to contract 3.1's WorldState / 契約 3.1 の WorldState に変換する |
| `check_effects(world, state, effects, origin)` | Whether the effects themselves are valid: referenced IDs exist; `set` values match the StateVar's `type` and `values`; `inc` is only used on `int` and `minutes`; `hold` is only used on `portable` items; `beat`'s `to` and `minutes` are valid; when `origin` is not `schedule` (neither the narrator's candidate events nor director events are), `{op:"beat", to:"happened"}` is also reported, so the narrator rejects it at step 3 per R2 instead of raising only when it reaches `apply`. (Contract 1.6, C-16) When `origin` is not `schedule`, also check `StateVar.valueRequires`, with the rule following the reference implementation's `value_requires()`. Distinguish by `origin`, not by `actor`: director events also have `actor` `system`. Returns a list of problems. Checks only shape and references; R1–R7 belong to the narrator (B-0 and M2), and the "simplest judgment" in `evals/s2_check.py` can serve as a reference / 効果そのものが妥当かどうか：参照している ID が存在する。`set` の値が StateVar の `type` と `values` に合う。`inc` は `int`、`minutes` にだけ使う。`hold` は `portable` の物品にだけ使う。`beat` の `to` と `minutes` が妥当。`origin` が `schedule` でないとき（ナレーターの候補イベントも演出役のイベントもそうではない）は `{op:"beat", to:"happened"}` も報告し、ナレーターが第 3 ステップで R2 に従って却下する。`apply` まで行って初めて例外を投げることにはならない。（契約 1.6、C-16）`origin` が `schedule` でないときは `StateVar.valueRequires` も確認し、規則は参照実装の `value_requires()` に従う。`actor` ではなく `origin` で区別する：演出役のイベントも `actor` は `system`。問題のリストを返す。形と参照だけを確認する。R1〜R7 はナレーターのもの（B-0 と M2）で、`evals/s2_check.py` の「最も簡単な判定法」が参考になる |

`state` is the package's own type (e.g. `SimState`), serializable to JSON: all of WorldState's fields, plus this playthrough's changes to beats (in order — the reference implementation's `sc.beats`), and the moments beats happened and the variants used. Whether to cache `SimState` or replay from the event log every time is B-0's decision.

`state` はパッケージ独自の型（例：`SimState`）で、JSON として保存できる：WorldState のすべてのフィールドに、このプレイでのビートへの変更（順番どおり。参照実装の `sc.beats` にあたる）、ビートが起きた時刻と使ったバリアントを加える。`SimState` をキャッシュするか、毎回イベントログからリプレイするかは B-0 が決める。

The 8 kinds of effect (contract section 3):

8 種の効果（契約第 3 節）：

| Effect / 効果 | What it does / 何をするか |
|---|---|
| `set`, `inc`, `relocate`, `hold` / `set`、`inc`、`relocate`、`hold` | As in the reference implementation's `apply`. `inc` is clamped by the StateVar's `min` / `max` / 参照実装の `apply` のとおり。`inc` は StateVar の `min` / `max` で切り詰める |
| `learn` | Recorded in `knowledge` (character → facts learned, without duplicates) / `knowledge` に記録する（登場人物 → 知った事実。重複しない） |
| `improv` | Recorded in `runFacts` (`factId` → who said it, the line, `madeBy`) / `runFacts` に記録する（`factId` → 誰が言ったか、そのセリフ、`madeBy`） |
| `promise` | Recorded in `promises`. `made` creates an `open` one; `kept` / `broken` / `voided` can only change from `open`, writing `resolvedBy` / `promises` に記録する。`made` で `open` のものを 1 件作る。`kept` / `broken` / `voided` は `open` からしか変えられず、`resolvedBy` を書く |
| `beat` | In a system event with `origin: "schedule"`: this is a beat's outcome; `happened` / `altered` / `prevented` are recorded in `beats`, and `altered` applies the `outcomes` it carries on the spot. In other events: this is a change for this playthrough; `delayed` / `hastened` / `prevented` / `altered` are recorded in the change list, and the scheduled times of beats without an outcome yet are recomputed (several changes to the same beat: delays and advances add up as signed minutes, a net of 0 is dropped; `prevented` overrides earlier ones; other combinations raise, and `check_effects` reports `bad-state`. Changed 2026-10-10 per backend review, spelled out in contract section 3 for 1.6); `altered`'s `outcomes` are applied by the system event when the beat comes due. `to: "happened"` in a non-system event is undefined in contract 1.5 and raises / `origin: "schedule"` のシステムイベントの中では：これはビートの結果で、`happened` / `altered` / `prevented` を `beats` に記録し、`altered` はそれが持つ `outcomes` をその場で適用する。その他のイベントの中では：これはこのプレイでの変更で、`delayed` / `hastened` / `prevented` / `altered` を変更リストに記録し、まだ結果の出ていないビートの予定時刻を計算し直す（同じビートへの複数の変更：遅らせると早めるは符号付きの分数として足し合わせ、正味 0 なら取り除く。`prevented` はそれ以前のものを上書きする。その他の組み合わせは例外を投げ、`check_effects` が `bad-state` を報告する。2026-10-10 にバックエンドのレビューに従って変更し、契約第 3 節 1.6 で明記）。`altered` の `outcomes` は時刻が来たときにシステムイベントが適用する。システムイベント以外の `to: "happened"` は契約 1.5 で定義されておらず、例外を投げる |

`improv` and `promise` need to record `madeBy` / `resolvedBy`, so applied events must carry an `eventId`. A trial computation before commit may omit it, but `world_state()` must raise an error when it meets a promise or improvised detail without an event ID.

`improv` と `promise` は `madeBy` / `resolvedBy` を記録する必要があるので、適用するイベントは `eventId` を持たなければならない。コミット前の試算では持たなくてもよいが、`world_state()` はイベント ID のない約束や即興の設定に出会ったらエラーを報告しなければならない。

Points data has already decided (contract 2.4.1 and the reference implementation agree):

データが既に決めたこと（契約 2.4.1 と参照実装は一致している）：

- **Order at the same moment**: beats first (by scheduled time, then by `order`), then deadlines, then events. So after the narrator commits a turn it first `settle`s to the new clock, and the next turn's events come after those beats.
  **同じ時刻の順序**：ビート（予定時刻順、次に `order` 順）、期限、イベントの順。したがってナレーターは 1 ターンをコミットした後にまず新しい時計まで `settle` し、次のターンのイベントはそれらのビートの後に並ぶ。
- **System event drafts** follow items 2 and 3 of contract 2.4.1: `actor: "system"`, `type: "beat"`, `origin: "schedule"`, `t` = the moment of settlement, `dt: 0`, `place` = the beat's place, with the beat ID or variant ID attached (B-0 uses it to fetch the `summary`). Order of `effects`:
  **システムイベントの草稿**は契約 2.4.1 の第 2、3 項に従って書く：`actor: "system"`、`type: "beat"`、`origin: "schedule"`、`t` = 決済の時刻、`dt: 0`、`place` = ビートの場所。ビート ID またはバリアント ID を付ける（B-0 はそれで `summary` を取る）。`effects` の順序：
  1. `relocate` for the participating characters (the reference implementation moves participating characters to the beat's place when the beat happens; replay only looks at `effects`, so it has to be written out);
     参加する登場人物の `relocate`（参照実装はビートが起きたときに参加する登場人物をビートの場所へ移す。リプレイは `effects` しか見ないので、書き出す必要がある）。
  2. `{op:"beat", to:"happened"}`, followed by the beat's `outcomes`; when there is a variant, it is `{op:"beat", to:"altered", outcomes: the variant's outcomes, note: variant ID}`, with no further outcomes added.
     `{op:"beat", to:"happened"}` に続けてビートの `outcomes`。バリアントがあるときは `{op:"beat", to:"altered", outcomes: バリアントの outcomes, note: バリアント ID}` とし、outcomes を別に加えない。
- **Precondition does not hold**: re-check at every `settle` until `window.latest`, and if it holds, the beat happens at that moment; after `latest`, write `{op:"beat", to:"prevented"}`, with the draft carrying the reason (precondition not met, or 「時間切れ」), which B-0 writes into `check.reason`. The exception is beats with outgoing `delays` / `hastens` edges: if their precondition does not hold when due, they are `prevented` on the spot, and their minutes are returned downstream per 2.5.1 (`auto` in the reference implementation's `run()`).
  **前提が成り立たない**：`window.latest` まで `settle` のたびに再確認し、成り立ったらその時刻に起こる。`latest` を過ぎたら `{op:"beat", to:"prevented"}` と書き、草稿に理由（前提が成り立たない、または「時間切れ」）を付ける。B-0 はそれを `check.reason` に書く。例外は `delays` / `hastens` の出辺を持つビート：時刻が来たときに前提が成り立たなければその場で `prevented` になり、その分数は 2.5.1 に従って下流に返す（参照実装の `run()` の中の `auto`）。
- **Deadlines**: when the clock reaches `clock.deadline.t`, the rules in `onDeadline` whose `if` holds are written as one system event draft (`type: "action"`, `origin: "schedule"`), whose `effects` are those rules' `then`, with every `if` judged on the state at the deadline moment.
  **期限**：時計が `clock.deadline.t` に達したら、`onDeadline` の中で `if` が成り立つ規則を 1 つのシステムイベントの草稿（`type: "action"`、`origin: "schedule"`）として書く。`effects` はそれらの規則の `then` で、すべての `if` は期限の時点の状態で判定する。
- **Beats without an outcome yet, in WorldState**: those delayed or advanced are recorded as `delayed` / `hastened`, the rest as `pending`. A beat registered as `altered` is also `pending` until it comes due, because `requires` treats `altered` as "happened".
  **まだ結果の出ていないビートの WorldState での扱い**：遅らされたものや早められたものは `delayed` / `hastened` と記録し、その他は `pending` と記録する。`altered` が登録されたビートも時刻が来るまでは `pending`。`requires` は `altered` を「起きた」として扱うからである。
- **Forecasting** (backend-design 2.5, items 2 and 3 of the contract's `keyMoment`) = `settle` to the end on a copy of the state, then `classify`. `arrival_delta` must also be computable from the incremental state (the change list is the reference implementation's `sc.beats`). No second implementation.
  **予測**（backend-design 2.5、契約の `keyMoment` の第 2、3 項）= 状態のコピーの上で最後まで `settle` してから `classify` する。`arrival_delta` も差分の状態から計算できなければならない（変更リストが参照実装の `sc.beats` にあたる）。別の実装は書かない。

  パッケージも `packages/worldsim/tests/test_value_requires.py` のケース（契約 1.6、C-16）を通る：39 は却下され 40 は通る。同じイベント内での 2 通りの順序。システムイベントは制限を受けない。橋がないときに `bridge` を設定すると却下される。値が変わらないものは判定しない。
- The same input run twice gives the same result; `t` never goes backward.
  同じ入力を 2 回実行すると同じ結果になる。`t` は後戻りしない。
- `resume` from any beat gives the same result as running straight to the end.
  どのビートから `resume` して続けても、一気に最後まで実行した結果と同じになる。
- Each scenario's `expect`, `expectBeats`, `expectTimes`, `expectVariant` and `expectVars` all hold.
  各シナリオの `expect`、`expectBeats`、`expectTimes`、`expectVariant`、`expectVars` がすべて満たされる。
- **Event by event = straight through**: all 24 simulations use the traveler (`startPlace`, `items`), so both sides have the same role. On the incremental side: `initial_state` → apply the scenario's `beats` changes as one event at clock 0 → `settle` to `startT` → for each of the scenario's `events` in `t` order, first `settle` to its `t` and then `apply` it → finally `settle` until every beat has an outcome. Compare beat outcomes and times, variables, where characters are, `holdings`, and the world ending. The reference implementation's `late`, `blocked`, and those still `precondition-failed` at the end all correspond to `prevented`.
  **イベントごと = 一気に**：24 回のシミュレーションはすべて旅人（`startPlace`、`items`）を使い、両側で身分を同じにする。差分の側：`initial_state` → シナリオの `beats` の変更を時計 0 で 1 つのイベントとして適用 → `startT` まで `settle` → シナリオの `events` を `t` の順に 1 つずつ、まずその `t` まで `settle` してから `apply` → 最後にすべてのビートに結果が出るまで `settle`。ビートの結果と時刻、変数、登場人物の居場所、`holdings`、世界のエンディングを比べる。参照実装の `late`、`blocked`、最後まで `precondition-failed` のままのものは、いずれも `prevented` に対応する。
- **Replay**: applying the drafts returned by `settle`, in order, to the pre-settlement state gives exactly the state `settle` returned; replaying from `initial_state` plus all events in the event log gives exactly the state computed event by event.
  **リプレイ**：`settle` が返した草稿を決済前の状態に順に `apply` した結果は、`settle` が返した状態と完全に同じになる。`initial_state` にイベントログのすべてのイベントを加えてリプレイした結果は、イベントごとに計算した状態と完全に同じになる。
- **Re-check**: a beat whose precondition does not hold at its scheduled time but becomes true before `latest` happens at that moment (build a small scenario yourself, e.g. in `sc.king-hardened`, `beat.26`'s precondition being satisfied after the fact).
  **再確認**：予定時刻には前提が成り立たず、その後 `latest` より前に成り立つようになったビートは、その時刻に起こる（小さなシナリオを自分で作る。例：`sc.king-hardened` で `beat.26` の前提が後から満たされる）。
- **Downstream of re-checks**: when an upstream beat happens late at t because its precondition was late, the downstream beats that `require` it and are already past their scheduled time and waiting happen right after at the same moment t (by `order`); the interval between them in the original story is not preserved. This is the literal behavior of contract 2.4.1 item 3: offsets from delays and advances shift per 2.5.1, but lateness caused by waiting for a precondition does not shift. The tests pin this down, e.g. after `beat.05`, an event sets `var.promise.made` back to false, and at 1450 sets it back to true; `beat.06` and `beat.07` both happen at 1450 (1410 and 1425 in the original story; verified with the reference implementation). Whether to change it to "the downstream is late by as much as the upstream" will be looked at after the R1 playtest; if changed, that is a matter for the contracts.
  **再確認の下流**：上流が前提の遅れのために t で起きたとき、それを `requires` していて既に予定時刻を過ぎて待っている下流は、同じ時刻 t に続けて起こる（`order` 順）。原作での両者の間隔は保たれない。これは契約 2.4.1 第 3 項の文字どおりの挙動：遅らせる・早めるによるずれは 2.5.1 に従って平行移動するが、前提を待ったことによる遅れは平行移動しない。テストでこれを固定する。例：`beat.05` の後にイベントで `var.promise.made` を false に戻し、1450 に再び true にすると、`beat.06` と `beat.07` はどちらも 1450 に起こる（原作では 1410、1425。参照実装で確認済み）。「上流が遅れた分だけ下流も遅れる」に変えるかどうかは R1 の試遊の後に検討し、変えるなら契約の問題になる。
- `world_state()`'s output passes C-2's `world-state.schema.json`. Whichever of W-1 and C-2 merges later adds this test.
  `world_state()` の出力が C-2 の `world-state.schema.json` を通る。W-1 と C-2 のうち後からマージする方がこのテストを加える。
