## Goal / 目標

On a machine without any cloud credentials, once this is done you can see:

クラウドの認証情報が一切ないマシン上で、完成すると次のことが確認できる：

1. One command (`docker compose up`) brings up PostgreSQL, the gateway and the narrator.
   1 つのコマンド（`docker compose up`）で PostgreSQL、gateway、narrator が起動する。
2. Log in with an invite code → start a playthrough → connect the WebSocket → `hello` / `welcome` → `focus` on a character → `session_ready` → speak one turn:
   招待コードでログイン → プレイを開始 → WebSocket に接続 → `hello` / `welcome` → 登場人物に `focus` → `session_ready` → 1 ターン話す：

**3. Authentication**

**3. 認証**

- `POST /v1/auth/login`: exchanges an invite code for a session cookie (`HttpOnly; Secure; SameSite=Lax`, 30 days, sliding renewal on every use). Under local http, `Secure` is turned off by a development switch.
  `POST /v1/auth/login`：招待コードをセッション Cookie（`HttpOnly; Secure; SameSite=Lax`、30 日、使うたびにスライド更新）と交換する。ローカルの http では、`Secure` は開発用スイッチでオフにする。
- `POST /v1/auth/logout`, `GET /v1/me`.
  `POST /v1/auth/logout`、`GET /v1/me`。
- The WebSocket handshake checks the cookie and `Origin`; REST calls that change data check `Content-Type: application/json` and `Origin`.
  WebSocket のハンドシェイクは Cookie と `Origin` を確認する。データを変更する REST は `Content-Type: application/json` と `Origin` を確認する。
- Invite codes are generated from the command line (`uv run zoujin-admin invite create`): the plaintext is printed once, and only the hash is stored in the database.
  招待コードはコマンドラインで生成する（`uv run zoujin-admin invite create`）：平文は一度だけ表示し、データベースにはハッシュだけを保存する。
- Invite code format: `inv-` plus 4 groups of 4 Crockford base32 characters (80 bits of randomness), written schematically as `inv-XXXX-XXXX-XXXX-XXXX` (only this all-X placeholder form is on the secret-scanning allowlist). R-0's secret scanning checks for this format. Login is case-insensitive, ignores spaces and extra hyphens, and per Crockford's rules treats I and L as 1 and O as 0. Tests generate invite codes at runtime and never write any into the repo.
  招待コードの形式：`inv-` に Crockford base32 の 4 文字 × 4 グループ（80 ビットの乱数）。表記例：`inv-XXXX-XXXX-XXXX-XXXX`（すべて X のこのプレースホルダー表記だけが秘密スキャンの許可リストに入っている）。R-0 の秘密スキャンはこの形式で検査する。ログイン時は大文字小文字を区別せず、空白と余分なハイフンを無視し、Crockford の規則に従って I と L を 1、O を 0 として扱う。テストは実行時に招待コードを生成し、1 つもリポジトリに書かない。

**6. Model interfaces**

**6. モデルのインターフェース**

Define one interface each for Live and the text model. This card builds the fake and replay implementations, not the real ones:

Live とテキストモデルにそれぞれインターフェースを 1 つ定義する。このカードでは偽の実装とリプレイの実装を作り、本物の実装は作らない：

- **Fake Live**: reads `fixtures/fake-voice/`. Each reply = 24 kHz PCM + character subtitles + player subtitles, emitted in chunks at realistic intervals. The PCM uses synthesized sound (e.g. tones generated per sentence length); no voice recorded by any real person or model is included.
  **偽 Live**：`fixtures/fake-voice/` を読む。各返答 = 24 kHz PCM + 登場人物の字幕 + プレイヤーの字幕で、実際の間隔でチャンクを送り出す。PCM は合成音（たとえば文の長さに応じて生成した音）を使い、実在の人やモデルが録った声は一切入れない。
- **Fake text model** (`fake`, the default for CI and E-0): each prompt type has a deterministic default output that passes the schema (e.g. extraction → no candidate events; character text reply → a fixed sentence), answers any request, and never crashes on a request it has not seen. Specific outputs a script needs go in `fixtures/fake-text/`, overriding the default per prompt type with simple conditions (e.g. the player's words contain a certain word).
  **偽テキストモデル**（`fake`、CI と E-0 の既定）：プロンプトの種類ごとに、スキーマを通る決定的な既定出力を 1 つ持つ（例：抽出 → 候補イベントなし。登場人物のテキスト返答 → 固定の一文）。どんなリクエストにも答え、見たことのないリクエストでクラッシュしない。台本が必要とする特定の出力は `fixtures/fake-text/` に置き、プロンプトの種類ごとに簡単な条件（例：プレイヤーの発言にある単語が含まれる）で既定値を上書きする。
- **Replay** (`replay`): looks up `fixtures/model-replays/` by (model, prompt version, sha256 of the normalized request). If nothing is found, raise `ReplayMissing` (the exception class is named exactly this; E-0 records it as "replay missing or stale"); never silently return empty and never fall back to the fake model.
  **リプレイ**（`replay`）：（モデル、プロンプトのバージョン、正規化したリクエストの sha256）で `fixtures/model-replays/` を引く。見つからなければ `ReplayMissing` を投げる（例外クラス名はまさにこれ。E-0 はこれを「リプレイ欠落または期限切れ」として記録する）。黙って空を返したり、偽モデルに戻ったりしない。
- **The replay format** is fixed by this card: JSONL, each line with `key`, `kind` (prompt type), `model`, `promptVersion`, `request` (after redaction), `response`, `usage` (token counts), `costUsd`, `recordedAt`. Recording real models on the Mac later and E-0's `live` auto-saving replays both use this format; the recording code is not in this card.
  **リプレイの形式**はこのカードで決める：JSONL で、各行に `key`、`kind`（プロンプトの種類）、`model`、`promptVersion`、`request`（マスキング後）、`response`、`usage`（トークン数）、`costUsd`、`recordedAt`。今後 Mac で本物のモデルを録るときも、E-0 の `live` がリプレイを自動保存するときもこの形式を使う。録るためのコードはこのカードに含まない。
- Every prompt has a version number (a hash of the prompt text is enough), written into the Trace and the replay.
  各プロンプトにはバージョン番号がある（プロンプト本文のハッシュで十分）。Trace とリプレイに書き込む。
- The real model implementation is not written. The code has no path that reads Google credentials; `ZJ_MODEL` accepts only `fake` and `replay`.
  本物のモデルの実装は書かない。コードには Google の認証情報を読む経路がない。`ZJ_MODEL` は `fake` と `replay` だけを受け付ける。

**7. Narrator skeleton**

**7. ナレーターの骨格**

1. Per playthrough, take the earliest pending turn: `FOR UPDATE SKIP LOCKED` plus a lease.
   プレイごとに最も古い保留中のターンを取る：`FOR UPDATE SKIP LOCKED` とリース。
2. Call the fake extraction outside the transaction, recording the `lastSeq` at read time.
   トランザクションの外で偽の抽出を呼び、読み取り時の `lastSeq` を記録する。
3. Rule checks use W-1's `check_effects` (references exist, values are valid, variable ranges); problematic candidates are rejected. R1–R7 are not done in this card, nor are the model checks (R5, R6); record `skipped` in the event's `check`. W-1's `apply` raises on `{op: "beat", to: "happened"}` in a non-system event: such a candidate is rejected at this step and must never reach `apply`.
   ルール検査は W-1 の `check_effects`（参照が存在する、値が妥当、変数の範囲）を使い、問題のある候補は却下と判定する。R1〜R7 はこのカードではやらず、モデルによる検査（R5、R6）もやらない。イベントの `check` に `skipped` と記録する。W-1 の `apply` はシステムイベント以外の `{op: "beat", to: "happened"}` に対して例外を投げる：そうした候補はこのステップで却下とし、`apply` に到達させてはならない。
4. **Single-transaction commit**:
   **単一トランザクションのコミット**：
   - Lock this playthrough and verify `lastSeq` has not changed;
     このプレイをロックし、`lastSeq` が変わっていないことを確認する。
   - Assign `eventId` and `seq` to this turn's events (W-1's `apply` needs `eventId` to record improvised details and promises), and apply them in `seq` order with W-1's `apply`;
     このターンのイベントに `eventId` と `seq` を割り当て（W-1 の `apply` は即興の設定と約束を記録するのに `eventId` を使う）、`seq` 順に W-1 の `apply` で適用する。
   - Use W-1's `settle` to settle the beats and deadlines that come due up to the new clock, complete the returned system event drafts into full events (`summary` uses the beat's or variant's `summary`; the reason for `prevented` goes into `check.reason`), and write them next; at the same moment, beats come first, then deadlines, then events (already fixed by W-1);
     W-1 の `settle` で新しい時刻までに来たビートと期限を決済し、返されたシステムイベントの草稿を完全なイベントに補って（`summary` はビートまたはバリアントの `summary` を使い、`prevented` の理由は `check.reason` に書く）続けて書き込む。同じ時刻ではビート、期限、イベントの順（W-1 で決定済み）。
   - Write all of this turn's events, including rejected ones; before writing to the database, validate each event against the data contract's Event type, and roll back the whole turn if any fails;
     このターンのすべてのイベントを書き込む。却下されたものも書く。データベースに書く前に各イベントをデータ契約の Event 型で検証し、通らなければターン全体をロールバックする。
   - Update `world_state` and mark the turn complete.
     `world_state` を更新し、ターンを完了にする。
   - The same happens when starting a playthrough: W-1's `initial_state(world, role)`, then `settle` up to the role's `startT`; beats due before the start (e.g. `beat.01`) are written as system events.
     プレイ開始時も同様：W-1 の `initial_state(world, role)` を行い、身分の `startT` まで `settle` する。開始前に時刻が来たビート（例 `beat.01`）はシステムイベントとして書く。
   - The `world_state` table stores W-1's `SimState` (JSON, with its corresponding `seq`); the external WorldState is computed on the fly with W-1's `world_state()`.
     `world_state` テーブルには W-1 の `SimState`（JSON、対応する `seq` 付き）を保存する。外部向けの WorldState は W-1 の `world_state()` でその場で計算する。
5. After commit, `NOTIFY`; the gateway pushes `commit` and `turn_settled`.
   コミット後に `NOTIFY` し、ゲートウェイが `commit` と `turn_settled` を送る。
6. If `lastSeq` has changed, discard this result and start over from the rule checks. If any step fails, roll back the whole turn and retry with the same idempotency key.
   `lastSeq` が変わっていたらこの結果を捨て、ルール検査からやり直す。どのステップが失敗してもターン全体をロールバックし、同じ冪等キーで再試行する。
7. The gateway calls the narrator: locally over HTTP (two processes), shaped like the later Cloud Run internal call. OIDC verification is turned off locally, with a switch left in place.
   gateway から narrator を呼ぶ：ローカルでは HTTP（2 つのプロセス）で、形は将来の Cloud Run の内部呼び出しに合わせる。OIDC の検証はローカルではオフにし、スイッチを残す。

**8. Replay**

**8. リプレイ**

`uv run zoujin-admin replay <playthroughId>`: rebuilds `SimState` from `initial_state` plus all events applied in `seq` order with W-1's `apply`, compares it with the one in the `world_state` table, and exits with a non-zero status on mismatch.

`uv run zoujin-admin replay <playthroughId>`：`initial_state` にすべてのイベントを `seq` 順に W-1 の `apply` で適用して `SimState` を再構築し、`world_state` テーブルのものと比較する。一致しなければ非ゼロのステータスで終了する。

**9. Minimal `eval_api`**

**9. `eval_api` の最小版**

- Called within the Python package, no HTTP. Entry points and parameter names follow api-contract section 7, so E-0 connects directly.
  Python パッケージ内で呼び出し、HTTP は開かない。入口とパラメータ名は api-contract 第 7 節に従い、E-0 が直接つなぐ。
- `setup`: supports `role`, `place`, `budgetTier` (only recorded, not applied); for the starting point, `scenario` (simulated with W-1 only) and `checkpoint` (simulated with W-1 up to that moment, with the result written as this playthrough's initial events), and `events` (written directly, marked as eval setup in the trace; those given only `effects` are completed into full events per api-contract section 7, with `check.checker` set to `eval-setup`). `sc.canon` is the original-novel path. `persona` + `seed` (simulated playthroughs) are not done: calling `setup` with a `persona` immediately raises `EvalNotImplemented("persona")` (E7's 11 cases and E5-001 are of this kind).
  `setup`：`role`、`place`、`budgetTier`（記録するだけで効かない）に対応する。開始点として `scenario`（W-1 のシミュレーションのみ）と `checkpoint`（W-1 でその時点までシミュレーションし、結果をこのプレイの初期イベントとして書く）、および `events`（直接書き込み、trace では評価用の配置として印を付ける。`effects` だけが与えられたものは api-contract 第 7 節に従って完全なイベントに補い、`check.checker` に `eval-setup` と書く）に対応する。`sc.canon` は原作どおりのルート。`persona` + `seed`（模擬プレイ）はやらない：`persona` 付きの `setup` を呼ぶとすぐに `EvalNotImplemented("persona")` を投げる（E7 の 11 ケースと E5-001 がこれに当たる）。
- Steps: `say(to, text)`, `advance(minutes)` and `check(candidate, turn, modelChecks?)`. `say` goes through the same narrator flow as a `text` turn. `check` hands the candidate event directly to step 3 without committing (this is how S-2's data `evals/s2/` runs); this card has no step 4, and the model parts of R5 and R6 record `skipped`.
  ステップは `say(to, text)`、`advance(minutes)`、`check(candidate, turn, modelChecks?)`。`say` は `text` のターンと同じナレーターの流れを通る。`check` は候補イベントを直接第 3 ステップに渡し、コミットしない（S-2 のデータ `evals/s2/` はこのように実行する）。このカードには第 4 ステップがなく、R5、R6 のモデル部分は `skipped` と記録する。

  第 7 節のその他のステップとクエリで、このカードがやらないものは、呼ぶと同じ例外クラスを投げる（例：`EvalNotImplemented("delete_memory")`）。E-0 はそれを「スキップ：バックエンド未実装」と記録し、合格にはせず、ランナーもクラッシュさせない。

## Interfaces / インターフェース

  イベントと世界状態：`packages/contracts/schemas/data/` の Event、WorldState。

## Acceptance check / 受け入れ確認

After `docker compose up`, `uv run pytest services/backend` passes in full, and must include these groups of tests:

`docker compose up` の後、`uv run pytest services/backend` がすべて通ること。その中に必ず次のテスト群を含める：

1. **End to end**: real PostgreSQL, two processes, one WebSocket test client.
   **エンドツーエンド**：本物の PostgreSQL、2 つのプロセス、WebSocket のテストクライアント 1 つ。
   - Log in → start a playthrough → `hello` → `focus` → speak one turn with fake Live.
     ログイン → プレイ開始 → `hello` → `focus` → 偽 Live で 1 ターン話す。
   - Received in order: `transcript` (the player's first `final: false` then `final: true`, the character's `final: true` with `source`), downstream binary, `turn_complete`, `commit` (`fromSeq` = previous `seq` + 1), `turn_settled`.
     受信の順：`transcript`（プレイヤーはまず `final: false`、次に `final: true`、登場人物は `source` 付きの `final: true`）、下りバイナリ、`turn_complete`、`commit`（`fromSeq` = 前回の `seq` + 1）、`turn_settled`。
   - Run the same turn again with `text`.
     同じターンを `text` でもう一度通す。
2. **Schema**: the tests intercept all sends, and every message passes C-1's schema.
   **スキーマ**：テストですべての送信を横取りし、どのメッセージも C-1 のスキーマを通る。
3. **Single transaction**: inject a failure at each step of the commit; the database holds no half-turn data; the result after retry is the same as a single success.
   **単一トランザクション**：コミットの各ステップで失敗を注入しても、データベースに半端なターンのデータが残らない。再試行後の結果は、一度で成功した場合と同じ。
4. **Concurrency**:
   **並行性**：
   - Push two turns into the same playthrough at once; they commit in order and `seq` is contiguous;
     同じプレイに同時に 2 ターンを入れると、順番にコミットされ、`seq` が連続する。
   - Two playthroughs in parallel do not block each other;
     2 つのプレイを並行させても、互いにブロックしない。
   - When a beat coming due changes `lastSeq`, this result is discarded and redone.
     時刻が来たビートが `lastSeq` を変えたとき、この結果は捨てられやり直される。
5. **Replay**: after running the minimal script, `replay` matches.
   **リプレイ**：最小の台本を通した後、`replay` が一致する。
6. **Reconnect**: `hello { lastSeq }` resends the missing `commit`s.
   **再接続**：`hello { lastSeq }` で欠けた `commit` が再送される。
7. **Authentication**:
   **認証**：
   - REST without a cookie returns 401, and the WebSocket handshake is rejected;
     Cookie のない REST は 401 を返し、WebSocket のハンドシェイクは拒否される。
   - A wrong `Origin` returns 403;
     `Origin` が正しくなければ 403 を返す。
   - The invite code table has no plaintext.
     招待コードのテーブルに平文がない。
8. **No network**: pytest intercepts sockets and allows only the local machine.
   **ネットワークなし**：pytest でソケットを横取りし、ローカルマシンだけを許可する。
9. **Eval entry point**: all 10 starting points in `evals/s2/s2_dev.jsonl` can be set up, and candidate events returned through `check` give a `CheckResult` that passes the schema (whether the verdicts are correct is the acceptance check of the M2 narrator card, not this one); `setup(checkpoint=…)` + `say` + `state()` runs through, and the result matches W-1's simulation from the same starting point; unimplemented steps and `setup` with `persona` all raise `EvalNotImplemented`.
   **評価の入口**：`evals/s2/s2_dev.jsonl` の 10 個の開始点がすべて立ち上がり、候補イベントが `check` を通してスキーマに合う `CheckResult` を返す（判定が正しいかどうかは M2 のナレーターのカードの受け入れ確認で、このカードではない）。`setup(checkpoint=…)` + `say` + `state()` が通り、結果が同じ開始点からの W-1 のシミュレーションと一致する。未実装のステップと `persona` 付きの `setup` はいずれも `EvalNotImplemented` を投げる。
10. **Replay of model calls**: with `ZJ_MODEL=replay`, requests present in the fixtures are returned as-is; after changing the prompt version or the request, it reports "replay missing or stale".
    **モデル呼び出しのリプレイ**：`ZJ_MODEL=replay` のとき、fixture にあるリクエストはそのまま返る。プロンプトのバージョンやリクエストを変えると「リプレイ欠落または期限切れ」を報告する。

CI runs the same tests with a PostgreSQL service container, all green.

CI では PostgreSQL のサービスコンテナで同じテストを実行し、すべてグリーンになる。

## Forbidden / 禁止事項

  デプロイしない、秘密鍵に触れない、本物のモデルを呼ばない、お金を使わない（dev-plan 2.2）。

  本物のモデルを呼ぶコードを書かない。Google の認証情報を一切読まない。環境変数からプロジェクト ID も読まない。

  ログと Trace に発話の原文を書かない。ID と件数だけを書く（data-design 第 8 節）。

  fixture には自分たちで書いたセリフだけを入れ、実在の人の録音や実在の人が言ったことは入れない。

  デプロイ先のアドレス、プロジェクト ID、招待コードの平文はリポジトリに入れない。
