## 目标

做完以后能看到：

1. `uv run zoujin-mock` 一条命令启动，也可以 `docker compose up mock`。
2. 它在同一个源上提供 api-contract 的 REST 和 WebSocket。按剧本回放写好的会话，保留真实的时间间隔。
3. 覆盖 api-contract 第 7 节列的 11 种情形，外加几种前端最容易处理错的边角情况（见「做」第 4 条）。
4. 发出的每条消息都过 C-1 的 Schema。
5. 前端 F-0 可以只对着它开发，前端 CI 可以对着它跑端到端测试，不需要数据库，不需要任何凭证。

## 依据

## 范围

### 做

**1. 位置**

- `services/backend/` 包里的 `mock/` 子包，入口 `zoujin-mock`。
- 不 import 数据库和叙事者的代码。B-0 还没合并时也能单独跑。

**2. REST**

- 全部 v1 接口（16 个，2.10 分享除外），回 `fixtures/mock/rest/` 里的固定数据，按路径参数挑。
- 状态码照 api-contract。例：结局先回 `202 { status: "pending" }`，几秒后回 `200`；开局时已有进行中的局回 `409 active_playthrough_exists`。
- 登录只认一个固定的码 `mock`，发会话 Cookie。本地 http 下不带 `Secure`。
- 改数据的接口照样查 `Origin` 和 `Idempotency-Key`，让前端早点发现自己漏发。
- 内存里记一点状态（重启就清空）：每个 Cookie 一局进行中的局，`/v1/me` 的 `activePlaythrough` 跟着变；开局遇到进行中的局回 `409`；`DELETE` 之后可以重新开局（F-0 的「新しく始める」）。
- 控制接口 `POST /__mock/expire-session`：让当前 Cookie 失效，之后 REST 回 `401`、WebSocket 握手以 `4001` 关闭（F-0 测「401 回登录」）。

**3. WebSocket 剧本**

- 剧本放 `fixtures/sessions/<名字>.jsonl`，一行一步，例：
  - `{"on": "activity_end", "delayMs": 120, "send": {…一条服务端消息…}}`
  - `{"on": "activity_end", "delayMs": 900, "audio": {"seconds": 2.4, "chunkMs": 40}}`
- mock 收到前端的消息后按剧本往下走。一轮的触发既认 `activity_end`，也认 `text`（F-0 先走文字）。`turnId`、`turnSeq` 用前端发来的值替换占位符；服务端发起的轮次用最高位为 1 的 `turnSeq`（3.1）。
- 每局记住发过的 `commit`。任何一次重连（不只是 `goaway` 之后）收到 `hello { lastSeq }`，都补发 `lastSeq` 之后的，`GET …/events?afterSeq=` 回同一批（F-0 测「断网再连，不重复、不丢」）。
- 控制接口 `POST /__mock/drop`：服务端主动断开当前连接，不发 `goaway`，模拟断网。
- 选剧本：mock 专用的控制接口 `POST /__mock/scenario { "name": … }`，在 `/v1` 之外，不进契约。默认剧本是「导览」：把全部情形串成一局。
- 速度：默认按剧本的 `delayMs`；`--speed 0` 不等待（给 CI 用）；`--speed 2` 两倍慢。
- 音频：合成的 24 kHz PCM，长度按句子算。不放任何真人或模型录的声音。

**4. 剧本至少这些**

api-contract 第 7 节的 11 种：

1. 一整轮对话：有事件、记忆、关键时刻（`reveal`）
2. 闲聊轮：`turn_settled` 没有事件
3. 打断：`interrupted`
4. 作废（`retracted` 和 `too_late`）和识别改正（`text { via: "correction" }`）
5. 意图确认：按按钮回答、超时
6. 人物走过来：`approach` → `approach_arrived` → `turn_started`
7. 幕末自由说：`act_ended` → `act_propose` → `act_plan_result` → `act_transition`
8. `goaway`，重连后补发 `commit`
9. 关闭码 `4009`（同一局在别的标签页打开）
10. 出戏卡：`safety_pause` → `safety_resume` → `safety_resumed`
11. 结局：`ending_started` → `ending_ready` → REST 取结局

再加 5 种边角情况：

- 人物的 `transcript` 定稿晚于 `turn_complete` 到
- 补转写也失败：`{ final: true, text: null, source: "fallback" }`
- `turn_complete { audio: false }`（人物没出声）
- `degraded`（改为文字回答）
- `limits`（今天的语音还剩 5 分钟）

另有一个「未来的消息」剧本：发一条 Schema 里没有的 `type`（例：`{"type": "future_feature"}`），只给 F-0 测「不认识的消息类型忽略」。这一步在剧本里标 `"unchecked": true`，是唯一跳过 Schema 自检的地方。

**5. 自检**

每条消息发出前用 C-1 的 Schema 校验（标了 `unchecked` 的那一步除外）。不过的就不发，在终端报错，让开发时立刻看见。

### 不做

- 判定逻辑、数据库、真模型、假 Live 以外的任何语音处理。
- 剧本以外的输入：忽略，在终端记一行。

## 接口

全部消息和响应用 `packages/contracts` 生成的类型构造，发出前过 Schema。

## 验收

- 用 Python 测试客户端在 `--speed 0` 下跑完全部 17 个剧本（11 + 5 + 「未来的消息」）：除标了 `unchecked` 的那一条，每条消息都过 Schema；一轮的顺序和 api-contract 3.5 的示例一致。
- 状态和控制接口：409 → 删除 → 重新开局；`expire-session` 后 401 和 4001；`drop` 后重连补发的 `commit` 不重复、不丢。
- **覆盖检查**：3.3 的 30 种服务端消息里，除 `event_rejected`（只在调试模式）以外，每种至少在一个剧本里出现。少了就红。
- 16 个 REST 接口都回过 Schema 校验的响应。
- 前端评审人用 F-0 的网络层（F-0 还没好时用任意 WebSocket 客户端）连上，能走完「导览」剧本。
- mock 的契约测试进 CI，`--speed 0` 下 30 秒内跑完，全绿。

## 禁止

- 不部署、不碰密钥、不调真模型、不花钱（dev-plan 2.2）。
- 剧本和固定数据里只放自己写的或设计文档里已有的日语，不放真人说过的话、真实的人名或个人信息。
- 不往契约里加 mock 专用的字段；mock 的控制只走 `/__mock/*`（`scenario`、`expire-session`、`drop`）。

## 评审

前端：剧本是否覆盖前端要处理的情形，时序是否像真的。数据：剧本里的事件、记忆、约定、结局符合契约。
