## Goal / 目標

Once this is done you can see:

完成すると次のことが確認できる：

1. `uv run zoujin-mock` starts it with one command; `docker compose up mock` also works.
   `uv run zoujin-mock` の 1 コマンドで起動する。`docker compose up mock` でもよい。
2. It serves the api-contract REST and WebSocket on the same origin. It plays back pre-written sessions from scripts, keeping realistic time intervals.
   api-contract の REST と WebSocket を同じオリジンで提供する。台本どおりに書かれたセッションを再生し、実際の時間間隔を保つ。
3. It covers the 11 situations listed in api-contract section 7, plus a few edge cases the frontend most easily gets wrong (see "In scope" item 4).
   api-contract 第 7 節に挙げた 11 の状況に加え、フロントエンドが最も扱いを誤りやすい境界ケースをいくつか網羅する（「やること」第 4 項を参照）。
4. Every message it sends passes C-1's schema.
   送信するすべてのメッセージが C-1 のスキーマを通る。
5. Frontend F-0 can be developed against it alone, and the frontend CI can run end-to-end tests against it, with no database and no credentials of any kind.
   フロントエンドの F-0 はこれだけを相手に開発でき、フロントエンドの CI はこれを相手にエンドツーエンドテストを実行できる。データベースも認証情報も一切不要。

## Scope / 範囲

### In scope / やること

**1. Location**

**1. 場所**

- A `mock/` subpackage in the `services/backend/` package, with the entry point `zoujin-mock`.
  `services/backend/` パッケージの `mock/` サブパッケージで、エントリポイントは `zoujin-mock`。
- It does not import database or narrator code. It runs on its own even before B-0 is merged.
  データベースとナレーターのコードを import しない。B-0 がまだマージされていなくても単独で動く。

**2. REST**

- All v1 endpoints (16, excluding 2.10 sharing) return the fixed data in `fixtures/mock/rest/`, chosen by path parameters.
  すべての v1 エンドポイント（16 個、2.10 の共有を除く）は `fixtures/mock/rest/` の固定データを返し、パスパラメータで選ぶ。
- Status codes follow api-contract. E.g. the ending first returns `202 { status: "pending" }` and a few seconds later `200`; starting a playthrough while one is in progress returns `409 active_playthrough_exists`.
  ステータスコードは api-contract に従う。例：エンディングはまず `202 { status: "pending" }` を返し、数秒後に `200` を返す。進行中のプレイがあるときにプレイを開始すると `409 active_playthrough_exists` を返す。
- Login accepts only the fixed code `mock` and issues a session cookie. Under local http, no `Secure`.
  ログインは固定のコード `mock` だけを受け付け、セッション Cookie を発行する。ローカルの http では `Secure` を付けない。
- Endpoints that change data still check `Origin` and `Idempotency-Key`, so the frontend notices early if it forgets to send them.
  データを変更するエンドポイントはそれでも `Origin` と `Idempotency-Key` を確認し、フロントエンドが送り忘れに早く気づけるようにする。
- A little state is kept in memory (cleared on restart): one in-progress playthrough per cookie, with `/v1/me`'s `activePlaythrough` following it; starting a playthrough while one is in progress returns `409`; after `DELETE` a new playthrough can be started (F-0's 「新しく始める」).
  メモリにわずかな状態を持つ（再起動で消える）：Cookie ごとに進行中のプレイを 1 つ持ち、`/v1/me` の `activePlaythrough` がそれに追従する。進行中のプレイがあるときに開始すると `409` を返す。`DELETE` の後は新たにプレイを開始できる（F-0 の「新しく始める」）。
- Control endpoint `POST /__mock/expire-session`: invalidates the current cookie, after which REST returns `401` and the WebSocket handshake closes with `4001` (F-0 tests "401 goes back to login").
  制御用エンドポイント `POST /__mock/expire-session`：現在の Cookie を無効にする。その後 REST は `401` を返し、WebSocket のハンドシェイクは `4001` で閉じる（F-0 が「401 でログインに戻る」をテストする）。

**3. WebSocket scripts**

**3. WebSocket の台本**

- Scripts live in `fixtures/sessions/<name>.jsonl`, one step per line, e.g.:
  台本は `fixtures/sessions/<名前>.jsonl` に置き、1 行 1 ステップ。例：
  - `{"on": "activity_end", "delayMs": 120, "send": {…a server message…}}`
  - `{"on": "activity_end", "delayMs": 900, "audio": {"seconds": 2.4, "chunkMs": 40}}`
- After receiving a message from the frontend, the mock advances through the script. A turn is triggered by either `activity_end` or `text` (F-0 does text first). `turnId` and `turnSeq` replace placeholders with the values sent by the frontend; server-initiated turns use a `turnSeq` whose highest bit is 1 (3.1).
  モックはフロントエンドからメッセージを受け取ると台本に従って進む。1 ターンのきっかけは `activity_end` と `text` のどちらでもよい（F-0 はまずテキストで進める）。`turnId`、`turnSeq` はフロントエンドから送られた値でプレースホルダーを置き換える。サーバー起点のターンは最上位ビットが 1 の `turnSeq` を使う（3.1）。
- Each playthrough remembers the `commit`s it has sent. On any reconnect (not only after `goaway`), receiving `hello { lastSeq }` resends those after `lastSeq`, and `GET …/events?afterSeq=` returns the same batch (F-0 tests "drop the network and reconnect: no duplicates, nothing lost").
  プレイごとに送信した `commit` を覚えておく。どの再接続でも（`goaway` の後に限らない）`hello { lastSeq }` を受け取ったら `lastSeq` 以降のものを再送し、`GET …/events?afterSeq=` も同じものを返す（F-0 が「ネットワークが切れて再接続しても、重複も欠落もない」をテストする）。
- Control endpoint `POST /__mock/drop`: the server actively drops the current connection without sending `goaway`, simulating a network loss.
  制御用エンドポイント `POST /__mock/drop`：サーバーが自ら現在の接続を切る。`goaway` は送らず、ネットワーク切断を模擬する。
- Choosing a script: the mock-only control endpoint `POST /__mock/scenario { "name": … }`, outside `/v1` and not part of the contract. The default script is "tour": all situations chained into one playthrough.
  台本の選択：モック専用の制御用エンドポイント `POST /__mock/scenario { "name": … }`。`/v1` の外にあり、契約には入れない。既定の台本は「ツアー」：すべての状況を 1 つのプレイにつなげたもの。
- Speed: by default follows the script's `delayMs`; `--speed 0` does not wait (for CI); `--speed 2` is twice as slow.
  速度：既定は台本の `delayMs` に従う。`--speed 0` は待たない（CI 用）。`--speed 2` は 2 倍遅い。
- Audio: synthesized 24 kHz PCM, length computed from the sentence. No voice recorded by any real person or model.
  音声：合成した 24 kHz PCM で、長さは文から計算する。実在の人やモデルが録った声は一切入れない。

**4. Scripts, at minimum**

**4. 少なくとも用意する台本**

The 11 from api-contract section 7:

api-contract 第 7 節の 11 種：

1. A full conversation turn: with events, memories, a key moment (`reveal`)
   会話の 1 ターン全体：イベント、記憶、重要な瞬間（`reveal`）あり
2. A small-talk turn: `turn_settled` with no events
   雑談のターン：イベントのない `turn_settled`
3. Interruption: `interrupted`
   割り込み：`interrupted`
4. Retraction (`retracted` and `too_late`) and recognition correction (`text { via: "correction" }`)
   取り消し（`retracted` と `too_late`）と認識の訂正（`text { via: "correction" }`）
5. Intent confirmation: answering with a button, timeout
   意図の確認：ボタンで答える、タイムアウト
6. A character walks over: `approach` → `approach_arrived` → `turn_started`
   登場人物が歩いてくる：`approach` → `approach_arrived` → `turn_started`
7. Free talk at the end of an act: `act_ended` → `act_propose` → `act_plan_result` → `act_transition`
   幕末の自由発言：`act_ended` → `act_propose` → `act_plan_result` → `act_transition`
8. `goaway`, with `commit`s resent after reconnect
   `goaway` と、再接続後の `commit` の再送
9. Close code `4009` (the same playthrough opened in another tab)
   クローズコード `4009`（同じプレイが別のタブで開かれた）
10. The safety card (stepping out of the fiction): `safety_pause` → `safety_resume` → `safety_resumed`
    安全カード（物語の外に出る）：`safety_pause` → `safety_resume` → `safety_resumed`
11. Ending: `ending_started` → `ending_ready` → fetch the ending over REST
    エンディング：`ending_started` → `ending_ready` → REST でエンディングを取得

Plus 5 edge cases:

さらに境界ケース 5 種：

- The character's `transcript` final arrives after `turn_complete`
  登場人物の `transcript` の確定が `turn_complete` より後に届く
- The fallback transcription also fails: `{ final: true, text: null, source: "fallback" }`
  補完の文字起こしも失敗する：`{ final: true, text: null, source: "fallback" }`
- `turn_complete { audio: false }` (the character made no sound)
  `turn_complete { audio: false }`（登場人物が声を出さなかった）
- `degraded` (switched to a text reply)
  `degraded`（テキストの返答に切り替え）
- `limits` (5 minutes of voice left today)
  `limits`（今日の音声は残り 5 分）

There is also a "future message" script: it sends a `type` not in the schema (e.g. `{"type": "future_feature"}`), only so F-0 can test "ignore unknown message types". This step is marked `"unchecked": true` in the script and is the only place that skips the schema self-check.

さらに「未来のメッセージ」の台本が 1 つある：スキーマにない `type`（例：`{"type": "future_feature"}`）を送り、F-0 が「知らないメッセージ種別は無視する」をテストするためだけに使う。このステップは台本で `"unchecked": true` と印を付け、スキーマの自己検査を飛ばす唯一の場所とする。

**5. Self-check**

**5. 自己検査**

Before each message is sent, it is validated with C-1's schema (except the step marked `unchecked`). One that fails is not sent, and an error is printed in the terminal so it is visible immediately during development.

各メッセージを送る前に C-1 のスキーマで検証する（`unchecked` と印を付けたステップを除く）。通らないものは送らず、ターミナルにエラーを出して、開発中にすぐ見えるようにする。

### Out of scope / やらないこと

- Judgment logic, database, real models, any speech processing beyond fake Live.
  判定ロジック、データベース、本物のモデル、偽 Live 以外のあらゆる音声処理。
- Input outside the scripts: ignored, with one line logged in the terminal.
  台本にない入力：無視し、ターミナルに 1 行記録する。

## Interfaces / インターフェース

All messages and responses are constructed with the types generated by `packages/contracts` and pass the schema before being sent.

すべてのメッセージとレスポンスは `packages/contracts` が生成した型で組み立て、送る前にスキーマを通す。

## Acceptance check / 受け入れ確認

- Run all 17 scripts (11 + 5 + "future message") with a Python test client under `--speed 0`: apart from the one marked `unchecked`, every message passes the schema; the order within a turn matches the example in api-contract 3.5.
  Python のテストクライアントで `--speed 0` のもと全 17 本の台本（11 + 5 +「未来のメッセージ」）を最後まで実行する：`unchecked` と印を付けた 1 つを除き、すべてのメッセージがスキーマを通る。1 ターンの順序は api-contract 3.5 の例と一致する。
- State and control endpoints: 409 → delete → start a new playthrough; 401 and 4001 after `expire-session`; after `drop`, the `commit`s resent on reconnect are neither duplicated nor lost.
  状態と制御用エンドポイント：409 → 削除 → 新たにプレイを開始。`expire-session` の後は 401 と 4001。`drop` の後、再接続で再送される `commit` に重複も欠落もない。
- **Coverage check**: of the 30 server message types in 3.3, every one except `event_rejected` (debug mode only) appears in at least one script. If any is missing, it goes red.
  **網羅チェック**：3.3 の 30 種類のサーバーメッセージのうち、`event_rejected`（デバッグモードのみ）を除くすべてが少なくとも 1 つの台本に現れる。欠けていたら赤になる。
- All 16 REST endpoints return responses that pass schema validation.
  16 個の REST エンドポイントがすべてスキーマ検証を通るレスポンスを返す。
- A frontend reviewer connects with F-0's network layer (or any WebSocket client if F-0 is not ready yet) and can get through the "tour" script.
  フロントエンドのレビュアーが F-0 のネットワーク層（F-0 がまだなら任意の WebSocket クライアント）で接続し、「ツアー」の台本を最後まで進められる。
- The mock's contract tests are in CI, finish within 30 seconds under `--speed 0`, all green.
  モックの契約テストを CI に入れ、`--speed 0` で 30 秒以内に終わり、すべてグリーンになる。

## Forbidden / 禁止事項

- No deploying, no touching secrets, no calling real models, no spending money (dev-plan 2.2).
  デプロイしない、秘密鍵に触れない、本物のモデルを呼ばない、お金を使わない（dev-plan 2.2）。
- Scripts and fixed data contain only Japanese we wrote ourselves or that already exists in the design docs; never anything a real person said, real names or personal information.
  台本と固定データには、自分たちで書いた日本語か設計文書に既にある日本語だけを入れる。実在の人が言ったこと、実名、個人情報は入れない。
- Do not add mock-only fields to the contracts; mock control goes only through `/__mock/*` (`scenario`, `expire-session`, `drop`).
  契約にモック専用のフィールドを加えない。モックの制御は `/__mock/*`（`scenario`、`expire-session`、`drop`）だけを通す。

## Review / レビュー

Frontend: whether the scripts cover the situations the frontend has to handle, and whether the timing feels real. Data: the events, memories, promises and endings in the scripts conform to the contracts.

フロントエンド：台本がフロントエンドの扱うべき状況を網羅しているか、タイミングが本物らしいか。データ：台本の中のイベント、記憶、約束、エンディングが契約に合っている。
