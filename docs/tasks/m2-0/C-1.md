**2. How schemas are written**

**2. スキーマの書き方**

- Each WebSocket message type is one `$defs` entry, with `type` as a `const`; the whole is a `oneOf` discriminated by `type`.
  WebSocket のメッセージ種別ごとに `$defs` のエントリを 1 つ作り、`type` は `const` にする。全体は `type` で区別する `oneOf`。
- Messages and responses we send are written strictly, with optional fields marked optional as in the doc. "The frontend ignores unknown fields" is runtime tolerance on the frontend, not a loosening of the schema: to add a field later, change the schema first.
  こちらから送るメッセージとレスポンスは厳密に書き、任意のフィールドは文書どおり任意と記す。「フロントエンドは知らないフィールドを無視する」はフロントエンドの実行時の寛容さであって、スキーマを緩めることではない：今後フィールドを足すときはまずスキーマを変える。
- Closing objects is done the same way as C-2: **plain objects use `additionalProperties: false`**. json-schema-to-typescript does not understand `unevaluatedProperties` and allows extra fields by default, so every interface would get an extra `[k: string]: unknown`; datamodel-code-generator also forbids extra fields only when it sees `additionalProperties: false` (frontend's review of C-2). `unevaluatedProperties: false` is used only on the outer layer of something composed with `allOf`; API schemas avoid `allOf` as much as possible.
  閉じ方は C-2 と同じ：**普通のオブジェクトには `additionalProperties: false` を書く**。json-schema-to-typescript は `unevaluatedProperties` を理解せず、既定では余分なフィールドを許すので、すべてのインターフェースに `[k: string]: unknown` が付いてしまう。datamodel-code-generator も `additionalProperties: false` を見たときだけ余分なフィールドを禁止する（フロントエンドによる C-2 のレビュー）。`unevaluatedProperties: false` は `allOf` で組み立てたものの外側にだけ使う。インターフェースのスキーマではできるだけ `allOf` を使わない。
- Referencing data contract types:
  データ契約の型の参照：
  - Where the shape is the same as the data type, `$ref` the whole thing; for substructures not in `$defs`, use a JSON pointer (e.g. `data/ending.schema.json#/$defs/Ending/properties/characters`) rather than adding extra `$defs` for them in `data/`.
    形がデータ型と同じものは、まるごと `$ref` で参照する。`$defs` にない下位構造は JSON ポインタを使い（例：`data/ending.schema.json#/$defs/Ending/properties/characters`）、そのために `data/` に `$defs` を追加しない。
  - Where the API adds or removes fields relative to a data type (api-contract 2.8: `card` = `Ending.card` plus `fallbackImageUrl`; the ending's `world` and `you` have a changed shape), write the API's own closed object, with each field `$ref`-ing the data-side field via a JSON pointer (e.g. `…/properties/card/properties/title`), so constraints such as character limits are not copied a second time. Do not use `allOf` to extend C-2's types: C-2's objects are already closed, so the extended fields would be rejected.
    インターフェースがデータ型にフィールドを足したり減らしたりしたもの（api-contract 2.8：`card` = `Ending.card` に `fallbackImageUrl` を追加。エンディングの `world`、`you` は形を変えている）は、インターフェース独自の閉じたオブジェクトとして書き、各フィールドは JSON ポインタでデータ側のフィールドに `$ref` する（例：`…/properties/card/properties/title`）。文字数などの制約を二重に書き写さない。`allOf` で C-2 の型を拡張しない：C-2 のオブジェクトは既に閉じているので、拡張したフィールドは拒否される。
  - Tests list the field differences between each such object and its data type (e.g. `card` only adds `fallbackImageUrl`), and go red if they differ from what api-contract says. When the data contracts later add optional fields, whether to expose them to the frontend is decided by api-contract; they do not flow out automatically.
    テストでこうしたオブジェクトとデータ型のフィールドの差を列挙し（例：`card` は `fallbackImageUrl` が増えるだけ）、api-contract の記述と違えば赤にする。データ契約が今後任意のフィールドを足しても、それをフロントエンドに渡すかどうかは api-contract が決め、自動的に外に出ることはない。
- Runtime IDs use the patterns C-2 defines in `data/common.schema.json` (prefix plus ULID).
  実行時の ID は C-2 が `data/common.schema.json` で定めたパターン（接頭辞 + ULID）を使う。
- Japanese text fields constrain only type and length; where the doc gives an upper limit, write it (e.g. `text` ≤ 200 characters).
  日本語のテキストフィールドは型と長さだけを制約する。文書に上限があるものはそのまま書く（例：`text` ≤ 200 字）。
- Things that exist only outside production (`hello.debug`, `fakeVoice`, `event_rejected`, `POST /v1/test/playthroughs/{id}/advance`) still get schemas, marked "non-production" in `description`.
  本番以外にだけあるもの（`hello.debug`、`fakeVoice`、`event_rejected`、`POST /v1/test/playthroughs/{id}/advance`）もスキーマを書き、`description` に「非本番」と記す。
- `npc_line` (P1) does not go into v1.0; nor does the sharing endpoint (2.10, P1).
  `npc_line`（P1）は v1.0 に入れない。共有のエンドポイント（2.10、P1）も入れない。

**3. Generation** (API and data schemas are generated together)

**3. 生成**（インターフェースとデータのスキーマをまとめて生成する）

- One command (`uv run contracts-gen`, or the task entry point R-0 decides).
  1 つのコマンド（`uv run contracts-gen`、または R-0 が決めたタスクの入口）。
- TypeScript: json-schema-to-typescript (the tool can be changed during frontend review). WebSocket messages generate a union type discriminated by `type`.
  TypeScript：json-schema-to-typescript（フロントエンドのレビューでツールを変えてもよい）。WebSocket のメッセージは `type` で区別する共用体型を生成する。
- Python: datamodel-code-generator generates pydantic v2 models, which the services use at runtime to construct and parse. WebSocket messages must parse to the right class by `type` in one pass; if the tool cannot do this, a very thin hand-written `TypeAdapter` wrapper outside the generated directory is allowed. The tests also use the `jsonschema` library to validate directly against the raw schemas, so that nobody misses a discrepancy between the generator and the schemas.
  Python：datamodel-code-generator で pydantic v2 のモデルを生成し、サービスは実行時にそれで組み立てと解析を行う。WebSocket のメッセージは `type` によって一度で正しいクラスに解析できなければならない。ツールでできない場合は、生成ディレクトリの外にごく薄い `TypeAdapter` のラッパーを手で書いてよい。テストでは別に `jsonschema` ライブラリで元のスキーマに直接検証し、生成器とスキーマの食い違いを見落とさないようにする。
- The generated output is committed to the repo; CI regenerates and runs `git diff --exit-code`.
  生成結果はリポジトリにコミットする。CI は再生成してから `git diff --exit-code` を実行する。

**5. 契約テスト**（CI に入れ、ネットワークは使わない）

  すべてのスキーマが 2020-12 のメタスキーマに対して妥当で、すべての `$ref`（`data/` を指すものを含む）が解決できる。

- **Coverage check**: read all `type` names from the tables in 3.2 and 3.3 of `docs/backend/api-contract.md` and match them one to one against the `const`s in the schemas; one missing or one extra goes red. That way the doc and the schemas cannot quietly diverge.
  **網羅チェック**：`docs/backend/api-contract.md` の 3.2、3.3 の表からすべての `type` 名を読み取り、スキーマの `const` と 1 対 1 で照合する。1 つ足りなくても 1 つ多くても赤。こうして文書とスキーマが黙って食い違うことを防ぐ。
- Valid examples, parsed by pydantic and exported again (`by_alias`, dropping None), are identical to the original files.
