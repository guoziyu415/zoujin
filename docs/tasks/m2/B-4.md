## 目标

做完以后：

1. **作废**：玩家按「取り消す」「言い直す」，或 12 秒没回应，那一轮就不算数。
   - 世界不变，不花时间，原话当场清空。
   - 人物的语音会话重建，新会话里没有这一轮：人物是真的没听到，不只是被要求忽略。
   - 窗口从按下到这一轮 `turn_settled` 之前。叙事者最早在 `turn_complete` 后 3 秒提交，所以人物回答完至少有 3 秒。
2. **识别改正**（S-025）：玩家点自己的字幕改字，旧的一轮作废，改好的句子作为新的一轮，等会话重建好再送进去。
3. **幕末用声音说的打算也能作废**（PM 10-10 23:49 定的，前端在 #61 评审里提的）：作废的那一轮不算一次试次。
4. **意图确认**（S-040）：叙事者提出会改变主线又撤不回的事，但玩家的意思不确定时，先存成草稿，由人物反问。
   - 玩家答「本気だ」：按那时的状态重新检查再提交。
   - 答「いや、違う」或 30 秒没答：丢掉，不花时间。
   - 一局最多问 3 次。
   - B-2 里这种候选是直接丢掉的（`candidates_confirm_dropped`），本卡以后才真的能写进世界。R1 里玩家想阻止的举动要靠它。

## 范围

### 做

**1. 作废一轮**（api-contract 3.6；网关 `gateway/ws.py`）

收到 `turn_retract { turnId }`，按这一轮到了哪一步处理：

| 这一轮在哪 | 做什么 | 回什么 |
|---|---|---|
| 还在连接内存里：玩家还在说，或人物还没说完、定稿还没到（没交给叙事者） | 停止转发这一轮的下行音频（取消转发任务，不补 `interrupted` 和说到一半的定稿）；不交给叙事者；`turns` 写一行 `retracted`，不写原话 | `turn_retract_result { retracted }` → `turn_settled { outcome: "retracted", minutes: 0, eventIds: [] }` |
| 已经交给叙事者、还没提交（`turns.status` 是 `pending` 或 `leased`） | 同一个事务里：`status` 改成 `retracted`；这一轮的原话 `text` 清空、记 `deleted_at`（行留着） | 同上 |
| 已经提交（`done`），或 `failed`、`lost`、`retracted` | 什么都不改 | `turn_retract_result { too_late }` |
| 不认识的 `turnId`、服务端发起的一轮（落地、确认的反问） | 什么都不改 | `turn_retract_result { too_late }` |

- **作废和提交不会同时成功**：作废用 `UPDATE … WHERE status IN ('pending', 'leased')`；叙事者提交时已经 `FOR UPDATE` 锁住这一轮、只认 `leased`（B-0 起就这样）。谁先拿到行锁谁算数。叙事者在提交时发现这一轮被作废了，丢掉结果，不推任何消息（`turn_settled` 已经由网关推过）。
- **会话重建**（backend-design 3.2）：作废成功以后关掉这个人物的会话，开一条新的。
  - 新会话带人设、局势说明和网关内存里「最近的对话」。最近的对话是这条连接上和这个人物的最近几轮文字，跳过作废的轮次。
  - 推 `session_preparing { reason: "rebuild" }`，就绪后推 `session_ready`。
  - 重建期间玩家可以按下说话：新的一轮等会话就绪再送进去（前端最多缓存 2 秒音频，3.6 第 2 条）。
  - B-4 只有假 Live：接口上 `live.open(character, recent=…)` 收最近的对话，假 Live 记下收到了什么，测试用它查作废的那一轮不在里面。真 Live 的重建跟真 Live 的卡一起做。
- **提交窗口**：对话一轮的 `turns` 多记一个 `commit_after` = 这一轮 `turn_complete` 的时刻 + 3 秒（测试按 `ZJ_SPEED` 缩短）。
  - 叙事者判完、提交之前，没到 `commit_after` 就等到那时，等的时候不占事务。
  - 真模型的判定本来就要 2〜5 秒，多数时候不用多等。
  - 文字的一轮也一样。情境动作、幕末选择、`act_propose` 没有窗口（玩家点了按钮、自己打了字，不能作废）。
- **作废的一轮不进「最近的对话」，也不进 `lastTurn` 的文字**：`welcome.lastTurn` 是作废的那一轮时，`status: "settled"`，`playerText`、`characterText` 都是 `null`（第 4 节「原话已清空的轮次不给文字」）。
- **计数**：`playthrough_metrics.turns_retracted` 每次作废成功加 1（太晚的不算）。
- **前后两轮**：被作废的那一轮是后一轮的 `prev`（B-0 让叙事者按玩家说的顺序判）时，照样放行后一轮。

**2. 识别改正**（3.6 第 6 条）

- 前端发 `turn_retract { turnId: 旧 }`，紧接着 `text { turnId: 新, via: "correction", replaces: 旧, text }`。
- 旧的一轮作废成功：新的一轮等这个人物的会话重建好再送进去，前端照常显示 `thinking`。
- 旧的一轮已经 `too_late`：新的一轮当作普通的一轮，之前那句的后果不撤回。
- 服务端不因为 `replaces` 自己去作废旧的一轮：只认 `turn_retract`。`replaces` 只用来等重建。

**3. 幕末用声音说的打算可以作废**（3.11）

- 还在说（`activity_end` 之前）：丢掉音频，不推转写的定稿，不写任务。
- 松开以后、叙事者提交之前：和对话一样，`turns` 改成 `retracted`、原话清空。
- 提交窗口：叙事者最早在转写定稿推出后 3 秒提交这一轮打算（同第 1 条的 `commit_after`），玩家看到自己的话识别错了，来得及「言い直す」。
- 作废成功：
  - 回 `turn_retract_result { retracted }`；
  - **不推 `act_plan_result`，也不推 `turn_settled`**（打算的一轮本来就没有 `turn_settled`）；
  - **不算一次试次**（`plan_tries` 不变），`freeform.triesLeft` 不变；
  - 没有人物在听，不重建会话。
- 已经判完（成行转场了，或者不成行用掉了一次）：`too_late`。
- `act_propose`（打出来的打算）不能作废，它没有 `turnId`。

**4. 意图确认**（3.9；叙事者 `narrator/`、网关）

触发条件（backend-design 2.4 第 6 步，B-2 已经在流水线里标出来了）：

- 提取标了 `needsConfirm`，并且这个候选不可逆：让节拍 `prevented` / `altered`，或改 `var.hostage.who`、`var.hostage.fate`、`var.player.custody`（`pipeline.py` 的 `IRREVERSIBLE_*`）。
- 它照常过第 3〜5 步。不过的照常拒绝，不问。

存成草稿：

- 过了检查的这个候选不写进事件日志。存成草稿（新表 `drafts`，第 7 条），这一轮别的候选和 10 分钟照常提交。
- 这一轮照常推 `commit`、`turn_settled`。**原来那一轮先结掉，再问**：
  - 前端的「言い直す」窗口照常到这一轮的 `turn_settled` 为止，不因为问话拖长 30 秒；
  - 玩家用声音回答的那一轮，也不会排在一个还没结的轮次后面。
- 草稿不花时间：这一轮的 10 分钟已经算过了。答「是」以后提交的那条事件 `dt: 0`，带 `confirmed: true`（契约 Event）。

同一时间、同一局：

- **最多一个**没答的草稿。草稿还开着时又提出一个，按 B-2 的老办法丢掉（`candidates_confirm_dropped` 加 1）。
- **一局最多问 3 次**（S-040「一局 0〜3 次」）。第 4 次起同样丢掉、计数。理由：这类事撤不回，不问就提交太冒险；问多了 UX 17.1 的「いや、違う」比例会超标。
- **收幕、进结局时不留草稿**（数据评审）。提出候选的那一轮自己的 10 分钟就可能跨过幕的终点；不这样，上一幕的事会在幕末选择的画面上被问，答了「是」还落在下一幕的时刻和地点上。所以：
  - 一次提交里出了 `act_ended`（或开始结局）时，这一轮新提出的要确认的候选不存草稿，按丢掉计（`candidates_confirm_dropped`）；
  - 已经开着的草稿，在推 `act_ended` 之前按超时关掉（写 `optionId: null`、`by: "timeout"` 的任务，推 `confirm_closed`），计进 `confirms_timeout`；
  - 幕末待选（`act_end` 不空）期间来的 `confirm_answer`，照「不是开着的草稿」忽略。

人物反问（3.9 第 2 条）：

- 提取的输出给要确认的候选多加两项：
  - `asked`：人物这一轮的回答是不是已经在反问；
  - `question`：人物反问的一句（≤ 30 字，人物自己的口吻）。
- `question` 照第 3 步 R6 的规则部分查（电话、邮箱、地址；和玩家原话连续 8 字相同）。不过就用固定的「……本気で言っているのか。」。
- `asked: true`：`turn_settled` 之后直接推 `confirm`，`prompt` 用 `question`。
- `asked: false`：
  - 服务端起一轮 `turn_started { reason: "confirm" }`（`turnSeq` 从 `0x80000001` 起，同落地）；
  - 人物说出 `question`（假 Live：`speak_first` 换成说给定的这一句）；
  - 推 `turn_complete` 和转写的定稿，再推 `confirm`。
  - 这一轮和落地那句一样：只存人物的原话，不交给叙事者，没有 `turn_settled`，不能作废。人物的原话**挂在原来那一轮下面**（`utterances.turn_id = drafts.turn_id`），记憶帳删掉那一轮时一起清掉（数据评审）。
  - 玩家已经不在和这个人物说话（`unfocus` 了或换了人）时，不起这一轮，直接推 `confirm`，`prompt` 照样是那一句。
- `confirm` 的形状照 3.9 第 3 条：
  - `options` 固定是 `yes`「本気だ」、`no`「いや、違う」；
  - `timeoutSec: 30`，从推出 `confirm` 起算。服务端在 `drafts.expires_at` 记下到期的时刻。

回答（3.9 第 4、5 条）：三种回答都写一行 `kind: "confirm"` 的任务，带 `draftId`、`optionId`（`yes` / `no` / `null`）和 `by`。叙事者按局排队处理，和别的任务一样串行。

- **按钮**：`confirm_answer { draftId, optionId }`。`draftId` 不是这一局开着的草稿（已经超时、已经答过）时忽略，只记日志。
- **声音或文字**：草稿开着时来的一轮照常是对话（10 分钟）。
  - 提取的输入多一个 `<confirm>`：反问的那句和草稿的摘要。
  - 输出多一个 `confirmAnswer`：`yes` / `no` / `null`（这句话不是在回答）。
  - 不是 `null` 时，这一轮的提交里同时写那一行 `confirm` 任务（`by: "voice"`）。
- **超时**：网关推 `confirm` 时开一个 30 秒的计时，到点写 `optionId: null`、`by: "timeout"` 的任务。
  - 断线时计时不在了：下一次 `hello` 时，过期的草稿先关掉（同样写超时的任务），`pending.confirm` 给 `null`；没过期的给 `remainingSec`。
  - 叙事者处理这一局别的任务之前，也先把过期的草稿关掉。

叙事者处理 `confirm` 任务：

- `yes`：草稿按当前状态从第 3 步重新检查（第 3〜5 步，同 B-2）。
  - 过了：提交，事件带 `confirmed: true`。
  - 没过（这期间状态变了）：写一条 rejected 的事件，也带 `confirmed: true`。这样一局的确认结果只看事件日志就能数：`confirmed` 且通过 = 提交了，`confirmed` 且没过 = 重查没过。这次 `commit` 的 `narration` 给一句叙事，说这件事没成（叙事者的 `narrate`，B-3；超时或不合格用固定的一句）。
  - 这两种事件的 `turnId` 都是**原来那一轮**（`drafts.turn_id`），不是 `confirm` 任务那一行：记憶帳删除按 `fromEvents → Event.turnId → Utterance.turnId` 清整轮原话（契约第 4 节），挂错了，玩家删掉记忆以后当初那句话还留着（数据评审）。幂等键照常用 `confirm` 任务的，重放不重复写。
  - 其余字段：`t` 是叙事者处理 `confirm` 任务时的钟点，`dt: 0`，`place` 是草稿里候选原来的地点（玩家这期间可能走开了）。
- `no`、`null`：丢掉草稿，不写事件，不花时间。
- 推的顺序：有提交时先推那次 `commit`，再推 `confirm_closed { draftId, optionId, by }`。用声音答的，那一轮自己的 `commit` → `turn_settled` 在前。
- 草稿关掉以后删掉那一行（摘要不留）。结果记进 `playthrough_metrics`（第 7 条）。
- 草稿开着时，玩家在記憶帳删掉了原来那一轮（那张卡做删除）：草稿按「不是」丢掉，不写事件，不然答「是」会把一句已经删掉的话的结果写进世界。本卡在 `drafts.turn_id` 上留好查的路。

**5. 评测入口**（api-contract 第 7 节）

运行器的协议在 `evals/src/zoujin_evals/api.py`，归数据。下面两处要数据同意，在这张卡的评审里定：

- **作废**：评测的 `say` 是同步的，返回时已经提交了，`retract(step)` 永远太晚。改法：
  - `say(to, text, hold=False)` 加一个可选参数。`hold=True` 时只写这一轮、拿人物的回答，返回 `reply`，`events: []`，`clockMinutes: 0`，`held: true`；这时窗口还开着。
  - 下一次调用（任何步骤或查询）开始时，先让叙事者判完、提交这一轮。这一轮的事件算在那一次调用的 `events` 里，事件上带第 n 步的 `turnId`。
  - 下一次调用是 `retract(n)` 就作废：返回 `retract: "retracted"`、`events: []`、`clockMinutes: 0`。已经提交的返回 `retract: "too_late"`。
  - 运行器在用例的下一步是 `{"retract": {"step": n}}` 时，给第 n 步传 `hold=True`。AI 玩家（B-5）想不想言い直す，由运行器决定传不传。
  - `utterance_cleared(step)`：那一步那一轮玩家和人物的原话都清空了。
  - 不传 `hold` 的 `say` 照旧，现有的用例不受影响。
- **确认**：
  - 这一步留下了草稿时，`StepResult` 多一项 `confirm: { draftId, character, prompt }`，草稿那条不在 `events` 里。
  - 新的步骤 `confirm(answer)`，`answer` 是 `"yes"` / `"no"` / `null`（`null` = 没答、超时）。用例里写 `{"confirm": {"answer": "yes"}}`。
  - 草稿在评测里最多等一步：
    - 下一步是 `confirm`，按它答；
    - 是 `say`，由叙事者判这句话是不是在回答（同第 4 条的声音回答）；
    - 是别的步骤，或者那句 `say` 不是在回答，就按超时关掉。
- 运行器那边（用例下一步是 `retract` 时传 `hold`、`confirm` 步骤、新的检查）等本卡的代码进 main 以后由数据开 PR（数据评审同意了上面的做法）。
- 评测里用的提交窗口是 0（不等 3 秒）；`hold` 就是评测里的窗口。

**6. 假模型和 fixture**

- `fixtures/fake-text/b4-*.json` 按条件覆盖，例：
  - 玩家说「人質」时出一个改 `var.hostage.who`、`needsConfirm: true` 的候选；

**7. 存储**（迁移 0004）

- 新表 `drafts`，随整局删除：
  - `draft_id`（`draft_…`）、`playthrough_id`、`turn_id`、`character`；
  - `candidate`（jsonb：候选的 summary、effects、actor 等，不放原话）；
  - `prompt`、`asked`、`created_at`、`expires_at`（推出 `confirm` 时写）。
  - 关掉就删行。data-design 第 5 节由数据加这张表。
  - 进删除清单：`tables.py` 的 `PER_PLAYTHROUGH` 加 `drafts`（评测的 `db_absent` 查它）。
- `turns`：
  - 加 `commit_after`（timestamptz，可空）；
  - `kind` 多 `confirm`；
  - `request` 放 `draftId`、`optionId`、`by`。
- `playthrough_metrics` 加 `confirms_asked`、`confirms_yes`、`confirms_no`、`confirms_timeout`、`confirms_rejected`（答了「是」、重查没过）。data-design 第 3 节由数据跟着改。关系：
  - `confirms_asked` = 推出的 `confirm` 次数 = `yes + no + timeout`（局终了时最多还开着 1 个）；
  - `confirms_rejected` 是 `confirms_yes` 的一部分；
  - UX 17.1 的「いや、違う」比例服务端也能算：`(no + timeout) / asked`。

## 验收

不联网（pytest 拦截 socket）。`uv run pytest services/backend` 和连库的 `-m db` 全过，其中要有下面这些。WebSocket 上的用切片世界模型。

1. **作废**：
   - 人物还没开口时作废：
     - 回 `retracted` → `turn_settled { retracted, minutes: 0 }`；
     - 没有 `commit`，时钟不动；
     - `turns` 有一行 `retracted`，没有原话；
     - 之后不再有这一轮的音频和字幕。
   - 人物说完、叙事者还没提交（`commit_after` 没到）时作废：
     - 同上；
     - 这一轮的原话 `text` 是空的、有 `deleted_at`；
     - 叙事者判完也不提交，不推第二个 `turn_settled`。
   - 提交以后再作废：`too_late`，世界不变。
   - 叙事者提交和作废同时来（用 `before_commit` 的钩子卡在提交前）：只有一个成功。两种结果都查。
   - 作废以后：
     - 这个人物的会话重建了，推了 `session_preparing { reason: "rebuild" }` 和 `session_ready`；
     - 新会话的「最近的对话」里没有作废的那一轮，有它之前的那一轮。
   - `welcome.lastTurn` 是作废的那一轮：`settled`，文字都是 `null`。
   - `playthrough_metrics.turns_retracted` 是作废成功的次数。
   - 提交窗口：`turn_complete` 之后 3 秒（按 `ZJ_SPEED` 缩短）之内没有 `commit`。
2. **识别改正**：
   - `turn_retract` + `text { via: "correction", replaces }`：旧的一轮作废；新的一轮在 `session_ready` 之后才送进会话，照常判、提交。
   - 旧的一轮太晚时：新的一轮照常判，旧的一轮的事件还在。
3. **幕末的打算**：
   - 用声音说、松开以后马上作废：
     - 回 `retracted`，没有 `act_plan_result`；
     - `plan_tries` 不变；
     - `turns` 是 `retracted`、原话清空；
     - 再说一次，`triesLeft` 还是 2。
   - 还在说时作废：没有转写的定稿，不写任务。
   - 判完以后作废：`too_late`，结果照旧（成行的照样转场）。
4. **意图确认**（假模型的提取用 b4 的 fixture）：
   - 要确认的候选：
     - 不进事件日志，这一轮其他的照常提交、10 分钟；
     - `turn_settled` 在前，`confirm` 在后，`options` 和 `timeoutSec: 30` 照 3.9。
   - `asked: false`：`turn_settled` → `turn_started { reason: "confirm" }` → `turn_complete` → 人物的定稿是 `question` → `confirm`。反问那一轮没有 `turn_settled`，不交给叙事者。
   - `asked: true`：`turn_settled` 之后直接 `confirm`，不起反问的一轮。
   - 按钮答「是」：
     - 事件提交，带 `confirmed: true`，`dt: 0`，`turnId` 是原来那一轮，`place` 是候选原来的地点；
     - `commit` → `confirm_closed { yes, by: "button" }`。
   - 反问那一轮（`asked: false`）人物的原话存在原来那一轮下面。
   - 答「是」、但期间状态变了（测试里在中间提交一条让前提不成立的事件）：写 rejected 的事件（也带 `confirmed: true`、`turnId` 是原来那一轮），`commit.narration` 有一句，`confirm_closed` 照推。
   - 收幕：
     - 草稿开着时这一局收幕：推 `act_ended` 之前先 `confirm_closed { optionId: null, by: "timeout" }`，计进 `confirms_timeout`；
     - 提出候选的那一轮自己收了幕：不存草稿，`candidates_confirm_dropped` 加 1，不推 `confirm`；
     - 幕末待选时的 `confirm_answer`：忽略。
   - 按钮答「不是」：没有事件，时钟不动，`confirm_closed { no, by: "button" }`。
   - 用声音答：
     - 那一轮照常 10 分钟；
     - 提取判出 `confirmAnswer: "yes"` 以后，顺序是那一轮的 `commit` → `turn_settled` → 草稿的 `commit` → `confirm_closed { yes, by: "voice" }`。
   - 30 秒超时（按 `ZJ_SPEED` 缩短）：`confirm_closed { optionId: null, by: "timeout" }`，没有事件。
   - 断线重连：
     - 没过期：`welcome.pending.confirm` 带 `remainingSec`；
     - 过期了：`pending.confirm` 是 `null`，草稿已经关掉（按超时计）。
   - 草稿开着时又来一个：丢掉，`candidates_confirm_dropped` 加 1。第 4 次：同样丢掉。
   - 已经关掉的 `draftId` 再答：忽略，不推东西。
   - `question` 里有电话号码，或照抄玩家原话 8 字以上 → `prompt` 是「……本気で言っているのか。」。
   - `playthrough_metrics` 的 `confirms_*` 对得上。
5. **评测入口**：
   - `say(hold=True)` → `retract(n)`：没有事件，`utterance_cleared(n)` 为真。
   - `say(hold=True)` → 下一步 `say`：前一轮照常提交，事件算在第二步里。
   - 草稿：`StepResult.confirm` 有值；`confirm("yes")` 提交，`confirm("no")` 不提交；下一步是别的，按超时关掉。
   - 不传 `hold` 的 E-0 用例结果不变（快照只有 traceId 变）。
6. **不记原话**：
   - 作废、改正、确认的日志和 Span 里找不到玩家的标记字符串，也没有 `question` 的文字；
   - 作废以后 `utterances` 里这一轮的 `text` 是空的。
7. **迁移**：0004 升上去、降回 0003 都能跑；删除整局以后 `drafts` 里没有这一局的行（`PER_PLAYTHROUGH` 里有 `drafts`）。
