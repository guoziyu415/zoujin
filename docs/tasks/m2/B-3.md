## 目标

做完以后：

1. 玩家的动作先判后演：快照给出此刻能做的情境动作和可调查物；`action` 消息和 `eval_api.act` 由叙事者判定，按 api-contract 3.8 的顺序回 `commit` 和 `action_result`。
2. 幕末能走完：
   - 收幕时推 `act_ended`，去处按 `roles`、`requires` 过滤，带副题、时刻和同行的人。
   - 选去处（`act_choose`）和说出打算（`act_propose`，或用声音）按契约 2.8.1 写事件、跳转、落地。
   - 不在选项里的去处回 `invalid_choice`。
3. 切片能从第一幕走到第四幕（S-077 ④⑤⑥）：
   - 两个给定去处和成行的打算，都落在三日目 17:30 的刑场，玩家和老爺站在各自的位置点。
   - 落地先显示一行地の文；去老爺家的那条，老爺先开口。
4. 切片的固定演出按契约 2.11 在对的时机下发。城门那一场让玩家知道约定（S-077 ⑪）；期限一行和梅洛斯的菱形，玩家知道约定以后才出（⑫）。

## 范围

### 做

**1. 快照和 patch**（`projection.py`）

- **`actions`**：世界模型 `affordances` 里此刻成立的那些。条件：
  - `place` 是玩家所在地；有 `act` 的，等于当前幕；
  - `roles` 含玩家的身份；`when` 成立；
  - 有 `target` 的，对象人物在这个地点，而且不是 `absent`；
  - `give` 的物品玩家拿得到（R7 的同一个判法）。
  - 每条的字段：
    - `actionId` = `act_` 加上 Affordance ID 去掉 `aff.` 的部分（例 `act_walk-old-man-home`），前端原样回传。
    - `estimatedMinutes` = `minutes`。
    - 带 `melos` 的：`melosMinutes`、`melosInTime` 用 `arrival_delta(本局, effects, 此刻)` 算（2.3）。不带的，这两个和 `melos` 都是 `null`。
    - `enabled: true`：列出来的都是有希望成立的，结果以判定为准。
- **`interactables`**：
  - `examine`：世界模型 `objects` 里地点在当前场景的那些。`id`、`label`、`spot` 照它，`estimatedMinutes: 0`，`enabled` = 它的地点进得去。
  - `go`（布局的 `exits`）：一律 `enabled: true`，走不走得了由判定说。S-077 ③：城门由警吏拦下，不用看不见的墙。现在的快照按身份能不能进那个地点给 `enabled`，这里改掉。
- **`player.spot`**：服务端按局记（契约 3.1：玩家的位置点不进 WorldState）。
  - 幕切换按 `ActExit.spot` 或 `Act.plan.spot`；做完情境动作按 `Affordance.playerSpot`。
  - `move` 到别的地点以后，或者记下的点不属于玩家现在的地点时，用这个地点的起点（`startSpots`）。
- **`deadline.shown`、`forecast`**：条件从「beat.05 发生了」改成 `knows(player, fact.promise)`（S-077 ⑫，api-contract 2.3）。
  - 下面四条路，哪条先到都算：城门那一场的 `learns`；第一幕幕末 act-transition 事件里的 `learn`；人物告诉；在场看见立约。
  - 切片世界模型的三个去处和 `Act.plan` 都写了这条 `learn`；约定没成立的局 `knows()` 为假，照旧不出。
- **`pending.actEnd`**：收了幕、还没选定时给，和 `act_ended` 同形，快照和 `welcome` 都带（第 4 节）。
- **`welcome.pending.arrival`**：落地带 `opener`、还没收到 `act_landed` 时给。

**2. 动作**（`action`，3.8；`eval_api.act`）

- 网关收到 `action` 就写一行任务（`turns.kind = "action"`，记下 `clientMsgId`、`kind`、`target`、`params`、`actionId`），然后叫叙事者。动作和对话同一个队列，按局串行。
- 叙事者按 `kind` 判：
  - **`move`**（同场景跨地点）：
    - 目标地点进得去 → 写一条 `move` 事件（`actor: "player"`，`set var.player.location`，`dt: 0`，`check` passed，不过模型）。
    - 进不去 → `refused`，不写事件、没有 `commit`（3.8），回一行 narration。
  - **`examine`**：对象是 `objects` 里、在玩家这个地点的可调查物。
    - 有固定演出就演；没有由叙事者说一行（下面的 `narrate`）。
    - 0 分，不写事件。
  - **`go`**：
    - `target` 是出口的 interactable ID（`way.*`），也认地点 ID（评测用例写 `place.castle`），统一换成布局 `exits[].place`。
    - 候选 = 玩家移动到那个地点（`move`，`dt` = 路程），过第 3〜5 步。
    - 切片里旅人进不了王城和城外的路 → R7 否决，按契约第 3 节写 rejected 事件（E4-107），回 `refused`。
    - 判过了：写 `move` 事件，回 `done`。换场景的过场和新场景的快照留到 M3（见「不做」）。
  - **有对应情境动作的**：前端给的 `actionId`；或者评测只给 `kind` + `target` 时，按 kind、target、地点、幕、身份、`when` 找到唯一的一条。
    - 候选 = 它的效果模板：`type: "action"`，`origin: "action"`，`dt` = `minutes`，`promise` 由叙事者分配 ID。
    - 过第 3〜5 步，改写、降级、拒绝照 B-2。
    - `aid` 记在这一步的结果里；记忆和关系是记忆那张卡。
    - 做成了，玩家站到 `playerSpot`（`commit.patch.player.spot`，3.8）。
  - **没有对应情境动作的**（例 `block char.guards`，或 `give` 一个不在 `items` 里的东西）：
    - 走 B-2 的提取。提取的输入多一个 `<action>` 数据字段，写 kind、target、物品。
    - 提取出 0〜3 个候选，再过第 3〜5 步。
    - `give` 的物品不在 `items` 里、或不在玩家手上 → R7（评测 E4-005、E4-010）。
  - **`wait`**：跳到这个地点的下一个节拍（排定时刻在此刻之后、地点是玩家所在地、在本幕收幕之前），结算到它刚发生之后。没有这样的节拍 → `refused`。
- **`status`**：
  - 候选全部提交（passed / rewritten）→ `done`；
  - 有降级的、或部分被否决 → `partial`；
  - 全被否决、或没有候选 → `refused`。
- **`minutes`**：
  - `done` / `partial`：事件 `dt` 的合计（情境动作照模板；没有模板的用 `pacing.situationalMinMinutes`）；
  - `refused`：0。
- **`narration`**：一行地の文。
  - 用新的提示类型 `narrate`（flash，思考 LOW）写：按动作、判定结果和失败的规则。
  - 有固定演出接管时不调用、不带 `narration`（3.14）。
  - 假模型的默认：每种 `status` 一句固定的话。
- **顺序**（3.8、3.14）：`commit`（写了事件时）→ 这次提交里节拍时机的 `set_piece` → `action_result` → 动作时机的 `set_piece`。

**3. 固定演出**（契约 2.11，api-contract 3.14）

- **时机**：
  - 动作：判完以后问 `pick_set_piece(world, state, {act: kind, target, refused}, played)`。`target` 照 2.11：人物、地点；`go` 是出口通往的地点；`examine` 是 `obj.*`。`refused` = `status` 是 `refused`。
  - 节拍：任何一次提交里（对话、动作、快进、幕切换的结算），每个节拍的系统事件应用以后问 `{beat}`。玩家不在节拍的地点时，W-1 返回 `None`。
- **演了以后**：
  - 这一局演过的 ID 记在局上（`played`）。它不是事件，不进 WorldState，和这次提交同一个事务。
  - 有 `learns` 的，写成同一次提交里紧跟着的一条 `type: "learn"` 事件：
    - `actor` = `lines` 里第一个说话的人物；只有地の文时是 `"system"`。
    - `effects` = `learns` 对应的 `learn`；`dt: 0`；`check` passed，`checker: "set-piece"`。
    - `summary` 是中性日语（例「警吏が、メロスの約束を口にした」）。
    - 动作时机的 `origin: "action"`；节拍时机的不写 `origin`（契约 1.6：`schedule` 只给节拍和期限）。
  - 2.11 留给后端定的「learn 写在动作的事件里还是另写一条」：取另写一条。原因是被拒的动作没有事件可挂（城门那一场就是被拒的 `go`）。
- **`set_piece {pieceId, lines}`**：`lines` 原样下发。不占 `seq`；断线时没收到的不补发。
- 预录句的音频不在本卡（见「不做」），前端没有录音时只出字幕（3.14）。

**4. 收幕和幕末**（api-contract 3.11，契约 2.8、2.8.1）

收幕：

- 每次提交以后检查当前幕。下面任一条成立，这一幕就收了：
  - `end.onBeats` 里有一个有了结果（happened / altered / prevented，或过了 `window.latest` 来不及）；
  - 时钟到了 `end.atLatest`。
- 结算只到收幕节拍为止（settle 的 `stop_after`；按 `atLatest` 收的，结算到 `atLatest`）。之后的节拍留到幕切换的第 3 步再结。
- 最后一幕（`exits` 为空）收幕后进结局，是结局那张卡的事；本卡不推 `act_ended`。
- 收幕以后、玩家选定之前，世界不动：
  - 网关对 `text`、`activity_start`（`purpose: "act_plan"` 除外）、`action` 回 `invalid_request`（第 5 节，不带 `turnId`）；
  - 已经在队列里的对话和动作，叙事者结成 `no_response`：0 分，不写事件。

`act_ended`：

- 网关在这次提交的 `commit`，和 `turn_settled` / `action_result` 之后推一次。断线时由 `welcome.pending.actEnd` 补上。
- **`options`**：`Act.exits` 按 `roles`、`requires` 过滤（用收幕时的状态）。每条去处：
  - `optionId` = 去处 ID；`label` 照世界模型。
  - 目标时刻 = `exit.t` 加 `alignTo` 的偏移（这一局 alignTo 节拍的排定时刻减去原作时刻），不早于此刻。
  - `sceneId`：落点在 `toAct` 那一幕的场景。
  - `tLabel`：目标时刻按 `clock.labels.format`。
  - `where` = `Place.name` +「・」+ 日子 +「の」+ 时段。地点是落点，日子和时段是目标时刻在 `clock.labels` 的 `days`、`bands` 里的叫法，不套 `format`。
  - `sub` 照 `ActExit.sub`，没有就省略。
  - `with` = 去处效果里 `set var.player.companionOf` 的人物，加上 `arrival.opener`，去重。切片里老爺那条是 `["char.old-man"]`，city 那条是 `[]`。
  - `because: null`。
  - `enRoute`：条件照 3.11（节拍还没结果，本局排定时刻在此刻和目标时刻之间）。`melosMinutes` 用 `arrival_delta` 按收幕时刻算，最后一项为 `null`；`afterLine` = `after`。
- **`recapLines`**：这一幕里玩家引起的事件，取它们的 `summary`。
  - 「玩家引起的」= `actor` 是 player 或 `beneficiary` 是 player，已提交，`effects` 非空，玩家可见。
  - 按 `seq` 排，最多 4 条；多了取最后 4 条。
  - 一条都没有时为空，见「契约的小改」第 1 条。
- **`freeform`** = `{allowed: triesLeft > 0, triesLeft}`。`triesLeft` = 2 减去这次幕末已经试过的次数（按局记，幕切换后清零）。

选给定去处：`act_choose {optionId, enRouteChoice?}`，评测是 `choose(exit, en_route)`。

- **回 `invalid_choice`、不写事件的情况**（第 5 节）：
  - `optionId` 既不在这次的 options 里，也不是这次的替代去处；
  - `enRouteChoice` 超出范围，或给了不带 `enRoute` 的去处。
  - `eval_api.choose` 这时返回 `error: "invalid_choice"`、没有事件的结果（E4-103）。
- **事件**：网关写任务（`kind = "choose"`），叙事者按 2.8.1 在同一次提交里写：
  1. `enRouteChoice` 不是最后一个时：玩家的 `action` 事件。`origin: "act"`，`exitId`，`dt: 0`，效果 = 那一项的 `effects`，过第 3、4 步。
  2. 玩家的 `act-transition` 事件：`origin: "act"`，`exitId`，`t` = 此刻，`dt: 0`，`effects` = 去处的 `effects`。
     - 这些是世界模型写死的效果，由数据的校验工具静态查过，不过模型检查。
     - `check` 是 passed，`checker: "world-exit"`（E4-102 要求 passed）。
  3. 结算到目标时刻。目标时刻在第 1 步以后算，`alignTo` 跟着动。
     - 这一段玩家一律算不在场：不按契约 2.1 ② 让玩家 learn 节拍的 public 事实，也不问节拍时机的固定演出。
     - W-1 的 `settle` 按 `var.player.location` 判在场，而这时玩家的地点还没换。要给它一个「玩家不在场」的参数，代码 PR 里和数据对（数据给契约补这一句时一起加）。
  4. 系统的 `act-transition` 事件：`origin: "act"`，`t` = 目标时刻，`effects` = `set var.act.current`、`set var.player.location`；`check` 是 passed，`checker: "world-exit"`。
- **记在局上的**：玩家的位置点（`exit.spot`，没写就是起点）；落地（有 `opener` 时记成待落地）。同时清掉幕末的试次和替代去处。

说出打算：`act_propose {clientMsgId, text}`、用声音（`activity_start {purpose: "act_plan"}`），评测是 `propose(text)`。

- **什么时候收**：收了幕、而且 `triesLeft > 0` 才收，不然回 `invalid_request`。
  - 文字：原话照常存进 `utterances`（这一轮只有玩家说话），写任务 `kind = "plan"`。
  - 声音：网关只做转写，假 Live 给一条固定的玩家字幕，照常推 `transcript`；`activity_end` 以后写同样的任务，结果带 `turnId`。
- **新的提示类型 `plan`**（flash，思考 LOW）：
  - 输入：这一幕的去处、这一幕有没有 `Act.plan`、世界状态、玩家的话（`<utterance speaker="player">`）。
  - 输出：
    - 能不能成行；
    - 转述 `label`（「〜ことにした」里的「〜」，不逐字引用玩家的话）；
    - 同行的人；
    - 打算自己的效果（例：把约定告诉城里的人 → `learn char.crowd fact.promise`，S-077 ⑥）；
    - 不成行时，1〜2 行故事里的理由，和最接近的替代去处（某个给定去处，或另一个打算）。
- **能成行，而且这一幕有 `Act.plan`**（切片的第一幕）：
  - 打算自己的效果过第 3〜5 步。被否决就当作不成行。
  - 过了：同一次提交里写玩家的 `act-transition` 事件（`origin: "act"`）。
    - 不写 `exitId`，写 `plan {label, toAct, place, t, with?}`，其中 `toAct`、`place`、`t` 照 `Act.plan`。
    - `effects` = `Act.plan.effects` 加上通过的效果。
  - 然后照上面选去处的第 3、4 步。落点用 `Act.plan.spot`，落地用 `Act.plan.arrival`。
- **这一幕没有 `Act.plan`**（完整版的第二、三幕）：叙事者按世界模型判落点是 M3 的事（契约 2.8 `plan` 的注释）。本卡一律不成行，替代去处只给给定的去处。
- **不成行**：
  - 不写事件，试次加一。
  - 替代去处记在局上：是给定去处时，`optionId` 就是去处 ID（见「契约的小改」第 2 条）；是另一个打算时，`optionId` 是 `plan_…`。
  - `plan_…` 被选中时按成行处理（上面那条）。
- **`act_plan_result`**：
  - `accepted`；
  - `narration`：成行是一行「あなたは、{label}ことにした。」，不成行是 1〜2 行理由；
  - `alternative`（`optionId`、`label`、`sceneId`、`tLabel`）、`triesLeft`；
  - 带 `clientMsgId`（文字）或 `turnId`（声音）。
- **打算的文字怎么过滤、怎么删**：`label`、`narration`、`alternative.label` 都是从玩家的话转述出来的。
  - 写入前过和事件 `summary` 一样的过滤（data-design 5.1）：Model Armor（第 0 步的标记，B-2 留了位置）、R6 的规则部分（个人信息的模式、和玩家原话连续 8 字相同）、长度上限（`label` 30 字，`narration` 每行 60 字）。
  - 不过的换成固定的、不转述的说法：
    - `label` →「自分で決めた道を行く」，成行的 `narration` 跟着它；
    - 不成行的 `narration` →「その考えは、いまは形にならなかった。」；
    - `plan_…` 替代去处的 `label` → 改给第一个给定去处。
  - 成行的事件里的 `plan.label` 删不掉（事件不删），所以必须写入前就干净，同 `summary`。
  - `turns.result` 里存的这些文字：記憶帳按轮删除（L1）时清空那一轮的；结局生成以后，和 `utterances` 一起清空（data-design 5.2、5.3、5.5）。本卡写好清空的函数和测试，L1 和结局那两处由记忆、结局那两张卡接上。
  - 局上的 `plan_alternative` 用过（幕切换）就清掉。

幕切换：

- **推送顺序**（选去处，或成行的打算）：`commit`（这次提交的全部事件）→ 打算的话先 `act_plan_result` → `act_transition`。跳过的这段时间里结算的节拍，玩家不在场，不可见。
- **`act_transition {fromActId, toActId, recap, snapshot, arrival?}`**：
  - `recap`（「その頃」，最多 3 件）从第 3 步结算的事件里按契约 2.8.1 第 5 步取：
    - 顺序：和玩家有关的约定兑现或违背 → `keyMoment` 事件 → 玩家见过的人物自己做的事（`origin: "plan"`）。
    - 导演事件（`origin: "director"`）也在这里交代（S-045 ③，契约 3.2 第 3 条）。
    - 「见过」按近似算，因为 WorldState 不记谁见过谁：这一局里和玩家说过话（有他说话的轮次），或者在玩家在场时提交的事件里当过 `actor` 或 `target`。
    - 不写 `voided` 的约定和 `forget`；`line` 用 `summary`。
    - `keyMoment`、人物的打算和导演是后面的卡，本卡按字段取。切片照原作走时这里为空，城里的三天由前端的跳转页写（S-080 ①）。
  - `snapshot` 是落地以后的快照（2.3，含 `player.spot`）。
  - `arrival` 照去处或 `Act.plan` 原样下发，没有就省略。
- **落地**：`arrival` 有 `opener` 时，网关收到 `act_landed {actId}` 才让人物开口。
  - `actId` 要是当前幕，同一幕只认第一次，别的忽略。
  - 发起一轮 `turn_started {reason: "arrival", speaker: opener}`，`turnSeq` 由服务端分配、最高位为 1（3.1）。
  - 人物先说一句（假 Live 给这个人物一句固定的开场白），之后照常对话。
  - 这一句不花故事时间、不交给叙事者、没有 `turn_settled`。原话照存（`turns` 写一行 `kind = "arrival"`），記憶帳按轮删除时一起清空。

**5. 评测入口**（api-contract 第 7 节）

- `act(kind, target, params)`、`propose(text)`、`choose(exit, en_route=None)`：和 WebSocket 走同一条流程（写任务、叫叙事者），不再抛 `EvalNotImplemented`。
- 返回（同 `say`）：这一步的全部事件（含被否决的）、时钟前进了几分钟。另外：
  - `act`：`status`、`narration` 或 `setPiece`、这一步演过的固定演出 ID、`aid`；
  - `propose`：`accepted`、成行时的 `plan`、`alternative`、`triesLeft`；
  - `choose`：选了不在选项里的去处时的 `error`。
- 检查点停在收幕节拍上（例 `sc.canon@beat.07`）时，`setup()` 之后就是幕末待选。

**6. 存储**（迁移 0003）

  - `player_spot`；
  - `played_pieces`（jsonb，这一局演过的固定演出 ID）；
  - `plan_tries`、`plan_alternative`（jsonb）；
  - `arrival`（jsonb，待落地）。
- `turns`：
  - 加 `client_msg_id`；
  - 加 `request`（jsonb：动作的 kind / target / params / actionId，幕末的 optionId / enRouteChoice）。不放原话，原话在 `utterances`；
  - 加 `result`（jsonb：要推的 `action_result` / `act_plan_result` / `act_transition`，和这次演的固定演出）。打算的文字怎么清见第 4 条；data-design 5.3 `turns` 那一行由数据跟着改；
  - `kind` 多 `action`、`choose`、`plan`、`arrival`。
- `playthrough_metrics` 加（data-design 第 3 节：每个功能加一列，数据跟着改）：
  - `cost_narrate_usd`、`cost_plan_usd`；
