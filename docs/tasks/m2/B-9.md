## 目标

做完以后：

1. 切片的一局能走到结局：
   - 第四幕里梅洛斯冲进刑场，或者到了日没他还没到，网关推 `ending_started`，前端开始演；
   - 后台生成三层结局，生成好了推 `ending_ready`，`GET …/ending` 回 200。
2. 结局按这一局写：
   - 尾声、你的结局、人物的结局由 Claude 按这一局的事件写，每一句都指回事件；
   - 世界结局的分类、演出站位、受影响的排序、卡上的字数由代码算、代码查，不交给模型。
3. 写不好也有结局：校验两次不过、超时或出错，就用 ux-design 11.4 的模板，照样有结局页和结局卡。
4. 评测能读结局：
   - `eval_api.ending()` 给契约第 5 节的完整形状，含 `signature`；
   - E5、E7、E8 里现在跳过的结局检查能跑；
   - B-5 的模拟局在文字快速模式里一局能跑到结局。
5. 结局生成以后：
   - 这一局的原话清空（S-035）；
   - 这一局不再接受对话和动作。

## 切片里简化了什么

| | 全版（backend-design 2.9） | 切片（本卡） |
|---|---|---|
| 世界结局 | 底线类，或这一局生成的结局（`variant`） | 只出底线类（`baseline: true`）；标题是世界模型里这一类的 `label` |
| 列哪些人物的结局 | 7 个可对话人物 | 世界模型新加的 `endings.characters`（切片也写那 7 个）；没被波及的合成一行 |
| 受影响的排序 | 因果链、关系、约定、记忆，加权 | 只数事件（第 3 条）。关系和记忆这一层还没做 |
| 检查 | 确定性校验 + 模型检查三层讲不讲得通 | 只有确定性校验 |
| 个人信息 | Model Armor 的 SDP | 叙事者 R6 规则部分的模式 |
| 跑在哪 | Cloud Tasks | 叙事者的任务表，`turns` 加一种 `kind: "ending"`，和别的轮次一样按局串行 |

切片里实际能到的世界结局：
- 玩家不会被抓（S-077 ②），到不了「あなたが身代わりになった」；
- 王在切片里不能对话，「王が先に変わった」也几乎到不了；
- 常见的是 `canon-reunion`；
- 玩家在第四幕拖住梅洛斯，会是 `too-late`。

代码照 5 类都写，测试用造出来的状态覆盖。

## 范围

### 做

**1. 什么时候进结局**（`narrator/ending.py`，叙事者提交时判）

- 只在最后一幕判，也就是 `exits` 为空的那一幕，切片是 act.4。每次提交以后看下面两条，满足一条就进：
  - 期限盯的节拍（`clock.deadline.watchBeat`，即 beat.24「日没、刑場へ」）这次有了结果；
  - 时钟到了 `clock.deadline.t`，也就是这次写了期限的系统事件。
- 满足了，在同一个事务里做五件事：
  1. 用共享规则库把这一幕结算到收幕：`settle` 到这一幕的 `end`（`onBeats` 有了结果，或者到了 `atLatest`），写成系统事件，`origin: "schedule"`，和平时到点结算一样。
     - 为什么在开演前就结算完：演出要从梅洛斯冲进来一直演到緋のマント（ending-shots 镜头 1〜11），所以世界结局开演前就要定下来。
     - 这样做不改结局：结局开始以后玩家什么也做不了（11.1，麦克风放掉）。收幕这一段本来就只按时间表走，和 S-077 ⑥ 一致（幕末的打算不改世界结局的分类）。
  2. 按结算后的状态 `classify`，再算 `staging`（第 2 条）。
  3. 局的 `status` 改成 `ended`，写 `ended_at`。
  4. 插一条 `kind: "ending"` 的任务，`request` 带 `trigger`、`staging`、分类。
  5. 这一轮的 `result.push` 加上 `ending_started`，排在 `turn_settled` 后面。
- `trigger` 的取法：
  - watchBeat 发生了，就是 `story-closed`：演出从梅洛斯冲进来演到收幕；
  - 到了期限 watchBeat 还没发生，就是 `deadline`。
- 玩家不在刑场也照样进结局：演出照演，玩家的状态是 `absent`。
- 玩家什么都不做，时钟就不走，结局也不来。第四幕有 `wait`（B-3：跳到这个地点的下一个节拍），这一点不改。
- `classify` 为空（5 类都不成立）时：取 `endings.world` 的最后一类，Trace 记规则名 `ending-unclassified`。见数据评审第 4 题。

**2. 演出站位 `staging`**（确定性，按结算到收幕以后的状态）

- `place`：watchBeat 的地点（`place.execution-ground`）。
- `characters` 列这些人：
  - 人质：`var.hostage.who` 是人物时，切片是セリヌンティウス（S-053 默认在场）；
  - 梅洛斯、王；
  - 结算后在这个地点的其余非群体人物：切片里是老爺、緋のマントの少女；
  - 玩家：`id: "player"`。
- 群体（警吏、群众）不列：前端在刑场一直摆着它们（F-4）。
- 状态，每个人按顺序取第一条成立的：

  | 谁 | 条件 | `state` |
  |---|---|---|
  | 任何人 | 结算后不在这个地点 | `absent` |
  | 人质 | `var.hostage.fate = released` | `freed` |
  | 人质 | 其余（`held`、`on-cross`、`executed`） | `on-cross`（不演处刑，11.1） |
  | メロス | `var.melos.custody = returned` | `arriving`（演出里从西门跑进来） |
  | メロス | 其余 | `collapsed` |
  | 王 | `var.king.disposition = reformed` | `approaching` |
  | 王 | 其余 | `present` |
  | 老爺、少女等 | — | `in-crowd` |
  | 玩家 | 位置点在群众前排（切片是 `stake-front`，「身を寄せる」落在这里，S-077 ⑤） | `in-crowd` |
  | 玩家 | 其余（例：「市に残り」落在 `ground-west`） | `present` |

- api-contract 3.13 的例子（`deadline` 时梅洛斯 `arriving`）和 mock（`story-closed` 时梅洛斯 `present`）都按这张表改。

**3. 受影响的排序**（确定性）

- 列哪些人物：世界模型的 `endings.characters`（新字段）；没有这个字段，就列 `talkable` 的人物。
- 每人一个分数，是两项相加：
  - 这一局「玩家的事件」里和他有关的条数：
    - 「玩家的事件」= 已提交、`actor` 是玩家或 `origin` 是 `turn` / `action` / `plan` 的事件，不含 `forget` 和被否决的；
    - 「和他有关」= 他是事件的 `actor`、`beneficiary`，或者是 `effects` 里的对象（`learn`、`relocate`、`improv` 的 `character`，`promise` 的对方）；
  - `changedBeats` 里他是 `participants` 的节拍数。
- 给 `rank`：
  - 分数 0 的：`unchanged: true`、`rank: null`；
  - 其余按分数从高到低给 `rank` 1、2、…；
  - 同分时按 `endings.characters` 的顺序。
- 全版要加的关系、记忆、约定的权重，等记忆那张卡。

**4. 生成**（`kind: "ending"` 的任务）

- 叙事者取到这条任务：在事务外调模型（和第 2 步提取一样），再用一个事务存结果。
- 用哪个模型：Claude Sonnet 5.5（D-028，B-8 的 `sonnet` 档）。
  - 新的提示种类 `ending`：`prompt_texts/ending.txt` 加输出 Schema，版本号照 B-2 的算法。
  - 结构化输出，effort low（不先思考），因为这一步要快，时限见下面。`config.TEXT` 照 B-8 加一行：供应商、档名加版本、思考、effort、输出上限、时限。
- 送给模型的 `request`（回放按它算键）：
  - 世界模型前缀：和别的种类同一份，走缓存；
  - 分类：`outcome` 和它的 `label`；最终状态里 `endings.signature.vars` 那几个变量的值；
  - `changedBeats`：每条带结果、原著的 `summary`、`causedBy` 的事件 ID；
  - 人物：`rank`、`unchanged`、`originalEnding`；
  - 这一局的全部事件，含不可见的和系统的，不含 `forget` 和被否决的。每条带 `eventId`、`t`、`actor`、`type`、`summary`、`beneficiary`。`summary` 用存的那份，玩家写作身份名；
  - 开局身份名：称号里用；
  - 不给原话（S-046），不给记忆（还没做）。
- 要模型写的（输出 Schema）：
  - `epilogue`：3〜5 句，每句带 `cites`。
  - `contrast`：`{ original, yours, beat? }`。
    - `beat` 只能取 `changedBeats` 里的。
    - `changedBeats` 为空时不带 `beat`，写「原作でも…」那种对照（11.4 `canon-reunion` 的口吻）。
  - `subtitle`：世界的去向，≤ 26 字，卡片副题（11.3、11.4）。
  - `cardContrast`：「原作との違い」一句，≤ 48 字。
  - `you`：
    - `title`：≤ 14 字，带身份名，不嘲笑玩家，附 `cites`；
    - `fate`：行方，一句，附 `cites`；
    - `didForYou`、`youDid`：各 0〜2 条，每条带 `cites`。
  - `characters`：`unchanged: false` 的每人 1〜3 句 `yours`，每句带 `cites`。排第 1〜3 的第一句 ≤ 40 字，因为它就是卡上那一行（11.3）。
  - 除了称号，文字里玩家一律写「あなた」。
- 代码补的，不交给模型：
  - `world` 里：`outcome`、`title`（这一类的 `label`）、`summary`（同 `title`）、`changedBeats`、`finalVars`、`signature`；
  - `player` 里：
    - `fate.id`：结算后在 `staging` 的地点是 `witness`，不在是 `elsewhere`；`var.player.custody` 是 `hostage` / `executed` 时就用这个值（切片到不了）；
    - `relationships`：空数组；
    - `lastScene`：地点；`present` = `staging` 里不是 `absent` 的人物；`description` = 地点名 + 时间说法；
  - `characters[].original`：取 `originalEnding`；
  - `card`：
    - `title` = `you.title`；
    - `characterLines` = `rank` 最前的 1〜3 人各自的第一句；都 `unchanged` 时放梅洛斯的 `originalEnding`（契约 1.6）。
- 时限：
  - 一次调用 30 秒〔推算，S-5 用实测定〕。超时就取消，照 backend-design 第 138 行重发一次；
  - 重写也算一次。最多调两次，之后走模板（第 6 条）；
  - 从 `ending_started` 起整段最长约 60 秒。演出盖不住时，前端照 11.1 出「物語を綴じています」。
  - B-8 的「风险」推算结局生成要 15〜40 秒（含思考约 3,000 token），提过分两次生成、先出卡面。切片不思考、输出约 1,500 token，推算 15 秒左右〔推算〕，先一次生成。验收第 13 条的探针 p95 超过 20 秒，再照 B-8 说的分两次。
- 花费：
  - 记 Claude 那本账，`use` 照 B-8 按这一局是正式还是评测；
  - 〔推算〕一次约 0.03 美元：前缀 1.7 万 token 走缓存，新的输入约 5,000，输出约 1,500，按 B-8 的单价 Sonnet 输入 2 美元、输出 10 美元、缓存读取 0.05 倍（每百万 token）。重写一次就再多一份。

**5. 校验**（确定性，全在代码里）

1. 引用：
   - 每一句（`epilogue`、`didForYou`、`youDid`、人物的 `yours`）和 `title`、`fate` 的 `cites` 都不能为空；
   - 引用的都是这一局已提交的事件，不能是 `forget`（契约第 5 节）。
2. 条数：
   - `epilogue` 3〜5 句；`didForYou`、`youDid` 各 0〜2 条；
   - `unchanged: false` 的人物各 1〜3 句，`unchanged` 的人物一句也没有；
   - 漏写了该写的人物，或者写了不该写的人物，都算不过。
3. 字数（11.3）：`title` ≤ 14，`subtitle` ≤ 26，卡上的人物那一行 ≤ 40，`cardContrast` ≤ 48。
4. `contrast.beat` 必须在 `changedBeats` 里。
5. 不逐字引用玩家原话（S-046，契约第 5 节）：
   - 每个文字字段和这一局的每句原话比；
   - 先把世界模型的专有名词（人物名、地名、引文）换成占位符，再算最长公共子串，≥ 8 字就不过；
   - 和 R6 规则部分用同一个 `lcs_len`、同一个 `VERBATIM = 8`，只多换占位符这一步；
   - 在清空原话之前做。
6. 现实的个人信息：用 R6 规则部分的 `PII` 模式（电话、邮箱、住址）。
7. S-067：这一局 `var.hostage.fate = executed` 或 `var.player.custody = executed` 时，文字里不能有「処刑」「死」「殺」「最期」（11.2）。
8. 删过记忆的人物不写「他记得你」：記憶帳还没做，本卡的输入里也没有记忆，这条等记忆那张卡。

不过的处理：
- 第一次不过：把不过的项（规则名和字段，不带文字）交给模型，重写一次；
- 还不过：用模板；
- Trace 只记规则名、次数、耗时、花费，不记文字（data-design 第 8 节）。

**6. 模板**（S-065；ux-design 11.4）

- 从世界模型新加的 `endings.templates` 里挑：同一个 `outcome` 有几条时，取第一条 `when` 成立的。
- 填法：
  - `card`：全用模板句。`title` 里的 `{role}` 换成开局身份名；
  - `world.title`：这一类的 `label`；
  - `epilogue`：一句，就是模板的 `subtitle`，`cites` 是这一局把分类用到的几个变量设成现值的事件（各取最后一次设的那条，例：期限的系统事件、beat.24、beat.26）；
  - `you.fate.label`：模板的 `fate`；`didForYou`、`youDid` 为空；
  - 人物：
    - 模板里写了句子的人物：梅洛斯；A、B 两组另有セリヌンティウス；
    - 这几个人 `unchanged: false`，按模板里的顺序给 `rank` 1、2，`yours` 一句，`cites` 同上；
    - 其余 `unchanged: true`；
  - `contrast`：`world.contrast` 不带（API 里可选）；卡上的 `contrast` 用模板的。
- 走模板的局在 `playthrough_metrics` 里单独记（S-065）。

**7. 保存**

- `endings` 表，迁移 0005（data-design 第 84 行）：
  - `ending_id`；
  - `playthrough_id`：整局删除时一起删；
  - `body`：jsonb，契约第 5 节的 Ending，`schemaVersion` 和写事件的 `SCHEMA_VERSION` 一致；
  - `decided_at`。
- 在同一个事务里做完下面这些：
  - 存结局；
  - 清空这一局的原话（`utterances.text`，S-035），以及 `turns.result` 里存的打算文字（B-3 写好的 `clear_plan_texts`，说明里已经留了「结局以后传 `None`，清这一局全部」）；
  - 补 `playthrough_metrics` 的结局几列；
  - 把任务改成 `done`，`result.push = [ending_ready]`；
  - NOTIFY。
- `playthrough_metrics` 加这几列：
  - `ending_started_at`、`ending_outcome`、`ending_template`（布尔）、`ending_calls`、`ending_ms`；
  - `cost_ending_usd`：data-design v1.2.1 定的，每局费用是所有 `cost_*_usd` 之和，新功能各加一列；
  - 原因链上有没有导演事件：切片没有导演，这一列不加。

**8. 网关**

- `GET /v1/playthroughs/{id}/ending`（api-contract 2.8）：
  - 要登录；别人的局回 403；
  - 还没进结局：404 `not_found`；
  - 任务还没好：202 `{ "status": "pending", "etaSeconds": n }`，`n` = 30 减去已经过的秒数，最少 5；
  - 好了：200 `EndingView`，照 2.8 的对应从存的 Ending 投影。`signature`、`finalVars`、`changedBeats`、各处的 `causedBy` 不给。
  - `card.fallbackImageUrl` 是 `/endings/{outcome}.webp`。5 张预画插画和场景包一样，由前端的部署出文件。没做出来时这个地址是 404，前端照 11.3 只在截帧失败时才用它。
- WebSocket：
  - 推送顺序：触发结局的那次 `commit`（含收幕结算的系统事件）→ `turn_settled` → `ending_started`；结局任务提交以后推 `ending_ready`。
  - 进了结局以后：
    - 网关关掉这一局的 Live 会话，丢掉音频帧；
    - 之后收到 `text`、`activity_start`、`action`、`act_choose` 都回 `invalid_request`，不断开（和 3.11 收幕后的做法一样）。
  - 重连（`hello`）时局已经 `ended`：
    - `welcome` 照常，`snapshot.status` 是 `ended`；
    - 接着补推一次 `ending_started`，用存的那份 `staging`；
    - 结局已经好了，再推 `ending_ready`。
- `/v1/me`：`ended` 的局不再算进行中的局（一账号一局的索引本来就只看 `active`）。

**9. 评测入口和假模型**
