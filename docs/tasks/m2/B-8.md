## Goal / 目標

When this is done:

完了すると：

1. Apart from Live voice and pre-recorded lines, every text model the narrator uses goes through Claude. Claude uses zg's Anthropic API credit (D-028), not Claude on Vertex.
   Live の音声と事前収録セリフを除き、ナレーターが使うテキストモデルはすべて Claude を使う。Claude は zg の Anthropic API の枠を使い（D-028）、Vertex 上の Claude は使わない。
2. There is only one copy of the Claude client, unit prices, cost calculation, ledger and replay keys, shared by the backend's narrator and Data's judges.
   Claude のクライアント、単価、費用の計算、台帳、リプレイのキーは一つだけにし、バックエンドのナレーターとデータの審査員で共用する。
3. CI and containers still use only the fake model and replays, with tests on a disabled network. Replays are split by provider, so Google replays cannot answer Claude calls.
   CI とコンテナは引き続き偽モデルとリプレイだけを使い、テストはネットワーク禁止で動かす。リプレイはプロバイダーごとに分け、Google のリプレイでは Claude の呼び出しが見つからない。
4. Which model each kind of call uses, how deep thinking goes and how long the time limit is are all in config. Latency and per-playthrough cost are first written in this card as estimates, then replaced with real numbers after one probe on the Mac.
   呼び出しの種類ごとにどのモデルを使うか、思考をどこまで深くするか、制限時間をどれだけにするかは、すべて設定に書く。遅延と 1 プレイのコストはまずこのカードに推定で書き、Mac で一度小規模に計測した後に実数に置き換える。

### What stays on Google (D-028's "only Live voice and pre-recorded lines") / Google に残るもの（D-028 の「Live の音声と事前収録セリフだけ」）

The text-related parts of a Live session all stay in Live and are not split off to Claude:

Live セッションの中でテキストに関わるものはすべて Live に残し、Claude に分けない：

- Character answers (voice, including turns where the player's typed text is sent in), characters speaking first (`speak_first`);
  人物の返答（音声。プレイヤーが打った文字を送り込むターンも含む）、人物が先に話すこと（`speak_first`）。
- Transcription of the player's speech (the utterance the narrator reads is exactly this) and of characters' speech (subtitles);
  プレイヤーの発話の書き起こし（ナレーターが読む発話そのもの）、人物の発話の書き起こし（字幕）。
- Transcription of a plan spoken aloud at the end of an act (Transcribe Live, Q-B10, M3);
  幕末に声で話したプランの書き起こし（Transcribe Live、Q-B10、M3）。
- B-6's pre-recorded lines (Live reads them out) and their automatic checks.
  B-6 の事前収録セリフ（Live が読み上げる）とその自動チェック。

If split, the same character would be Gemini when speaking and Claude when answering text, their personality would not match, and there would be the latency of an extra call; besides, Claude has no real-time voice.

分けてしまうと、同じ人物が話すときは Gemini、文字で答えるときは Claude になり、性格が合わなくなり、呼び出しが 1 回増える分の遅延も生じる。そもそも Claude にはリアルタイムの音声がない。

**Model Armor** (second layer for injection, supplement for personal information, only HIGH for harmful content, `sanitizeModelResponse` for character output) is not a generative model but Google's filtering service. We recommend keeping it as the second layer: it is from a different vendor than the Claude classifier, adding one more independent check (PM to decide).

**Model Armor**（インジェクションの第 2 層、個人情報の補完、有害な内容は HIGH のみ、人物の出力の `sanitizeModelResponse`）は生成モデルではなく、Google のフィルタリングサービス。従来どおり第 2 層として残すことを勧める：Claude の分類器とは別の会社なので、独立したチェックが一つ増える（PM が決める）。

evals はバックエンドに依存せず（ランナーはモジュール名で `eval_api` を読み込む）、バックエンドも evals に依存しないので、共用の部分は新しい小さなワークスペースのパッケージに入れ、両方がそれに依存する：

- **Ledger** `Ledger(path, provider, max_total_usd, max_item_usd=None, item=None, use="product")`: the backend's current `models/ledger.py` and Data's `ClaudeLedger` merged into one. The line format is unchanged (`at`, `provider`, `kind`, `model`, `usage`, `costUsd`, `item`), plus `use`, tagged by which path the call belongs to rather than whether it runs inside an eval: the narrator's steps, safety classification, memory, ending, Live and pre-recorded lines are `"product"` (even when run inside an eval; lines in the Google ledger get it too); judges and the AI player are `"eval"`. S-5's per-playthrough cost only adds `product`. Old lines without this column are inferred from `kind` (`judge` and `player` are eval). Cap computation is unchanged: the total cap counts only its own vendor, and the per-item cap combines both ledgers.
  **台帳** `Ledger(path, provider, max_total_usd, max_item_usd=None, item=None, use="product")`：バックエンドの現在の `models/ledger.py` とデータの `ClaudeLedger` を一つにまとめる。行形式は変えず（`at`、`provider`、`kind`、`model`、`usage`、`costUsd`、`item`）、`use` を加える。評価の中で動かしているかどうかではなく、呼び出しがどの経路に属するかで付ける：ナレーターの各ステップ、安全分類、記憶、エンディング、Live、事前収録セリフは `"product"`（評価の中で動かしても同じ。Google の台帳の行にも付ける）。審査員と AI プレイヤーは `"eval"`。S-5 の 1 プレイのコストには `product` だけを足す。この列がない古い行は `kind` から推定する（`judge`、`player` は eval）。上限の計算方法は従来どおり：全体の上限は自分の会社の分だけを数え、項目ごとの上限は 2 冊の台帳を合わせて数える。
- **Unit prices**: `claude-prices.json` moves from `evals/config/` into this package (Data already wrote cache-read multipliers by tier in #74: Haiku 0.1× input price, Sonnet and Opus 0.05×, Fable 0.025×). Recognizing models by tier, computing cost and pre-call estimates all live here. Google's unit prices stay in the backend's `config.PRICES`.

- **Replay key** `<provider>|<model>|<prompt version>|<sha256 of the request>`: Data's judges already use this format; the backend's key currently lacks the provider, and this card adds it.
  **リプレイのキー** `<provider>|<モデル>|<プロンプトのバージョン>|<リクエストの sha256>`：データの審査員はすでにこの形式。バックエンドのキーには今 provider がないので、このカードで加える。

The SDK lives in this package's optional dependency `real`, and both the backend's and evals' `real` reference it.

### Backend changes / バックエンドの変更

1. **Config**: `TEXT_MODELS` becomes one row per prompt kind (provider, model tier, thinking, effort, output cap, time limit). Claude's model tiers are written as `haiku` and `sonnet`, and replay keys use the tier name plus a code (e.g. `sonnet-5.5`); concrete model IDs are given only on the Mac via environment variables (`ZJ_CLAUDE_HAIKU`, `ZJ_CLAUDE_SONNET`), never written in the repo, the same as Data's judges. IDs whose tier name cannot be recognized are not called.
   **設定**：`TEXT_MODELS` をプロンプトの種類ごとに 1 行にする（プロバイダー、モデルのティア、思考、effort、出力の上限、制限時間）。Claude のモデルのティアは `haiku`、`sonnet` と書き、リプレイのキーにはティア名とコード（例 `sonnet-5.5`）を使う。具体的なモデル ID は Mac 上で環境変数（`ZJ_CLAUDE_HAIKU`、`ZJ_CLAUDE_SONNET`）で渡すだけで、リポジトリには書かない。データの審査員と同じ。ID からティア名が判別できないものは呼ばない。
2. **Real client** `models/claude.py` (`ClaudeText`, with the same interface as `RealText`):
   **本物のクライアント** `models/claude.py`（`ClaudeText`。`RealText` と同じインターフェース）：
   - The world model prefix goes in the first system block and this prompt kind's instructions in the second, each followed by a cache breakpoint (all prompt kinds on the same tier share the prefix; the same prompt kind shares the instructions); state, this turn and request fields go in user, with rendering reused from `vertex.render` (the prefix block moved out to be shared, `models/render.py`).
     世界モデルのプレフィックスを system の 1 段目に、このプロンプト種別の説明を 2 段目に置き、それぞれの後にキャッシュのブレークポイントを一つずつ打つ（同じティアの各種プロンプトでプレフィックスを共有し、同じプロンプト種別で説明を共有する）。状態、このターン、リクエストのフィールドは user に置き、描画は `vertex.render` を流用する（プレフィックスの部分は共用のために外に出す、`models/render.py`）。
   - Schema: the copy sent to the API strips unsupported keywords and sets `additionalProperties: false` on every object; on receipt the full Schema is still validated locally, and failure gives `BadOutput`, resent per the time-limit rules.
     Schema：API に送るものはサポートされないキーワードを取り除き、オブジェクトはすべて `additionalProperties: false` にする。受け取った後は従来どおり完全な Schema でローカルに検証し、通らなければ `BadOutput` とし、制限時間のルールに従って再送する。
   - `temperature` is not passed: `messages.create` (both sync and async) in Anthropic's Python SDK 1.13.0 has no `temperature`, `top_p` or `top_k` parameters (how this was verified: both signatures were inspected with `inspect.signature`, and passing them raises `TypeError` directly; only the SDK was checked, not the API over raw HTTP). v0.2's "pass it only when thinking is off" cannot be done; output stability relies on the Schema and the thinking level.
     `temperature` は渡さない：Anthropic の Python SDK 1.13.0 の `messages.create`（同期、非同期の両方）には `temperature`、`top_p`、`top_k` の引数がない（確認方法：`inspect.signature` で二つのシグネチャを見て、渡すとそのまま `TypeError` になる。確認したのは SDK だけで、生の HTTP で API を試してはいない）。v0.2 で書いた「思考をオフにしたものだけ渡す」はできない。出力の安定は Schema と思考のレベルに頼る。
   - Before the call, check the ledger at the estimated cost (`BudgetStop`); after the call, record actual usage; calls cancelled by the time limit are recorded at the estimate (they may already be billed, so better to over-record).
     呼び出し前に見込み費用で台帳を確認し（`BudgetStop`）、呼び出し後に実際の使用量で記帳する。制限時間で取り消したものは見込みで記録する（すでに課金されているかもしれないので、多めに記録する方がよい）。
3. **Client selection per call**: one eval can have both Claude and Google calls (`reply` goes to Google). Vertex environment variables are only checked when one of the Google kinds is actually called; runs that only call Claude do not require them.
   **呼び出しごとにクライアントを選ぶ**：1 回の評価の中に Claude と Google の呼び出しが同時にありうる（`reply` は Google を使う）。Vertex の環境変数は Google の種類を実際に呼ぶときだけ確認し、Claude だけを呼ぶときは要求しない。
4. **Handle 429 and 529 differently for runs and for serving**: runs on the Mac (S-2, evals, probes) stop on the first one (S-079); later, when serving players, the service is not stopped: resend once per the time-limit rules, and if that still fails, commit only the clock event for that turn and count it in `playthrough_metrics` (the degradation in backend-design 2.4). This card only builds the run half; the serving half is written into the code's branches and tests, waiting for the production gateway to hook it up.
   **429、529 の扱いを実行時と提供時で分ける**：Mac での実行（S-2、評価、小規模計測）は最初の 1 回で止まる（S-079）。今後プレイヤーに提供するときはサービスを止めず、制限時間のルールに従って 1 回再送し、それでもだめならそのターンは時計のイベントだけをコミットし、`playthrough_metrics` に数える（backend-design 2.4 の縮退）。このカードで作るのは実行時の半分だけで、提供時の半分はコードの分岐とテストに書いておき、正式なゲートウェイがつながるのを待つ。
5. **Caps for the two ledgers**: add `ZJ_MAX_CLAUDE_USD` (total cap for the Claude ledger, required with real models, no default); `zoujin-s2` gains `--max-claude-usd`.
   **2 冊の台帳の上限**：`ZJ_MAX_CLAUDE_USD`（Claude の台帳の全体の上限。本物のモデルを使うときは必須で、既定値はない）を加える。`zoujin-s2` に `--max-claude-usd` を加える。
6. **Replays**: keys gain the provider, and CI replays (`fixtures/model-replays/`) are re-recorded with the fake model; E-0 snapshots where only IDs and the model name in `checker` change are handled by the usual rule (differences in IDs alone are not committed).
   **リプレイ**：キーに provider を加え、CI のリプレイ（`fixtures/model-replays/`）は偽モデルで録り直す。E-0 のスナップショットで ID と `checker` 内のモデル名だけが変わる場合は決まりどおりに扱う（ID だけの差はコミットしない）。
7. **Completing the cost accounting** (raised by Data in the #76 review): money already spent on a turn retracted within the window (the `Gone` path) and on resends after failures is currently not recorded in `playthrough_metrics`, so per-playthrough cost and the "economy" tier undercount. While touching cost in this card, add them, and include every prompt kind's `cost_*_usd`.
   **費用の記録漏れを補う**（データが #76 のレビューで指摘）：猶予時間内に取り消されたターンですでに使った費用（`Gone` の経路）と、失敗後に再送した分は、今 `playthrough_metrics` に記録されておらず、1 プレイの費用と「節約」の段階が少なく見積もられる。このカードで費用を扱うついでに補い、各プロンプト種別の `cost_*_usd` をすべて含める。
8. **Probe command** `zoujin-probe`: from the requests recorded from E-0 slice cases under the fake model (never touching holdout samples), take 20 per prompt kind, call the real models serially on the Mac, and measure first-token and total p50 and p95, plus input, cached, output and thinking tokens. The result file has only numbers and stores no request or response text.
   **小規模計測のコマンド** `zoujin-probe`：E-0 のスライスのケースを偽モデルで動かして記録したリクエスト（ホールドアウトサンプルには触れない）から、プロンプト種別ごとに 20 件を取り、Mac で本物のモデルを直列に呼び、最初の token と全体の p50、p95、さらに入力、キャッシュ、出力、思考の token を測る。結果ファイルは数値だけで、リクエストと応答の文言は保存しない。

## Risks / リスク

- **Check is slowest**: Sonnet with `medium` thinking may have a long tail that hits 15 seconds. If the Mac probe's p95 exceeds 12 seconds, lower effort first. (10-11 probe: p95 3.4 seconds, not hit.)
  **チェックが最も遅い**：Sonnet に `medium` の思考を加えると、長いテールが 15 秒に届くかもしれない。Mac での小規模計測で p95 が 12 秒を超えたら、まず effort を下げる。（10-11 の計測：p95 3.4 秒で、届かなかった。）
- **Overly complex Schemas sent to the API get rejected**: the end-of-act plan originally had 10 union types and got 400 on the first call; shrinking to 4 made it pass. A test caps it at the maximum that passed in the probe, 5 (`test_api_schemas_stay_as_small_as_what_passed`); new prompt kinds should be measured against this first.
  **API に送る Schema が複雑すぎると拒否される**：幕末のプランはもともと union 型が 10 個あり、最初の呼び出しで 400 が返った。4 個に減らすと通った。テストで、小規模計測で通った最大の 5 個に抑えている（`test_api_schemas_stay_as_small_as_what_passed`）。今後プロンプトの種類を増やすときは、まずこれに照らして測る。
- **Ending generation**: Sonnet writing about 3,000 tokens (including thinking) is estimated at 15–40 seconds, which the 10–20 seconds of ending staging cannot cover. This belongs to the ending card: generate in two passes (card face first, the rest filled in later), or stream the card face first. This card only sets the model.
  **エンディングの生成**：Sonnet が約 3,000 token（思考を含む）を書くと 15〜40 秒と推定され、10〜20 秒のエンディング演出ではカバーしきれない。これはエンディングのカードの担当：2 回に分けて生成する（カードの表面を先に出し、残りは後で補う）か、カードの表面を先にストリーミングで送る。このカードではモデルを決めるだけ。
- **Slow first Schema compilation**: each prompt kind's Schema takes a little longer on first use, then is cached for 24 hours. Warm up with one fake request per kind when the service starts; latency of an eval's first round is not counted.
  **Schema の初回のコンパイルが遅い**：各プロンプト種別の Schema は初回使用時に少し余計に待ち、その後 24 時間キャッシュされる。サービスの起動時に種類ごとに偽のリクエストを 1 回ずつ送って温めておく。評価の最初の 1 回の遅延は数えない。
- **Rate tier**: a new account's per-minute call and token limits are low. Development is all serial, which is enough; before R2 has many concurrent players, decide from measured concurrency whether to upgrade (upgrading costs money; ask zg).
  **レートのティア**：新しいアカウントの 1 分あたりの呼び出し回数と token の上限は低い。開発中はすべて直列なので足りる。R2 で多人数が同時にプレイする前に、実測の同時実行数を見てアップグレードするかを判断する（アップグレードには費用がかかるので zg に聞く）。
- **Prompts were written for Gemini**: this card does not change prompt wording, and version numbers stay the same; only the provider and model change. Tuning the check prompt on the Mac (the roughly $1 item in Z-8) now tunes it on Claude.
  **プロンプトは Gemini 向けに書かれている**：このカードではプロンプトの文言を変えず、バージョン番号も変わらない。プロバイダーとモデルを替えるだけ。Mac でのチェックのプロンプトの調整（Z-8 の約 1 ドルの項目）は、今は Claude で調整することになる。
