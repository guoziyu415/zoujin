## Goal / 目標

When this is done:

完了すると：

1. One conversational turn (a speech transcript, or one `text`) goes through the whole pipeline of backend-design 2.4: triage → extraction → deterministic rules → model check → rewrite, downgrade or reject → single-transaction commit. B-0's mapping table, which "only runs W-1's `check_effects` and provisionally maps to R rules by table", is replaced with the real R1–R7.
   会話の 1 ターン（音声の書き起こし、または `text` 1 件）が backend-design 2.4 のパイプラインを最後まで通る：トリアージ → 抽出 → 決定的ルール → モデルによるチェック → 書き換え・格下げ・却下 → 単一トランザクションのコミット。B-0 の「W-1 の `check_effects` だけを調べ、表で R ルールに仮に対応させる」対応表は、R1〜R7 の本体に置き換える。
2. The eval entry point's text mode works: `say` goes through the whole pipeline, `check` runs steps 3 and 4 (S-2 relies on it), and `advance`, `state()` and `events()` stay as before; it judges correctly on the slice world model (`ZJ_WORLD`) too.
   評価入口のテキストモードが使える：`say` はパイプライン全体を通り、`check` はステップ 3 と 4 を実行し（S-2 はこれに頼る）、`advance`、`state()`、`events()` は従来どおり。スライス版の世界モデル（`ZJ_WORLD`）でも正しく判定する。
3. The real-model client is written and runs only on zg's Mac (G-7): deadlines and resends, ledger and caps, stop on the first 429, record replays. Threads in the project and CI still use only the fake model and replays.
   本物のモデルのクライアントを書き、zg の Mac でのみ動かす（G-7）：締め切り時間と再送、台帳と上限、最初の 429 で停止、リプレイの記録。プロジェクト内のスレッドと CI は引き続き偽モデルとリプレイだけを使う。
4. The S-2 run script and report are written: the 10 public items run end to end in CI with the fake model and replays; on the Mac, the self-check prompt is tuned with the real model; once the prompt is final, Data runs the 50-item holdout set on the Mac with the same script.
   S-2 の実行スクリプトとレポートを書く：公開の 10 件は CI で偽モデルとリプレイを使って最後まで通る。Mac では本物のモデルで自己チェックのプロンプトを調整する。プロンプトが確定したら、データが同じスクリプトで 50 件のホールドアウトセットを Mac で実行する。

## Scope / 範囲

### In scope / やること

**1. Pipeline** (`narrator/`, built on B-0's job claiming and single-transaction commit) / **パイプライン**（`narrator/`。B-0 のジョブ取得と単一トランザクションのコミットの上に作る）

- **Step 0 interface**: turns carry screening flags (`injection`, `pii`, to be filled by Model Armor later), which step 3's R6 reads. In this card the gateway only fills empty flags; tests and fixtures can inject flags. The self-harm classifier v2 and Model Armor themselves belong to the safety card.
  **ステップ 0 のインターフェース**：ターンにスクリーニングのフラグ（`injection`、`pii`。後で Model Armor が埋める）を持たせ、ステップ 3 の R6 がそれを読む。このカードでは、ゲートウェイは空のフラグだけを入れる。テストと fixture ではフラグを入れられる。自傷分類器 v2 と Model Armor そのものは安全のカードで扱う。
- **Step 1 triage** (`triage`, flash-lite): whether this turn could change the world, form a promise, or state a new improvised detail. If not → write only one `say` event that advances the clock (`effects` empty, contract section 3), and go straight to step 7.
  **ステップ 1 トリアージ**（`triage`、flash-lite）：このターンが世界を変える、約束を結ぶ、新しい即興の設定を口にする可能性があるか。なければ → 時計を進める `say` イベントを 1 件だけ書き（`effects` は空、契約第 3 節）、ステップ 7 に直行する。
- **Step 2 extraction** (`extract`, flash, thinking LOW, structured output):
  **ステップ 2 抽出**（`extract`、flash、思考 LOW、構造化出力）：
  - Input: the world model prefix (placed first and unchanged, to benefit from implicit caching), the world state, and this turn (the utterance placed only in the `<utterance speaker="…">` data field).
    入力：世界モデルのプレフィックス（先頭に置き、内容を変えないので暗黙のキャッシュが効く）、世界の状態、このターン（発話そのものは `<utterance speaker="…">` のデータフィールドにだけ入れる）。
  - Output: 0–3 candidate events (a subset of the contract's Event, with `actor` per contract section 0; promises and improvised details are its `promise` and `improv` effects) and whether each candidate needs confirmation.
    出力：0〜3 件の候補イベント（契約の Event の部分集合。`actor` は契約第 0 節どおり。約束と即興の設定はその中の `promise`、`improv` 効果）と、各候補に確認が必要かどうか。
  - Output is validated against the Schema; failing the Schema counts as a failed call and is resent once per the "time limits" rule below.
    出力は Schema に通す。Schema を通らなければその呼び出しは失敗とし、下の「制限時間」のルールに従って 1 回だけ再送する。
- **Step 3 deterministic rules** (`narrator/rules.py`, no model calls): R1, R2, R3, R4, R7, plus the rule part of R6.
  **ステップ 3 決定的ルール**（`narrator/rules.py`。モデルは呼ばない）：R1、R2、R3、R4、R7 と R6 のルール部分。
  - **Whatever `judge()` can catch, step 3 must catch**: the judging must cover at least the table "minimal judging method for deterministic rules" in `evals/s2/README.md`.
    **`judge()` が止められるものは、すべてステップ 3 で止める**：判定は少なくとも `evals/s2/README.md` の「決定的ルールの最小の判定方法」の表をカバーする。
  - Plus what backend-design 2.4 says: R3 checks the schedule for characters who follow a schedule, and `places.adjacent` only measures the player's moves and `relocate` outside the schedule; the rule part of R6 checks every `summary` and improvised detail to be committed (patterns for phone, email, address; the step-0 flags; 8 consecutive characters identical to the player's utterance).
    さらに backend-design 2.4 に書かれていること：R3 はスケジュールで動く人物についてはスケジュールを見て、`places.adjacent` はプレイヤーの移動とスケジュール外の `relocate` だけを測る。R6 のルール部分は、コミットするすべての `summary` と即興の設定を調べる（電話、メール、住所のパターン。ステップ 0 のフラグ。プレイヤーの発話と 8 文字連続で同じ）。
  - World rules (condition evaluation, applying effects, schedules, `valueRequires`, `OCCURRED`) come only from W-1; the narrator does not keep a second copy. Primitives the judging needs that W-1 does not have yet (e.g. shortest distance by `adjacent`, whether someone knows a given fact at this moment) — first ask Data whether they should go into W-1: if yes, Data adds them and Backend reviews; if not, write them in `rules.py` and test them against `judge()`.
    世界のルール（条件の評価、効果の適用、スケジュール、`valueRequires`、`OCCURRED`）は W-1 からだけ取り、ナレーターの中に別のコピーを書かない。判定に必要で W-1 にまだないプリミティブ（例：`adjacent` による最短距離、ある人がこの時点である事実を知っているか）は、まず W-1 に入れるかをデータに聞く。入れるならデータが追加し、バックエンドがレビューする。入れないなら `rules.py` に書き、`judge()` と突き合わせてテストする。
  - Several candidates in the same turn are judged in order, with earlier passes tentatively applied to the state first (B-0 already does this).
    同じターンの複数の候補は順番に判定し、先に通ったものから仮に状態に反映する（B-0 ですでにそうなっている）。
- **Step 4 model check** (`check`, flash, thinking MEDIUM):
  **ステップ 4 モデルによるチェック**（`check`、flash、思考 MEDIUM）：
  - Scope per backend-design 2.4: all candidates that passed step 3 and have non-empty `effects`; a turn's candidates go in one call.
    範囲は backend-design 2.4 どおり：ステップ 3 を通り、`effects` が空でないすべての候補。1 ターンの候補は 1 回の呼び出しにまとめる。
  - Judges R1 anchor contradictions that exist only in text, R5 persona and motive, and the parts of R6 outside the rule part. Each rule gets `pass` / `fail` and a one-sentence reason in Japanese.
    文章にしか書かれていない R1 のアンカーとの矛盾、R5 のキャラクター設定と動機、R6 のルール部分以外の内容を判定する。各ルールに `pass` / `fail` と日本語の理由を一文付ける。
- **Step 5 rewrite, downgrade or reject** (`rewrite`, flash):
  **ステップ 5 書き換え・格下げ・却下**（`rewrite`、flash）：
  - Fails step 3 or 4 → rewrite with the failed rules and reasons, go back to step 3, at most 2 rewrites (`attempts` ≤ 3).
    ステップ 3 か 4 を通らない → 失敗したルールと理由を持たせて書き換え、ステップ 3 に戻る。書き換えは最大 2 回（`attempts` ≤ 3）。
  - Still fails → downgrade to a smaller impact if possible (`downgraded`, e.g. "persuade the bridegroom" → "the bridegroom begins to hesitate"), otherwise reject (`rejected`, the log entry has empty `effects`, contract section 3).
    それでも通らない → できれば小さな影響に格下げし（`downgraded`。例：「花婿を説得する」→「花婿が迷い始める」）、できなければ却下する（`rejected`。ログのその項目は `effects` が空、契約第 3 節）。
  - `check.reason` gets one sentence in Japanese. The smoothing-over hint written into the character's situation briefing belongs to the situation briefing card, which reads it from here.
    `check.reason` には日本語で一文を書く。人物の状況説明に書く取り繕いのヒントは状況説明のカードが扱い、ここから読む。
- **Step 6 intent confirmation** is not in this card (B-4, together with the gateway's `confirm`). In this card, candidates that extraction marked as needing confirmation and that are of the step-6 kind in 2.4 (making a beat `prevented` / `altered`, changing the hostage's or player's identity or situation) are handled as "not confirmed = no": discarded, no event written, no time spent (the same as no answer within 30 seconds). Recorded once in Trace and `playthrough_metrics`.
  **ステップ 6 意図確認**はこのカードの範囲外（B-4、ゲートウェイの `confirm` と一緒に行う）。このカードでは、抽出で確認が必要とされ、かつ 2.4 のステップ 6 に当たる種類のイベント（ビートを `prevented` / `altered` にする、人質やプレイヤーの身分・境遇を変える）の候補は、「確認なし = いいえ」として扱う：捨てて、イベントを書かず、時間も使わない（30 秒答えがないのと同じ）。Trace と `playthrough_metrics` に 1 回記録する。
- **Step 7 commit**: B-0's single-transaction commit. If `lastSeq` changed, restart from step 3 without re-extracting. The retraction window (3 seconds after `turn_complete`) belongs with retraction in B-4; this card does not wait before committing.
  **ステップ 7 コミット**：B-0 の単一トランザクションのコミットどおり。`lastSeq` が変わっていたらステップ 3 からやり直し、抽出はやり直さない。取り消しの猶予（`turn_complete` 後 3 秒）は取り消しと一緒に B-4 で扱い、このカードではコミット前に待たない。
- **Time limits** (backend-design 2.4):
  **制限時間**（backend-design 2.4）：
  - 15 seconds per call for extraction, check and rewrite; 5 seconds for triage 〔provisional; S-5 decides〕.
    抽出、チェック、書き換えは 1 回の呼び出しにつき 15 秒、トリアージは 5 秒〔暫定、S-5 で決める〕。
  - On timeout, cancel and resend immediately once.
    タイムアウトしたら取り消し、すぐに 1 回だけ再送する。
  - If the second attempt also times out: a triage timeout is treated as "possible" and extraction continues; for the others, this turn commits only the clock event, the candidates are discarded, and `playthrough_metrics` records it once.
    2 回目もタイムアウト：トリアージのタイムアウトは「可能性あり」とみなして抽出を続ける。それ以外は、このターンは時計のイベントだけをコミットし、候補は捨て、`playthrough_metrics` に 1 回記録する。
- **Character answers in text mode** (`reply`, flash): `text` turns and `eval_api.say` need the character's text answer.
  **テキストモードでの人物の返答**（`reply`、flash）：`text` のターンと `eval_api.say` には人物の文字での返答が必要。
  - This card uses parts 1, 2 and 4 of 2.3 (fixed rules, the persona trimmed to this moment, who the player is), plus a minimal situation briefing (time, place, who is present, facts known at this moment).
    このカードでは 2.3 の第 1、2、4 部（固定のルール、この時点に合わせて切り出したキャラクター設定、プレイヤーが誰か）に、最小限の状況説明（時刻、場所、その場にいる人、この時点で知っている事実）を加えて使う。
  - The full situation briefing, memory, smoothing-over hints and questions already asked in this playthrough are for later cards.
    完全な状況説明、記憶、取り繕いのヒント、このプレイですでにした質問は後続のカードで扱う。
  - Character answers in voice turns are still the fake Live.
    音声のターンでの人物の返答は引き続き偽 Live。

**2. Absent characters and the slice / その場にいない人物とスライス**

- Characters who are `absent` at this moment do not count as present, e.g. セリヌンティウス and フィロストラトス at the stone workshop in the slice (S-077 ⑩).
  この時点で `absent` の人物はその場にいるものとして数えない。例：スライスで石工房にいるセリヌンティウスとフィロストラトス（S-077 ⑩）。
  - Events that only hold if one is in the same place as them fail step 3 under R7.
    彼らと同じ場所にいなければ成り立たないイベントは、ステップ 3 で R7 により通らない。
  - They are still listed in snapshots, with `activity: "absent"` and `talkable: false`.
    スナップショットには従来どおり載せ、`activity: "absent"`、`talkable: false` とする。
- S-077 ② the player cannot be arrested: in the slice world model `var.player.custody` has no `arrested` value, so step 3 rejects it as an invalid value (R7), and the narrator writes no separate judgment. This card adds a test for it.
  S-077 ② プレイヤーは捕まらない：スライスの世界モデルでは `var.player.custody` に `arrested` という値がないので、ステップ 3 が不正な値として却下する（R7）。ナレーターは別の判断を書かない。このカードでテストを 1 件追加する。
- `ZJ_WORLD` (absolute path to world.json; E-0's runner sets it this way, and with `--slice` it is the slice version) is already wired up by B-0 (#26, added after Data's review): new playthroughs and `eval_api.setup()` use it, and when unset it is the full draft; existing playthroughs use the version locked at their start. This card only adds tests for the two items above on the slice version.
  `ZJ_WORLD`（world.json の絶対パス。E-0 のランナーがこのように設定し、`--slice` のときはスライス版）は B-0 ですでにつながっている（#26 でデータのレビューを受けて追加）：新しいプレイと `eval_api.setup()` はこれを使い、未設定なら完全版の草稿。既存のプレイは開始時に固定したバージョンを使う。このカードではスライス版について上の 2 項目のテストを足すだけ。

**3. Model interfaces and three implementations / モデルのインターフェースと 3 種類の実装**

- Prompt types `triage`, `extract`, `check`, `rewrite`, `reply`. Each has an output JSON Schema (backend-internal, not in the contract) and a version number (the hash of the prompt text, as in B-0). Examples in prompts are written by us.
  プロンプト種別 `triage`、`extract`、`check`、`rewrite`、`reply`。種別ごとに出力の JSON Schema（バックエンド内部のもので、契約には入れない）とバージョン番号（プロンプト本文のハッシュ。B-0 ですでにそうなっている）を持つ。プロンプト内の例は自分たちで書く。
- `ZJ_MODEL` accepts three values:
  `ZJ_MODEL` は三つの値を受け付ける：
  - `fake` (default): each prompt type has a fixed default output (triage = possible, extraction = no candidates, check = all pass, rewrite = unchanged, reply = one fixed line). `fixtures/fake-text/` overrides by condition and can inject latency and errors, to test time limits, resends and 429.
    `fake`（既定）：プロンプト種別ごとに決まった既定の出力がある（トリアージ = 可能性あり、抽出 = 候補なし、チェック = すべて合格、書き換え = そのまま、返答 = 決まった一言）。`fixtures/fake-text/` で条件ごとに上書きでき、遅延やエラーも注入できる。制限時間、再送、429 のテストに使う。
  - `replay`: as in B-0.
    `replay`：B-0 どおり。
  - `real`: Gemini on Vertex AI, using the application default credentials from gcloud login on the Mac, with no API key.
    `real`：Vertex AI 上の Gemini。Mac で gcloud にログインしたアプリケーションのデフォルト認証情報を使い、API Key は使わない。
    - The project ID and region are read only from explicitly set environment variables, and only in `real`; if unset, exit without sending a request. Never use a default project inferred by the SDK or application default credentials (the default gcloud configuration on the Mac is not this project's). The project ID never enters the repo, logs, Trace or replays.
      プロジェクト ID とリージョンは明示的に設定された環境変数からだけ、しかも `real` のときだけ読む。未設定なら終了し、リクエストは送らない。SDK やアプリケーションのデフォルト認証情報から推定される既定のプロジェクトは使わない（Mac の gcloud の既定の設定はこのプロジェクトのものではない）。プロジェクト ID はリポジトリ、ログ、Trace、リプレイに入れない。
    - The SDK goes into the optional dependency group `real` of `services/backend`. CI installs it only for type checks and network-free unit tests (with a fake transport layer), and never calls it.
      SDK は `services/backend` の任意の依存グループ `real` に入れる。CI では型チェックとネットワークなしの単体テスト（偽の通信層に差し替える）のためだけにインストールし、呼び出すことはない。

## Rules for holdout samples (S-2) / ホールドアウトサンプルの決まり（S-2）

- Until the self-check prompt is final, Backend does not read `data/evals/holdout/` in the project folder (including its README), and does not use holdout scenes as examples in prompts. Prompt tuning uses only the 10 public items and eval E4.
  自己チェックのプロンプトが確定するまで、バックエンドはプロジェクトフォルダーの `data/evals/holdout/`（その README も含む）を読まず、ホールドアウトサンプルの場面をプロンプトの例に使わない。プロンプトの調整には公開の 10 件と評価の E4 だけを使う。
- **Final** = Backend writes down the `check` prompt's version number in the code PR and notifies Data and PM. After that, Data runs the 50-item holdout set on the Mac with `zoujin-s2`, and the report goes to Data to check against the labels. The replays and `report.json` from this run stay with Data first (see "Recording replays" above); Backend only gets the summary numbers.
  **確定** = バックエンドがコード PR に `check` プロンプトのバージョン番号を書き、データと PM に知らせること。その後データが Mac で `zoujin-s2` を使って 50 件のホールドアウトセットを実行し、レポートはデータに渡してラベルと照合する。この回のリプレイと `report.json` はまずデータの手元に置き（上の「リプレイの記録」を参照）、バックエンドは集計した数値だけを受け取る。
- If the `check` prompt changes after it is final, this S-2 result no longer represents the new prompt, and Data needs to produce a new measurement set (`evals/s2/README.md`).
  確定後に `check` プロンプトを変えたら、今回の S-2 の結果は新しいプロンプトを表さなくなり、データが新しい計測セットを作る必要がある（`evals/s2/README.md`）。

## Prohibited / 禁止事項

- No deploying, no creating accounts or keys, no spending money zg has not approved. Real models only on the Mac, and only after PM's notice.
  デプロイしない。アカウントも Key も作らない。zg が承認していない費用は使わない。本物のモデルは Mac でのみ、PM の通知の後で。
- Credentials, project IDs, billing IDs and deployment URLs never go into the repo, docs, logs, replays or chat. The code reads the project ID from the Mac's environment only when `ZJ_MODEL=real`.
  認証情報、プロジェクト ID、請求先 ID、デプロイ先のアドレスはリポジトリ、ドキュメント、ログ、リプレイ、チャットに入れない。コードは `ZJ_MODEL=real` のときだけ Mac の環境からプロジェクト ID を読む。
- Logs and Trace never contain utterances, or summary and reason text; only IDs, counts and rule names (data-design section 8).
  ログと Trace には発話そのものも、要約や理由の文言も書かない。ID、回数、ルール名だけを書く（data-design 第 8 節）。
- Fixtures and replays contain only lines we wrote ourselves and synthetic inputs, never anything real people said.
  fixture とリプレイには自分たちで書いたセリフと合成の入力だけを入れ、実際の人が言ったことは入れない。
- Do not read the holdout samples (see above).
  ホールドアウトサンプルを読まない（上記を参照）。
- CI and containers never call real models; tests run with the network disabled.
  CI とコンテナでは本物のモデルを呼ばない。テストはネットワーク禁止で動かす。
