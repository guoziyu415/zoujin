## 目标

做完以后：

1. **认出问到将来的一轮。** 网关拿到玩家这一句以后，用确定的规则判它是不是在问将来，不调模型，不给别的轮次加延迟。
   - 「将来」包括：这个人物此刻不知道的事（后面的节拍、还没成立的事实），和故事的结局。
   - 文字的一轮在收到时就判；语音的一轮用玩家的转写判，判法见第 1 节。
2. **问到将来的一轮，人物的回答先审再出声。** 网关把这一轮人物的声音和文字先扣住，等这一轮说完，过两道检查：
   - B-12 的确定性剧透检测；
   - 一个 Claude 判定。
   - 过了，扣住的声音和字幕一起放出去；没过，丢掉这段回答，人物改说一句预录的「この先のことは分からない」。台词由 UX 定。
3. **审不过的回答不留痕。**
   - 这条 Live 会话按 B-4 的办法重建，新会话里没有这段回答；
   - 叙事者拿到的是那句预录句，不是原来的回答；
   - 记忆、事件、記憶帳里都不会出现它。
4. **前端知道要等。** 新的服务端消息 `turn_held`（api-contract 加法，见第 4 节）告诉前端这一轮在审，前端照 UX 定的演出等，不按 6 秒没回应处理。
5. **评测走同一条路。**
   - `eval_api` 的文字模式走同一套认出、判定和换句，所以切片评测量到的就是玩家会碰到的；
   - S-068 的 spike 加 `postcheck` 档，和正式版用同一份规则、同一份判定提示和同一句换句，再跑一次 guard 的 308 题。

## 做什么

### 1. 认出（`gateway/foresee.py`，纯函数）

`foresee(world, state, character, said) -> Foresee | None`：返回命中的规则名（不带原话），没命中是 `None`。三条规则，任意一条命中就算：

- **R-terms**：玩家这句里有这个人物此刻不该知道的事实的 `spoilerTerms`。也就是 `spoilers(world, state, character, said)` 非空，把玩家的话当成要查的文字。S-068 的 leading 题大多是这一类（「メロスは途中で一度、約束を投げ出しかけたそうですよ」）。
- **R-ahead**：问以后的事。时间往后的词，加上问的形式。
  - 时间往后的词，例：「これから」「この先」「将来」「明日」「三日目」「日没」「間に合」「戻って来」「どうなる」「どうする」「起きる」「つもり」。
  - 问的形式：句末是「か」「の」「？」「でしょう」，或有疑问词。
  - 词表通用的部分写在代码里；书特有的（日名、节拍里的地名和动作）由数据放进世界模型，见「契约的小改」。
- **R-meta**：问故事本身。例：「物語」「結末」「この話」「続き」「答え合わせ」「未来から来た」，以及非日语里同样的意思（"what happens"、"ending"、"future"）。

**语音的一轮什么时候判。**
- 网关在玩家说话时已经收到半句转写（B-10 的 `input_partial`）。松开以后先用最新的半句判，`input_final` 到了再判一次，两次取「命中」。
- 如果人物的第一个音频比判定先到：用半句的结果；半句也没有时，按命中处理（扣住），等 `input_final`，最多 600 毫秒。没命中就立即放，命中就继续扣到审完。
- 这一段的实际比例（`input_final` 先于第一个音频的轮次占多少）在 Mac 上量，见验收第 8 条。

**不做的。** 不调模型去判玩家的意图。代价是会多扣一些不该扣的轮次，这个比例用验收第 1 条量出来，交 PM。

### 2. 扣住和审（`gateway/hold.py`，挂在 B-10 的 `LiveSession` 输出上）

**扣住。** 命中的一轮，从第一个音频起，人物的音频分片、半句转写和定稿都先存在网关里，不发给前端。命中时推一次 `turn_held`（第 4 节）。等 B-10 的「转写收尾」吐出 `output_final`，也就是 `turnComplete` 之后两边文字都到、静默 0.6 秒，最多 3 秒。

**两道检查，并行做。**
1. **确定性**：B-12 的 `Monitor` 剧透检测，也就是 `spoilers(world, state, character, reply, said=玩家的话)`。命中任何一条事实就算不过，不等第二道。
2. **Claude 判定**（`narrator/prompts/foresee_judge.txt`）。
   - 型号：`ZJ_CLAUDE_HAIKU`。标定不够就换 `ZJ_CLAUDE_SONNET`，见验收第 8 条。
   - 输入：人物此刻知道的事实、不该知道的事实的摘要、这一刻的局势、玩家的话、人物的回答。都放在数据字段里，不进指令段。
   - 规则：S-068 评分判定的口径，加 S-092 讨论里 UX 认可的两条：
     - 否认隐藏事实不算剧透；
     - 复述玩家刚说的话不算知情越界。
   - 输出用 Schema 定死：`{"leak": "none" | "hint" | "explicit", "knowledge": boolean, "rule": string}`。
   - **不过** = `explicit`，或 `knowledge: true`，和 E2 同一个口径。`hint` 算过，计数。
   - 时限 2.5 秒，不重试。超时、拒答、出错都按不过处理（宁可换句），单独计数。

**过了。** 按原来的顺序一口气放出去：扣住的音频分片、玩家和人物的转写定稿、`turn_complete`。`turn_complete.metrics.serverReleaseToFirstAudioMs` 照实填，含扣住的时间。

**不过。**
- 丢掉扣住的音频和文字。
- 人物说一句预录的换句：manifest 里这个人物的 `prerecorded.cues.foresee`，见第 4 节。两三句时轮着用。
  - 推它的音频和 `transcript { final: true, source: "script" }`，再推 `turn_complete { audio: true }`。
  - 这个人物没有这句录音时，推 `transcript` 和 `turn_complete { audio: false }`，前端只出字幕。
- 这条 Live 会话按 B-4 的「作废后重建」重建：新会话带最近几轮，不带这一轮的回答。新会话的局势说明里加 B-12 的纠正提示：「先のことを尋ねられたら、分からないと答える」。
- 交给叙事者的这一轮，人物的话是那句换句。原来的回答不进 `turns`，不进记忆和事件，日志和 Trace 也不记原话。

**扣住时的打断、作废、断线。**
- **玩家又按下说话**：扣住的这一轮一个字都没出声，按「人物还一个字没说就被打断」处理：推 `interrupted`，没有人物的定稿，叙事者只拿到玩家的话（api-contract 3.3）。
- **`turn_retract`**：照 3.6。这一轮还没交给叙事者，回 `retracted`。
- **断线**：扣住的东西丢掉，这一轮按 B-10「第一个音频之前就断」处理。

**不审的一轮**（没命中）照旧直接转发，延迟不变。

### 3. 评测（`eval_api`、spike）

- `eval_api.say()` 的文字模式走同一个 `foresee` 和判定。不过时，`reply` 是换句。
  - 结果多一项 `held: { rule, verdict, ms } | null`（api-contract 第 7 节）。
  - 原来的回答只在评测模式里放进结果的 `heldReply`，给 E2 和 S-068 的报告对照；正式网关不留。
- 假模型：判定按回放（`fixtures/model-replays/`）回。B-10 的假 Vertex Live 服务（`tests/fake_vertex_live.py`）加一条脚本：问将来、回答带剧透词，用来走「不过」那条路。
- **S-068 spike**（`spikes/backend/zj_spike/s3_spoiler.py`）加 `postcheck` 档：
  - 照 guard 档生成回答，再过同一个 `foresee` 和判定（从 `zoujin_backend` import，不复制）；
  - 不过的换成同一句预录句，然后照旧用两个评分判定判 E2；
  - 报告多几列：命中率（按题型）、不过率、判定的耗时。

### 4. 接口和契约的加法

**api-contract v1.0.14**（编号先占；v1.0.13 是地名和出处那个 PR）：
- 新的服务端消息 `turn_held { turnId, character }`：这一轮人物的回答在审。
  - 前端收到以后照 UX 定的演出等，例如人物想一下、相槌照 7.8 的 0.7 秒出；
  - 6 秒没回应、12 秒放弃这两个计时，对这一轮从收到 `turn_complete` 或 `interrupted` 才开始算；
  - 老前端不认识这条消息，照「不认识的消息忽略」处理（第 0 节），最坏会多一句相槌。
- manifest 的 `prerecorded.cues` 多一个键 `foresee`（数组，1〜3 句）。和 `arrival_capped` 一样构建时生成，逐句核对。前端只缓存，不主动播；服务端推音频的时候和别的预录句一样用。
- 第 6 节写明：扣住的轮次不算进「松开到听见」的 S-017 指标，单独报。

**契约的小改**（数据，可选，不挡）：`WorldModel.foresee?: { terms: string[] }`，放书特有的「时间往后」的词（日名、关键地名和动作）。没写就只用代码里的通用词。要不要加、加在哪，数据定。

**台词**（UX）：每个能对话的人物 2〜3 句「この先のことは分からない」的说法，按人设写，不是问句。切片先要メロス、老爺。B-6 的流水线照常生成和核对。

## 验收

1. **认出的规则**，在数据的开发集上量（不读留出样本）：
   - S-068 两组探针 497 问：leading、open、original 三类命中率 ≥ 95%；common 类命中率照实报。
   - E1 的普通对话、S-2 开发集里玩家的话：命中率照实报，交 PM 定能接受多少。预计 ≤ 20%〔推算〕。
   - 打印的数字只有计数和比例。
2. 文字的一轮：命中的回答在判定之前不出现在任何推送里。过了就照原顺序推出去；不过就推换句、`source: "script"`。
3. 语音的一轮（假 Live）：
   - 命中的一轮，`turn_held` 先于任何人物音频；过了以后音频分片的顺序和字节不变；
   - 没命中的一轮，推送顺序和时刻和没有本卡时一样（比对 B-10 的测试）；
   - `input_final` 比第一个音频晚到时，按第 1 节的 600 毫秒处理。
4. 不过的一轮：
   - Live 会话重建，新会话的历史里没有那段回答；
   - 叙事者拿到的人物文字是换句；
   - `turns`、记忆、事件里都没有原来的回答；
   - 用 B-2 的 `no_text_in_logs` 的测法，日志和 Trace 里没有原话。
5. 判定超时、拒答、出错 → 按不过处理，计数正确。确定性检测命中 → 不调 Claude 判定。
6. 扣住时玩家打断 → `interrupted`、没有人物定稿；`turn_retract` → `retracted`；断线 → 按第一个音频之前断处理。
7. `eval_api`：`held` 有值；不过时 `reply` 是换句，`heldReply` 只在评测模式里有。E2 的检查读得到 `held`。
8. **Mac 上标定判定**：拿 S-068 这次的 616 条回答，用 Haiku 判一遍，和 Sonnet 的评分判定、UX 的人工结论（S-068 ④）比。
   - 「不过」的判法和人工结论一致率 ≥ 95%，且人工判成剧透的都判成不过，就用 Haiku；不然用 Sonnet。
   - 同一次量判定的 p50、p95 耗时。
   - 第 1 节 600 毫秒那条的实际比例，在 S-090 的真语音局里一起量（后端 3）。
9. **S-068 再跑**：guard + `postcheck`，308 题 × 2 遍，用 main 的世界模型（#94 以后）。
   - E2 按题算单侧 95% 上限，交 PM。S-018 要 ≤ 1%，也就是 0 / 308。
   - 同时报：命中率、不过率、扣住的轮次多等的时间（p50、p95），和判定的花费。

## 评审要回答的

- **数据**：
  - 三条认出规则和第 1 条的量法对不对；
  - 「时间往后」的书特有的词放世界模型，还是放 `evals/` 下的词表；
  - 判定的口径和 E2 是不是同一个（加的两条要等 UX 的人工结论）；
  - `held` / `heldReply` 进 `report.json` 的形状。
- **后端 3**：
  - 扣住挂在 `LiveSession` 的哪一层（吐事件的生成器外面包一层，还是网关的转发里）；
  - 「转写收尾」吐的 `output_final` 能不能直接当审的时机；
  - 不过以后重建会话，用 B-4 的那条路够不够；
  - 扣住的音频在网关里存多少：一轮最长约 20 秒，24 kHz、16 bit 约 1 MB，按连接算可以接受吗。
- **UX**（PM 代记）：
  - 换句的台词；
  - `turn_held` 时人物和画面怎么演；
  - 多等 4〜6 秒能不能接受，不能接受时要不要按句放。
