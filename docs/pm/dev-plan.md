## 2. 开发阶段怎么协作

### 2.1 仓库

一个私有仓库，单仓多包：

```
apps/web/                前端（Vite + React + R3F，frontend-design 第 3 节）
services/backend/        后端：一个 Python 包、一个镜像、两个入口
                           gateway（鉴权、REST、WebSocket、Live 代理、安全筛查、预算；Cloud Run，公开）
                           narrator（叙事者流水线、世界推进、记忆、结局；Cloud Run，仅内部）
                           mock（B-1，按 api-contract 回消息，给前端开发用）
packages/contracts/      schemas/data（数据说了算）、schemas/api（后端）；前后端的类型都从这里生成
packages/worldsim/       共享规则库（Python，移植 data/spikes/pipeline/worldsim.py）
worlds/hashire-merosu/   世界模型
evals/                   评测集、画像、运行器
fixtures/                假 Live 的句子、假文本模型的输出、录好的模型回放、mock 剧本（三方共用）
assets/pipeline/         Blender 和 gltf-transform 脚本
assets/manifest/         每个源素材的网址、授权、sha256
assets/budgets.json      frontend-design 10.6.2 的预算数字，CI 读它
infra/                   Terraform（只写不跑；部署逐次问 zg）
docs/                    设计文档、决定、任务卡（docs/tasks/）
```

- **后端栈**：Python 3.13 + uv + FastAPI + pydantic v2 + SQLAlchemy 2 + Alembic，和 spikes、worldsim、评测同一种语言。gateway 和 narrator 合成一个包，是因为 `eval_api` 要在一个进程里调两边的逻辑，两边共用一套表和迁移，也不会版本不一致；部署时仍是两个 Cloud Run 服务。
- **Cloud Run 的服务名会出现在地址里**，部署时用中性名字（zg：「对外的一定不能暴露信息，名字等等」）；仓库里的包名不受影响。
- **文档迁移**：R-0 把六份设计文档、PRD、decisions、open-questions、数据契约、api-contract、世界模型、评测集原样搬进仓库。以后只在仓库里改，走 PR。项目文件夹里的旧副本头一行写「已迁到仓库，以仓库为准」，不再改。评审记录、交接、核对报告这类过程文件留在项目文件夹。Schema 的位置统一成 `packages/contracts/schemas/{data,api}`，C-1 顺手改文档里的两处旧写法。
- **留出样本用过之前不进仓库**：仓库对所有写提示的线程可见，放进去就不再是留出。新的留出样本先放项目文件夹 `data/evals/holdout/`，用过一次再搬进仓库。项目文件夹各线程其实也读得到，所以这道隔离靠约定：写叙事者提示的后端线程不读 `holdout/`，数据不在 README、评审记录和消息里写留出样本的内容。
- **美术大文件**（A-0 量完定稿）：
  - GitHub 个人免费账号的 LFS 是每月 10 GiB 存储 + 10 GiB 流量，Actions 检出 LFS 也算流量；预算设 0 美元时超额只会挡到下个月，不扣钱。
  - CC0 源素材（扫描材质、MPFB 素材、动作捕捉）不进仓库，脚本按 `assets/manifest/` 下载并核对 sha256。
  - 生成的 glb、ktx2、导航网格不进仓库，只进清单（大小和 sha256），CI 和部署构建时现场生成（S-075：项目线程的容器推不了 LFS）。手工改过的 .blend（A-0 真梅洛斯）怎么进仓库，做好时 PM 问 zg。
  - 预录音频（B-6）没法现场生成，但很小（切片 19 条约 0.2〜0.3 MB〔推算〕），走普通 git，不进 LFS（S-084）；`check_large_files.py` 的 1 MB 照旧管着。
  - CI 只在改了流水线或场景时现场生成，生成两次、比两份清单是否一致；仓库里的清单只查预算、颜色档和位置点。
  - 估算（原来按进 LFS 算的）：一版生成物约 115 MB，留 20 版历史约 2〜3 GB，在 10 GiB 内。以后要改回 LFS 时再用。
- **不进仓库的**：部署地址、项目 ID、账单 ID、密钥、测试码、邀请码（README 部署规范）。CI 加一道扫描。

### 2.2 任务卡

大块编码写成任务卡，放 `docs/tasks/<阶段>/<编号>.md`。一张卡是一个线程能做完、开成一个 PR、能单独评审的量；太大就拆成几个 PR，卡里写明先后。卡的格式：

- **目标**：做完以后能看到什么。
- **依据**：引用哪份文档的哪一节、哪个版本。
- **范围**：做什么、明确不做什么。
- **接口**：输入输出用 `packages/contracts` 里的哪个 Schema。
- **验收**：要跑的命令、要过的测试、要达到的数字。
- **禁止**：不部署、不碰密钥、不调真模型、不花钱。
- **评审**：哪两个角色。

**谁写卡**：负责那部分的角色写，PM 对照 PRD 看一遍。**谁执行**：写卡的角色在自己的线程里做（第 4 节「写卡」那一列；R-0 由 PM 做）：在分支上写代码、本地跑过 CI 要的检查、开 PR，再请卡上写的两个评审角色看。zg 不用开会话（D-023）。一个角色同时只做一张写代码的卡，按依赖顺序排；排在后面的卡挡住别人时，PM 请协调为那张卡另开一个线程，同一个角色、读同样的文档。小改动和修复照旧由角色线程直接做。

### 2.3 评审和合并

- 每个 PR：CI 全绿 + **两个角色评审**。配对照设计阶段：
  - 前端的 PR 由 UX（界面）或后端（接口）看。界面 PR 的评审是 M2 里 UX 最大的一块工作。
  - 后端的由前端或数据看；数据的由后端看。
  - 改 `packages/contracts` 的要后端、前端、数据三方都看。
  - 碰到 PRD 验收数字的，PM 也看。
- **合并**（zg 10-10 允许，D-024）：PR 最新的提交上 CI 全绿，卡上写的两个角色都在这个提交上评审通过（改契约的三方都要，碰 PRD 数字的加 PM），也没有没处理的「要改」，写卡的角色线程就把 PR 合进 main（squash），不用等 zg。main 不等于上线，花钱和部署照旧逐次问 zg。
  - 所有线程在 GitHub 上是同一个身份，用不了 GitHub 的「批准」（作者不能批准自己的 PR）。评审写成 PR 评论，第一行固定是「评审通过 · <角色> · <提交前 7 位>」或「要改 · <角色>」。评审之后又推了提交，评审人在新提交上再确认一行。
  - GitHub 免费版的私有仓库开不了分支保护（GitHub 文档：私有仓库要 Pro 或团队版），所以这道门靠合并的线程自己查。仓库设成只能 squash 合并、合并后删分支；zg 的账号开得了分支保护的话，再给 main 加「必须过 CI」「不许强推和删除」。
- 争议照设计阶段的规则：3 轮还没定，PM 定；产品问题经 PM 问 zg。

### 2.4 CI（不花钱、不调真模型）

- 格式、类型检查、单元测试。CI 起 PostgreSQL 服务容器（B-0 的单事务和并发测试要真库）。
- **测试禁网**：pytest 拦截 socket，只放行本机，保证 CI 和项目里的线程碰不到真模型。
- 契约测试：前后端的消息都按 Schema 校验；mock 服务和真服务回同一套 Schema；`world.json` 和种子里的 `events` 也按 Schema 校验。
- 世界模型：`build_world` 校验 0 错误；`scenarios.json` 的 23 个情景加原作（什么都不做）共 24 次推演，全部推演出预期结局（E5 的确定性部分）；`check_evals`、`check_probes` 0 错误。
- **生成物一致**：C-1 的类型、`world.json`、`report.md`、`REVIEW.md`、评测种子、探针、安全样本，用各自的生成器重跑后 git diff 必须为空，手改过就红。
- 评测的确定性部分（E7 全部、各套件里不需要模型的检查），用录好的模型回放跑。**回放会过期**：提示一改，回放就对不上，CI 报「回放过期」，不算通过（回放按模型、提示版本、请求哈希存）。
- 前端预算：打包体积、每个场景的资产大小和 draw call 读 `assets/budgets.json`，超了就红。
- 秘密扫描：gitleaks 加自定义规则（run.app 地址、项目 ID 和账单 ID 的样子、邀请码格式）。
- **Actions 免费分钟有限**（私有仓库 GitHub Free 约每月 2,000 分钟，以 GitHub 当时的页面为准）：只用 Linux runner、按路径过滤、缓存依赖、同分支新提交取消旧的。Actions 和 LFS 的花费上限都保持 0 美元，超了就停，不扣钱（建仓库时请 zg 确认这两个设置）。

### 2.5 真模型在哪调

凭证只在 zg 的 Mac 上（G-7）：Gemini 用 gcloud 登录，没有 API Key；Claude 的 Key zg 10-11 已建好，只存在 Mac 的钥匙串（S-079 ⑤）。所以：

- 项目里的线程和 CI 用假 Live（前端 S2 已有）、假文本模型（对任何请求都给确定的回答）和录好的回放。
- 需要真模型的（叙事者调提示、S-2、S-5、评测的模型部分、模拟局），由负责的角色写好脚本和预算，经协调交 Mac 跑：
  - **Mac 直接从仓库拉到指定的提交**，不再打 zip、不再经协调贴文件和 sha。Mac 只读仓库；要 Mac 推分支开 PR，得 zg 另外同意 Mac 用他的 GitHub 账号推送（第 7 节，真要时再问）。
  - **长任务和 Mac 上的 Claude 会话脱钩**：单独的终端窗口或 nohup，加 `caffeinate -i`。S-068 停在 143/616，就是进程跟着断线的会话一起停了。
  - 每个脚本都要：`--resume`、单项上限加总账本（按供应商分 Google 和 Claude 两本，两个上限，任一到了就停，S-079）、串行、第一个 429 就停（Claude 的 529 也是）、先打印预计花费和命令给 zg 看。
  - 原始输出留在 Mac 的 `out/`，不进仓库；脱敏汇总照旧经协调回负责的角色。
  - **要模型的评测，每次调完提示跑的那一遍顺带重录回放**，给 CI 用。
  - **录回放只用合成输入**（AI 玩家、评测用例），不录真人玩家的话；脱敏后再进仓库。
- 跑长任务前先和 zg 确认 Mac 开着。
- 开发期模型花费的上限要 zg 定（第 7 节 Z-8）。除了 Gemini Live 的语音对话和预录句，用模型的地方都用 Claude，不做两家对比（D-028）：叙事者的文字各步、地の文、幕末打算、安全分类、记忆摘要、结局文字等（清单以 B-8 卡为准），加上评测的评审员和模拟局的 AI 玩家。评测文字模式里替 Live 当人物的 `reply` 留在 Google，Model Armor 照旧当第二层（S-085）。
