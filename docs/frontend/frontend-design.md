## 0. 一页摘要

**结论先行**

1. **技术栈**：Vite 8 + TypeScript + React 19（React Compiler）+ three.js r186 + React Three Fiber 9 + zustand。所有日文文字都放在 DOM 层，不画进 WebGL。
2. **渲染器先不定死**：WebGPU 分块比 WebGL 大 140KB（brotli）〔实测〕，WebGPU 在 iPhone 上只有 iOS 26 才有，手机上也不一定更快。用 S1 真机数据决定：如果 iPhone 上 WebGPU 的 p95 帧时间不比 WebGL2 好 10% 以上，就用 WebGLRenderer。
3. **语音按住说话（push-to-talk）**，关掉服务端自动语音检测，由前端发「开始说 / 说完」信号。好处：不会把角色的声音录回去，不会误录，轮次清楚，省钱。角色说话时再按下就是打断：前端立刻停播放，同时通知服务端。
4. **前端不直连 Gemini**：麦克风音频经 WebSocket 发给后端（Cloud Run）代理，角色语音和字幕原路返回。后端能看到每一句，才能做注入过滤、日志、预算和叙事者判定（决定 A-004）。
5. **世界状态以服务端为准**：前端只渲染服务端推来的投影（时钟、角色在哪做什么、事件、记忆），不在前端拼故事逻辑。前端自己决定的只有：玩家走路、动画、镜头、界面反馈。
6. **性能预算写成数字并进 CI**（第 10 节）。最大的风险不在三角形数，在 draw call：S1 里 13 个示例机器人 + 阴影就有约 340 个 draw call〔实测〕，所以角色资产必须是「1 个蒙皮网格、≤ 2 个材质」。

**已对齐**：UX（`ux-design.md`，最初 v0.1 时的前端评审见 `frontend/reviews/ux-v0.1.md`）：竖屏优先、横屏可用；点地面走、点角色自动走近并开始对话、「近くの人」列表，摇杆只在设置里；进入对话时拿麦克风（暂定，S2 验证）；语音状态和等待阶梯按 UX；原型的 21 个状态作为画面依据。后端：一条 WebSocket（音频二进制、其余 JSON）；客户端拿不到任何 Google 令牌；一次只和一个角色对话；静态资源和 API 同源；邀请码登录 + Cookie（S-020）；「言い直す」的规则；事件只给玩家可见的部分；幕和时钟由叙事者推进（S-021）。接口以 `backend/api-contract.md` 为准（第 14 节）。PM：性能和语音验收数字（S-014、S-015、S-017）；存档续玩是 P0，切后台、页面被回收后回到同一刻（S-024，见 9.5）；语音和文字是平等的两个入口，识别文字可以一键改正（S-025）；结局卡可保存为图片，分享链接是 P1（S-026）；角色会自己走动、去找别人、走过来搭话（D-013、S-030，见 8.6，可行，帧时间代价约 1〜2ms）。

**v1.0 时的状态（详见第 15、16 节）**

- 语音：S-1b 在 zg 的 iPhone、4G 下测过，松手到听见中位 1031ms、p95 1342ms，打断在按下当时停播（S-073，7.7）。没量到的（蓝牙耳机和外放分开、麦克风每轮开关 F-3、小声说话、切后台 1 分钟、LINE）等下一次本来就要部署时补，公开上线前必须有数字；F-3 在那之前按 UX 7.2 暂定。
- 写实画风的档位已定（D-019，zg 2026-10-06）：档 B 为底（iPhone 12，单场景 ≤ 10MB、首次进入 ≤ 10 秒，效果全开），强机自动升到档 C 的效果。规格、两档的下载预算、升降档规则见 10.6.1〜10.6.3。S7 两次实测：zg 的 17 Pro Max 上所有配置一帧 GPU 1〜4ms，iPhone 12〔推算〕4〜10ms。
- 接口：前端提的要求后端全部采纳，以 api-contract v0.3.6 为准（第 14 节）；遥测以 data-design 9.3（1.2）为准（第 11 节）；字幕来源和出戏卡的收尾按 ux-design 7.7、14.1（7.5、第 12 节）。
- 还开着、不挡开发的：mock 和 JSON Schema（开发阶段和后端一起对）、LINE 的票据接口、S1 渲染器选择（WebGPU / WebGL2，要 zg 跑一次 S1）、S4 字幕性能、S5 发热、S6 续玩。

## 1. 范围与前提

- 只做网页，手机浏览器优先（D-008）；质量第一（D-009），不参加 10/15 黑客松（D-010）。
- 第一版内容：4 个可走动场景（S-001）、3 个身份（S-002）、7 个可对话角色（S-003）、四幕结构（S-004）、故事时间按行动消耗（S-005）、日语界面（S-008）。
- 前端负责：3D 世界（移动、镜头、角色、互动点）、语音采集和播放、字幕、全部界面（对话、连锁反应地图、記憶帳、结局卡）、加载与性能、前端可观测。
- 前端不负责：故事判定、记忆生成、结局推导（后端叙事者），世界模型（数据）。前端不保存玩家原话以外的任何故事状态。

## 3. 技术选型

| 层 | 选择 | 理由 | 放弃的方案 |
|---|---|---|---|
| 构建 | **Vite 8**（Rolldown） | 构建快 10–30 倍；内置 tsconfig paths；Vite 8.3.3 已实际跑通本项目依赖〔实测〕 | webpack：慢，配置重 |
| 语言 | TypeScript（strict） | 契约多（data/contracts.md、api-contract），类型直接从 JSON Schema 生成 | — |
| UI | **React 19 + React Compiler 1.0** | 界面多（对话、地图、記憶帳、结局卡），React 生态成熟；Compiler 自动 memo。外壳只有 58KB（brotli）〔实测〕 | Svelte/Solid：更小，但 3D 生态（R3F）和团队熟悉度不如 React |
| 3D | **three.js r186 + React Three Fiber 9** | three.js 生态最大（周下载约 Babylon 的 39 倍）；R3F 让 3D 场景和界面共享同一份状态 | Babylon.js、PlayCanvas：包更大或更偏引擎，和 React 结合弱 |
| 渲染器 | **WebGPURenderer 或 WebGLRenderer，S1 真机决定**〔待真机〕 | WebGPURenderer 没有 WebGPU 时自动回退 WebGL2，一套代码；但 3D 分块 349KB vs 209KB（brotli），要多解析约 690KB JS〔实测〕；r186 下官方迁移指南也说部分场景 WebGL 更快。为了切换成本低：只用标准材质和少量自定义着色，不依赖只有一边能用的后处理 | — |
| 状态 | **zustand**（游戏/界面状态）+ **TanStack Query**（REST 数据：記憶帳、结局、清单） | zustand 能在 R3F 渲染循环外直接读写，不触发 React 重渲染；TanStack Query 管缓存、重试、失效 | Redux：样板多；XState：只给语音状态机用（见 7.6） |
| 路由 | 轻量路由（≤ 5KB） | 只有 4 个屏幕，但结局卡要能用链接直达 | 大型路由框架 |
| 文字 | **全部 DOM**（字幕、对话、地图、記憶帳、结局卡） | 日文字形多，WebGL 里要做 SDF 字库（几 MB）；DOM 天然支持 `<ruby>`（ふりがな P1）、读屏、复制、系统字体 | troika-three-text 等 WebGL 文字 |
| 字体 | 正文用系统日文字体（Hiragino / Noto Sans JP）；标题和故事文字用一款明朝体，经 Google Fonts 按 unicode-range 分片只下用到的字 | 日文字体完整版 5〜20MB，不能整包下 | 自托管完整字体 |
| 3D 资产 | Blender → glTF → **gltf-transform**：几何 **meshopt**，贴图 **KTX2**（颜色 ETC1S，法线 UASTC） | meshopt 实测 464KB → 183KB〔实测〕；KTX2 在显存里保持压缩，WebP 解码后按 RGBA 全尺寸占显存（原项目用 WebP 省了下载但没省显存） | Draco：解码器大、慢；WebP 贴图：显存不省 |
| 移动与碰撞 | 每个场景在 Blender 里烘一张导航网格（navmesh），前端做寻路和贴地 | 不需要物理引擎（Rapier wasm 约 1MB+）；角色只走路，不需要刚体 | 物理引擎 |
| 音频 | Web Audio + **AudioWorklet**（采集重采样、播放缓冲），无第三方库 | 低延迟、可控、可打断 | MediaRecorder：只能出压缩分片，延迟高；`<audio>` 流：打断和衔接差 |
| 网络 | REST（一次性读写）+ **一条 WebSocket**（实时：语音、字幕、世界推送），和后端已对齐 | 见第 9、14 节 | WebRTC：Artifact 和部分 App 内浏览器不支持，服务端也更复杂 |
| 可观测 | `web-vitals/attribution` + Long Animation Frames + 自定义指标（帧时间、语音延迟），批量发后端 | 见第 11 节 | 第三方 RUM 脚本（INP 杀手、隐私） |
| 离线缓存 | **Service Worker** 预缓存带 hash 的静态资源（3D 分块、当前和下一个场景、字体分片）；API 不缓存 | 页面被回收后重开不用再下 4MB 场景（S-024）。注意 Safari 对 7 天没访问的站点会清掉脚本可写的存储，缓存没了就退回网络下载 | 只靠 HTTP 缓存：内存紧张时也会被清 |
| 托管 | 静态资源和 API **同源**：外部负载均衡 + Cloud CDN，静态资源放 Cloud Storage，`/v1/*` 转发到 Cloud Run（Q-B7，和后端已对齐）。文件名带 hash、长缓存、预压缩 br；`index.html` 不缓存 | 同源才能用 Cookie 鉴权；避开原项目 no-store、不压缩的坑。部署先得到 zg 同意 | Firebase Hosting（和 API 不同源） |

## 4. 架构

```
┌──────────────────────── 浏览器 ────────────────────────┐
│  屏幕：封面 → 选身份 → 世界 → 结局                     │
│  ┌─────────── DOM 层（React）───────────┐              │
│  │ 字幕/对话 · 说话按钮 · 时钟 · 连锁反应 │              │
│  │ 記憶帳 · 结局卡 · 设置 · 错误与等待    │              │
│  └───────────────▲──────────────────────┘              │
│  ┌──────────── 3D 层（R3F）──────────────┐             │
│  │ 场景 · 角色 · 玩家 · 镜头 · 互动点     │             │
│  └───────────────▲──────────────────────┘              │
│          zustand：world / player / voice / ui           │
│  ┌────────┐  ┌──────────────┐  ┌──────────┐            │
│  │ 网络层  │  │ 音频引擎      │  │ 遥测      │            │
│  │REST+WS │  │Worklet 采集/播放│ │指标批量上报│            │
│  └───┬────┘  └──────┬───────┘  └────┬─────┘            │
└──────┼──────────────┼───────────────┼──────────────────┘
       ▼              ▼               ▼
   后端 API      后端语音代理       后端遥测接口
 （Cloud Run）  （→ Gemini Live）
```

原则：

- **服务端权威**：世界时钟、角色位置和活动、事件、记忆、结局都以服务端推送为准；前端只做表现（插值、动画、寻路）。
- **乐观只用在不影响故事的地方**：玩家走路、按钮按下态、字幕逐字出现可以立即反应；「这件事算不算发生」永远等服务端。
- **3D 层不碰网络**：3D 组件只读 zustand；网络层收到消息后写 zustand。这样 3D 部分可以单独做性能测试。
- **一切等待都有状态**：网络层和音频引擎的每个状态都暴露给 UI（第 7.6 节），UX 为每个状态出画面。

## 7. 语音链路

### 7.1 一轮对话

消息名和字段以 `backend/api-contract.md` 3.2〜3.5 为准。

```
玩家走到某个可对话角色 8m 内 → near(character)（只对最近的一个角色发；离开 12m 才发 far，避免在边界来回切）
   ← session_preparing { etaMs } … 服务端预热这个角色的 Live 会话
玩家点这个角色 → 立刻发 focus(character)，同时玩家自动走过去（1〜3 秒）；已授权麦克风时在这一下拿麦克风并静音待用（F-3 暂定，7.4）
   ← session_ready（预热命中时几乎立即；没命中 ≤ 1 秒，走路时间盖住）
   会话没好玩家就开口：前端本地缓存最多 2 秒音频，session_ready 后一次发出；超过 2 秒显示「準備中」
玩家按下「話す」
   → 立即：按钮按下态 + 角色转头看玩家（100ms 内）
   → activity_start { turnId, turnSeq }；麦克风音频以 16kHz PCM、40ms 一帧连续上传
玩家松开
   → activity_end；300ms 内出现「考えている」等待演出（S-017）
   ← transcript（玩家，final）、角色音频（24kHz PCM，带 turnSeq）、transcript（角色，按句）
   → 收到第一个音频包即开始播放；嘴型跟音量动
   ← turn_complete { metrics.serverReleaseToFirstAudioMs }
   … 「言い直す」窗口到这一轮的 `turn_settled` 为止（约 3〜5 秒，就是叙事者判定的时间；不阻塞对话，玩家可以接着说，api-contract 3.6）
   ← `commit`（事件、`patch`、记忆、约定、关键时刻一次原子地到）/ `turn_settled`（每轮判完都推，api-contract 3.4）
离开对话 → unfocus
```

**打字和说话平等（S-025）**：输入框任何时候都在说话按钮旁边。发出一句文字 = 一轮（`text { turnId, turnSeq, text }`，≤ 200 字），之后的流程和语音一样（角色仍用声音回答并出字幕）；角色说话时发文字也是打断。麦克风被拒、App 内浏览器、环境嘈杂时，界面自然以输入框为主，不弹「请改用文字」之类的提示。玩家不说话时，界面也不催（角色不催由后端负责）。

### 7.2 采集

- `getUserMedia({ audio: { echoCancellation: true, noiseSuppression: true, autoGainControl: true, channelCount: 1 } })`。
- 一个 `AudioContext`（设备原生采样率，iPhone 通常 48kHz），AudioWorklet 里降采样到 16kHz、转 16-bit PCM 小端，按 40ms 一包发出（Gemini Live 原生输入就是 16kHz PCM；其他采样率它也会重采样，但多发三倍流量没有意义）。
- 采样率转换在 Worklet 里做，不建第二个不同采样率的 AudioContext（不同采样率节点互连在部分浏览器会报错）。
- 只在按住期间发送音频；松开后立刻停止上传。不在前端保存任何录音。
- 按住期间玩家自己的识别文字实时显示（S-025），需要服务端在说话过程中就推玩家的 `transcript`（`final: false`），不只在松手后推定稿（api-contract 3.3 已定；S-1b 实测松手后第一段中位 344ms）。

### 7.3 播放

- 角色语音 24kHz PCM 分片 → 播放 Worklet 的环形缓冲（重采样到设备采样率）→ 输出。起播前攒 60〜100ms 抗网络抖动（S2 调参）。
- 打断：角色说话时玩家按下，前端**本地立即清空播放缓冲**（≤ 50ms 静音），同时发 `activity_start`；服务端取消这一轮生成（Gemini Live 收到新输入会丢弃正在生成的回答）。下行音频帧带 `turnSeq`，打断后还在路上的旧音频包按 turnSeq 直接丢弃。验收标准是 0.2 秒内停（S-014、S-017）。
- 嘴型：播放 Worklet 每 20ms 回传一次音量包络，驱动角色下颌骨或嘴型 morph。Live API 不给音素时间轴，第一版不做精确口型。

### 7.5 字幕

- 开启 Live API 的输入、输出转写，字幕跟着流式出现；玩家自己的识别结果也显示，识别错了玩家能看见。
- 角色字幕**跟着声音的进度出**，不提前出全句（UX 7.7，不剧透下半句）：每收到一段角色转写，记下当时播放缓冲排到的位置，播放走到那里才显示这一段。粒度是转写分片（几个字），不是逐字高亮。最多同时 2 行，停留到下一句或玩家点击。
- **字幕从哪来（S-071，ux-design 7.7，api-contract 3.3 的 `source`）**：每轮人物恰好有一条定稿 `transcript { final: true, source }`。
  - `live`（几乎全部）：照上一条跟声音的分片出；定稿到了，替换这一轮已经出的部分，不重新播出现动画。
  - `script`（原作里固定的台词、预录台词）：现在全部是预录（构建时生成，S-071 ②），manifest 里每句是 `{ url, text, durationMs }`（api-contract 2.1），不等转写。在「、」「。」处分段，第 k 段在播放走到「前 k 段字数 / 总字数 × 音频长度」时出，不提前出全句。原作原文标「原作のことば」（有 `Cite` 时），相槌不标。以后如果有服务端经 WebSocket 推的固定台词，`source: script` 的定稿会在第一个音频包之前到（api-contract 3.3）；音频总长在 `turn_complete` 前取「已收到的音频长度」和「字数 ÷ 每秒 6 字」里大的那个。
  - `fallback`（补转写，约 1% 以下）：整句一次出，人物名那一行右边标「書き起こし」：和「原作のことば」同一个位置、同样式（界面黑体 11px、`ink-2`），不加框、不能点；读屏先读「書き起こし」再读句子。两个标不会同时出现。
  - 声音播完还没收到定稿：文字行出灰色「……」（`ink-2`，静止的，不是思考时跳动的三个点）。收到 `{final: true, text: null}` 时改成「（字幕を出せませんでした）」，不让人物重说。保险：`turn_complete` 后 8 秒还没有定稿（消息丢了），也按 `text: null` 处理。
  - 玩家已经按下说话键或发出文字以后才到的定稿，不插回字幕区（只换掉本地记录里这一轮的文字）。
- 原生语音模型直接听音频，屏幕上的识别文字来自另一路转写，文字错了不代表角色听错了。界面文案不要暗示「以字幕为准」（后端评审第 7 条）。
- 作废一轮只用一个消息 `turn_retract`（api-contract 3.6），UX 提的 `turn_cancel` 不另加：思考中（人物还没开口）点「取り消す」= 打断 + `turn_retract`；按下不到 250ms 的误触、上滑取消、12 秒没回应作废也都发 `turn_retract`。按钮文字：人物还没开口时叫「取り消す」，已经回答之后叫「言い直す」（已定，F-23）。
- 「言い直す」（UX 提议，后端已确认可行）：
  - 含义是「打断角色、玩家重说、这一轮作废」，不是按文字改正。服务端重建这个人物的语音会话，新会话里没有这一轮，人物是真的没听到（api-contract 3.6 第 2 条）；重建约 1 秒，期间玩家照样能按下说话（前端最多缓存 2 秒音频）。按钮名字只看人物开没开口：还没开口叫「取り消す」，回答之后叫「言い直す」。
  - 按钮在 `turn_complete` 后出现，收到这一轮的 `turn_settled` 就收起（之后不能再作废，不再按固定 5 秒，api-contract 3.4）。
  - 点下：角色还在说就先本地停播，发 `turn_retract { turnId }`，回到可以说话的状态。
  - 太晚（叙事者已提交）时服务端回 `turn_retract_result { status: "too_late" }`：不播声音，前端自己从文案表出一行叙事（地の文）「……もう伝わってしまった。」（ux-design 7.6，api-contract v0.3.8；和 `narration` 同样式，服务端不另发字幕），世界里的结果不撤销。
- **识别文字一键改正（S-025、UX 7.6）**：松手后玩家自己的字幕可以点一下，弹出预填好识别结果的输入框，改完发送。在作废窗口内（这一轮还没在世界里生效之前）= `turn_retract` + 改好的文字作为新的一轮，叙事者只看到改对的那句；窗口外 = 只发新的一轮。送回模型的方式已定（api-contract 3.6）：窗口内发 `turn_retract` 作废原来这一轮，再发 `text { via: "correction", replaces }` 作为新的一轮，服务端重建会话，叙事者只看到改正后的话。超出窗口就不能改正，按钮收起。
- ふりがな（F-11，UX 13）：第一版给专有名词和难读词（邪智暴虐、身代わり等）注音，每个场景第一次出现时加。做法：manifest 带一个小词表（几十个词和读音，读音来自世界模型，内容请数据工程出），前端在字幕里做最长匹配，每个场景第一次出现时包 `<ruby>`；不需要分词器，也不需要后端给每句加标注。全部汉字的注音开关是 P1。
- 原作原文照搬的句子右上标「原作のことば」，点开看出处（UX 7.7，数据的 `Cite`）。

### 7.6 语音状态机（名字和画面按 UX 7.4）

| 状态 | 什么时候 | 前端要做的 |
|---|---|---|
| `mic-unknown` | 还没问过麦克风 | 正常对话；说话键显示「押して話す」 |
| `primer` | 第一次按说话键 | 显示麦克风说明（UX 7.3）；玩家点「マイクを使う」时在这一下点击里 `getUserMedia`，点「文字で話す」则说话键换成键盘键。这一次按下不录音 |
| `denied` / `unavailable` | 被拒、没有设备、App 内浏览器、audiomxd 故障 | 说话键换成键盘键；输入框成为主入口；出错文案按 UX 第 12 节 |
| `preparing` | `session_preparing`（换人、记忆删除后重建、重连，通常 ≤ 1 秒） | 人物转身、吸气；按钮可按，按下先本地缓存 ≤ 2 秒音频；超过 2 秒显示「準備中」 |
| `idle` | 轮到玩家说 | 字幕停在人物最后一句；人物等待的小动作 |
| `listening` | 按住中 | 「聞いています」，外圈随音量；自己的话实时出现在字幕区；上滑 60px 变「指を離すと取り消し」 |
| `thinking` | 松手后、人物还没出声 | 等待阶梯（7.8）；可以再按（= 打断式重说） |
| `speaking` | 人物出声 | 字幕跟声音进度出；嘴型；按下即打断 |
| `interrupted` | 玩家打断了人物 | 本地 ≤ 50ms 停播，字幕断处加「——」，进入 `listening` |
| `cancelled` | 上滑取消、误触、思考中点「取り消す」 | 自己那行字幕变淡、划掉；发 `turn_retract`；回到 `idle` |
| `no-response` | 6 秒没有声音，或服务端告诉前端这一轮不会有声音 | 出候选「もう一度話す」「文字で送る」；12 秒时作废（`turn_retract`）并播这个人物预录的「听不清」第 1 句（ux-design 16.2，api-contract 3.6 第 5 条） |
| `confirming` | 服务端发来意图确认（`confirm`，UX U-4） | 人物反问，下方二选一按钮发 `confirm_answer`；玩家用声音回答时照常发一轮语音，由后端判断 |
| `degraded` | 收到 `degraded` | 说话键换成键盘键，字幕代替声音，告诉玩家现在是文字 |
| `paused` | 收到 `safety_pause`（S-043、S-069） | 人物声音 0.2 秒淡出、丢掉没播的；压暗后出全屏出戏卡；说话键不可用。步骤见第 12 节 |
| `reconnecting` | 网络断开 | 顶部「つながり直しています」；场景照常能走；说话键不可用 |
| `suspended` | 切到后台回来，声音需要一次点击才能恢复（9.5） | 「タップして続ける」 |

输入框不属于这个状态机：除了 `reconnecting` 期间先暂存、连上再发，任何状态下都能打字；打开键盘不打断人物，发出文字才打断。

### 7.7 延迟预算（松手到角色出声：验收线 p50 ≤ 1.8s、目标 1.5s，p95 ≤ 3s，S-017）

| 段 | 预算 | 负责 |
|---|---|---|
| 前端发出最后一包 + `activity_end` | ≤ 50ms（〔实测〕按下到第一包上行中位 7ms、最大 21ms） | 前端 |
| 手机 → Cloud Run（东京）| ≤ 50ms（4G）（〔实测〕往返中位 91ms、32〜387ms，单程约一半） | 后端 |
| 网关 → Gemini Live（只有美国、欧洲端点）→ 第一个音频包 | 目标中位数 ≤ 1.2〜1.3s（〔实测〕代理松手到首音中位 924ms、p95 1081ms） | 后端 |
| 第一个音频包 → 出声（抖动缓冲） | ≤ 120ms；跨太平洋抖动大时缓冲在 60〜150ms 间自适应（〔实测〕中位 0ms、最大 62ms，测试页没有加缓冲，30 轮里没有断音记录） | 前端 |

前端上报 `clientReleaseToAudibleMs`，和 `turn_complete.metrics.serverReleaseToFirstAudioMs` 按 `turnId` 对齐，能看出慢在哪一段。

**S-1b 实测（2026-10-07，zg 的 iPhone、Safari、4G，S2 测试页）**：端到端中位 1031ms，大头是模型首音（约 0.9s），4G 只占约 0.1s，前端两段加起来不到 30ms。打断：按下当时就本地停播（7 次都在按下的同一帧），服务端 34〜49ms 确认。所以正式版的等待演出（7.8）主要是盖住模型那 1 秒，不是网络。

**被打断的那一轮也要记**：S2 测试页在「服务端已经说完、手机还在播」时被打断的那一轮没有记录（S-1b 第 11、19、26 轮），因为记录要等播放结束，按下时又清空了播放。正式客户端在按下打断的那一刻就结算上一轮：发 `talk_turn`（`interrupted: true`，`clientReleaseToAudibleMs` 照常带），不等播放结束，也不等它的 `turn_complete`。测试页已按这个改好（`spikes/s2-voice/README.md`）。

### 7.8 等待阶梯（UX 7.5，S-017 的具体做法）

| 松开后 | 发生什么 | 前端怎么做 |
|---|---|---|
| 0〜0.2 秒 | 人物抬眼、轻轻点头 | 本地动画，松手的同一帧开始 |
| ≤ 0.3 秒 | 头上「…」，说话键变「考えています」 | 本地（S-017） |
| 0.7 秒仍无声音 | 播这个人物的一句预录相槌（≤ 0.5 秒），同一局不连续用同一句，最多每两轮一次 | 场景加载时把在场人物的预录音频下载并解码好（每人相槌 3 句、听不清 2 句、等一下 1 句，AAC，URL 来自 manifest，后端用同一声音预生成）；真回答到了要等相槌播完（最多晚 0.5 秒） |
| 3 秒 | 思考的动作 | 本地动画 |
| 6 秒 | 候选「もう一度話す」「文字で送る」 | 进 `no-response`；服务端如果提前告诉这一轮不会有声音，就立刻进 |
| 12 秒 | 这一轮作废，不花故事时间，人物用预录的话接住 | 发 `turn_retract`，播这个人物预录的「听不清」第 1 句（每个人物不同，见 ux-design 16.2；例：老爺「……すまぬ、耳が遠うてな。」） |

遥测同时记「第一个音频包到达」和「真正出声」，相槌造成的延迟单独看得出来。

## 8. 3D 世界

### 8.1 场景 ID（`Place.sceneRef`，数据工程已写进世界模型 1.0.0-draft.2）

| sceneId | 场景（S-001） | 包含的地点（以 `world.json` 为准） |
|---|---|---|
| `scene.syracuse-square` | 锡拉库萨的大路与广场；第 3 天日落时同一场景换布景变刑场 | `place.syracuse-square`、`place.stonemason-workshop`（石工的仕事场，广场一角）、`place.execution-ground` |
| `scene.castle-throne` | 王城·王座之间 | `place.castle` |
| `scene.village` | 梅洛斯的村子（家、羊舍、花婿家、婚礼） | `place.village`、`place.melos-home`、`place.groom-house` |
| `scene.homeward-road` | 归途：河与桥、山口、草原和泉水、往城里的野路 | `place.river`、`place.mountain-pass`、`place.spring`、`place.road-to-city` |
| （第一版不做） | — | `place.neighbor-village`（`sceneRef` 为空：玩家不能停留，经过或在那里发生的事由叙事者用一两句旁白交代，前端显示字幕并播旁白音） |

一个场景里有多个地点。服务端说角色在哪个 `place` 的哪个 `spot`（位置点名），前端在场景文件里查到坐标。位置点不叫 `anchor`，因为世界模型里 `anchors` 是「故事锚点」（R1），见前端评审第 2 条。

### 8.2 场景加载

- 每个场景一个 glTF（meshopt + KTX2）+ 一个 navmesh + 一个位置点表（spots：门口、喷泉边、王座前……，由美术在 Blender 里放空物体导出）+ 地点边界（哪块区域属于哪个 `place`，用来判断玩家跨地点，见 9.4）。
- 加载顺序：先能走（地面、碰撞、低模远景）→ 再补细节（道具、高清贴图）。
- 预加载：选身份时预载起点场景；幕末选择去处时预载下一幕场景；同一时刻最多保留 2 个场景在显存里。
- 加载期间先 `compileAsync(scene, camera)` 预编译着色器，避免进场后第一次看到物体时卡顿。

### 8.3 角色

- 资产预算（交给 UX/美术）：每个角色 **1 个蒙皮网格、≤ 2 个材质、≤ 8k 三角形（主要角色可到 12k）、≤ 60 根骨骼、1 张 1024 KTX2 贴图**。理由：S1 里由 13 个子网格组成的示例机器人，13 个 + 阴影就有约 340 个 draw call〔实测〕。
- **写实画风（D-016、D-019）下，上面这条是走动版（LOD1）的预算**；可对话的角色另做对话版（LOD0）：标准档 2〜3 万面、4〜5 个材质、52 个表情形变 + 口型，下载 ≤ 4MB，同一时间最多 2 个；高档 4 万面、皮肤（含脸）2048 贴图、其余 1024，下载 ≤ 6.5MB，最多 4 个。美术按高档做，再减出标准档和走动版。规格和下载预算见 10.6.2。
- 动画：idle / walk / talk / 少量情绪动作（点头、摇头、惊讶、坐下）。共用一套骨架，动画可以跨角色复用。
- 远处角色降低动画更新频率，画面外的角色不更新动画。
- 角色在哪、在做什么由服务端推（`characters[id].place/spot/activity`）；怎么走过去由前端寻路。

### 8.6 角色自己走动（D-013、S-030）

角色在玩家面前会自己走动、去找别人、主动走过来搭话。**结论：可行，前端代价不大**：7 个角色同时走动，底线机每帧多约 1〜2ms（估算，S1 真机数据核实），在 33ms 的预算里。前提是角色资产守住 8.3 的预算。

**两种走动，分开处理**

| | 故事走动 | 表演走动 |
|---|---|---|
| 谁决定 | 服务端（叙事者的 `commit.patch.characters` 改了角色的 `place` / `spot`） | 前端自己 |
| 例子 | メロス 冲出广场；セリヌンティウス 被带去王城；老人走到喷泉边找年轻人 | 在自己的位置点附近踱步、转身、看向走过的玩家、和旁边的人「说话」的动作 |
| 有没有故事意义 | 有，算数 | 没有，只是让世界看起来活着 |
| 为什么需要 | 故事变化要看得见 | 时钟不随真实时间走（S-021），玩家不开口时世界不会推进；没有表演走动，角色就像站桩 |

表演走动只在角色当前地点的一个小范围里，不会走进别的地点，也不会走到玩家身边去，避免玩家误以为发生了什么。

**故事走动怎么演**

1. 收到 `commit.patch` 里某个角色的新 `spot`：在导航网格上从他现在的位置算路径（A* + 拉直，一次不到 1ms），按 `activity` 用走或跑的速度沿路径移动；行走动画的播放速度跟移动速度匹配（不滑步），转向按最大角速度平滑转过去，到了切成新的 `activity`（idle、work……）。
2. 目标地点在别的场景（例：离开广场去王城）：走到场景出口的位置点（`way.*`，美术在场景里放，对应世界模型 `adjacent`；不用 `exit.`，那是世界模型 `ExitId` 的前缀），然后淡出。从别的场景进来的角色在入口出现再走进来。
3. 去找另一个角色：走到对方旁边，两人面对面，播「说话」动作，第一版没有声音。**如果这次交谈在故事里算事件、而且对玩家可见**（contracts 2.6：玩家在场），玩家在 8m 内时显示一行灰色的旁白式字幕，内容取事件的 `summary`（例：「（メロスが老爺に、王のことを尋ねている）」），不另外生成台词、没有额外成本；真的出声（`npc_line`）是 P1（UX 评审）。
4. 走在路上被玩家点了：前端让他停下、转向玩家。这次对话在故事里算在玩家所在的地点（api-contract 3.8）。

**走过来搭话怎么演**

1. 服务端推 `approach`（这个角色要来找玩家），前端让他走向玩家**当前**的位置（玩家位置只有前端知道），玩家移动超过 1m 就重新算路。
2. 玩家正在和别人说话时，他停在约 4m 外看着这边等，不打断；**最多等 20 秒**，之后回到附近的位置点做自己的事，玩家结束对话（`unfocus`）后他再走过来一次（UX 评审、S-044）。
3. 他从画面外过来时：画面边缘出现一张纸色、墨色字的小纸条，写名字和朝向箭头（「← セリヌンティウス」，不用红色，只给 `approach` 用，其他角色走动不出提示）；脚步声和第一声招呼（「おい、旅の方！」）用 Web Audio 的立体声定位，**招呼同时出字幕**，听不见的人也知道有人来了（UX 评审）。
4. 走到约 2.5m 内：面对玩家，前端发「已经到了」的信号，服务端这时才让角色开口（不然声音会在他还在 20m 外时就开始）。镜头切到对话构图；玩家可以直接回答，也可以走开（发 `approach_dismiss { reason: "walked_away" }`；`far` 只管预热），或者点候选「いまは、いい」表示不理（`approach_dismiss { reason: "dismissed" }`，api-contract 3.10）（窄的地方如王座之间不容易走到 12m 外）；选了就当作不理，这一幕不再为同一件事来找（S-044）。
5. 角色先开口这一轮的 turnSeq 由服务端分配，需要和前端分配的分开（见第 14 节第 12 条）。

**性能和代价**

| 项 | 7 个角色同时走动时 | 说明 |
|---|---|---|
| CPU：动画混合 | 约 0.5〜1ms / 帧（底线机，估算） | 每个角色约 60 根骨骼、两段动画交叉淡入淡出；25m 外降到 15 次/秒更新，画面外只更新位置不更新动画 |
| CPU：寻路、避让 | 约 0.1ms / 帧 | 只在目标改变时算路径；角色之间用简单的分离力避免重叠（≤ 12 个角色，两两比较 144 次），不需要导航群体库（recast 的 wasm 约几百 KB） |
| GPU：蒙皮和阴影 | 7 × 8k 三角形 × 2（含阴影）≈ 11 万三角形，28 个 draw call | 在 300k 三角形、120 draw call 的预算内 |
| 网络 | 几乎为零 | 故事走动只在叙事者提交时推；表演走动在前端 |
| 包体积 | 寻路约 10KB；没有新的 wasm | — |

S1 测试页里的「路人 6 / 12 / 24 人闲逛」测的正是这件事（示例机器人比正式角色多 6 倍 draw call，结果偏保守）。判断规则：iPhone 上 12 人闲逛 + 阴影在预算内，7 个角色自己走动就没有问题；如果超了，先砍阴影（低画质用圆形假阴影）和远处动画频率，不砍角色。

**美术和 UX 要多准备的**

- 动画：除了 idle / walk / talk，加 run（メロス 赶路）、原地转身、招手 / 呼喊（走过来搭话）、头部看向目标（用骨骼朝向，不用 IK 库）。共用骨架，动画跨角色复用。
- 场景：出口位置点 `way.*`；每个角色常待位置点附近的表演走动范围。
- UX（已回答，见上面各条）：走过来的提示、对话中别人等的样子、两个角色交谈时玩家能看到多少。玩家不在时发生的事放在幕切换的「その頃」里（最多 3 件，优先级：和玩家的约定 > keyMoment > 其他，`SonoKoro` 组件）；内容范围由 UX 和数据定（contracts 2.8）。

### 8.4 镜头与操作（已和 UX 对齐）

- 竖屏优先，横屏也支持。界面是 CSS 布局，3D 按宽高比调视野和镜头距离（竖屏视野窄，镜头拉远补）。主要成本是测试量翻倍。
- 移动：**点地面 = 走过去；点角色 = 自动走近、面对他并开始对话**，单手能玩。虚拟摇杆不默认显示，作为设置项。寻路在导航网格上做 A*，一次不到 1ms，不需要物理引擎。美术交场景时要同时交导航网格、位置点（空物体）和地点边界。
- 镜头：平时第三人称跟随，拖动画面转视角；对话时自动切过肩镜头，把对方框在画面里，结束后回到跟随。性能开销可以忽略；要处理镜头穿墙（王座之间、屋内），用简化碰撞网格做射线检测，被挡时拉近，拉得太近、脸会被裁掉时改成正面单人镜头。
- 对话构图（UX 评审）：竖屏时人物在画面上三分之一，玩家背影在左下前景、只露肩膀，不挡人物的脸，字幕和输入区占下方约 40%；横屏时人物在右三分之一，玩家背影在左下，字幕在下方居中、限宽 640px。
- 键盘：WASD / 方向键移动，空格按住说话。

### 8.5 光照与时钟

- 故事时间驱动太阳角度和天色，**天色跟当天的时段走**（UX 评审）：每一天都有早晨和傍晚，各时段的光按 art-direction 第 4 节；第四幕跟梅洛斯走的归途从三日目・昼前开始，连续走过「雨后的昼前 → 午後的烈日 → 斜陽」，回到广场是日没（UX art-direction 3.1、3.5）。紧迫感主要靠太阳带和第四幕的天色，不靠「离期限越近越红」。
- 写实画风下，光照怎么随时段变（烘焙和实时的分工、每个时段的代价）见 10.6。S7 的广场资产（场景、天空、光照流程）直接给 M2 垂直切片用（S-050：同一个广场兼做结局的刑场）。
- 阴影：只有一盏方向光投影，阴影贴图跟着玩家走（S1 的做法）；低画质改成角色脚下的圆形假阴影。

## 9. 和服务端的同步

### 9.1 通道

- **REST**：登录、读 manifest、开局、读快照、补拉事件、「なぜこうなった？」、記憶帳、删记忆、结局、删除整局、上报遥测。会改数据的请求带 `Idempotency-Key`（同一次用户操作的重试用同一个 key）和 `Content-Type: application/json`。
- **WebSocket（一条，按局建立）**：JSON 控制消息 + 二进制音频帧。握手靠同源 Cookie，服务端校验 `Origin`，前端不持有任何令牌。断线后按 1、2、4、8 秒退避重连，发 `hello { lastSeq }`，服务端补发之后的事件；收到 `goaway` 就在 `reconnectAfterMs` 后主动重连；重连后重新 `focus` 当前角色，正在说的那一轮可能丢失，提示「もう一度話しかけてください」。关闭码（`4001` 未登录、`4004` 局已删除、`4009` 别的标签页打开了同一局……）的处理见 api-contract 第 4 节；`4009` 时显示「別のタブで開かれています」和「ここで続ける」。

### 9.2 事件在前端的样子

- 前端只拿已提交事件的**玩家可见投影**（api-contract 2.4；哪些变化可见按 contracts 2.6：改的是标为对玩家可见的变量或节拍走向，而且玩家当时在场或者是玩家自己做的；文字来自世界模型的 `valueLabels`）：`eventId, seq, turnId, t, dt, tLabel, type, actor, forPlayer, place, summary, causes, visibleEffects（每条带可直接显示的 label）, promise, keyMoment, supersedes`。隐藏状态可能是剧透，前端只按 `visibleEffects` 渲染，不从其他字段推断。被否决的候选事件不推给前端（只在调试模式）。
- 一局只有一个 `seq` 序列。按 `seq` 有序应用；不连续时用 `GET /events?afterSeq=` 补拉，再不行取快照，不靠前端猜。
- 一次叙事者提交在前端要一次应用完（事件、世界变化、记忆、连锁反应），不出现「事件说梅洛斯走了，人还站着」的中间状态。已定：合成一条 `commit`，带 `fromSeq`〜`seq`，前端一次应用（api-contract 3.4）。
- 玩家不在场时发生的变化不实时显示，留到幕切换时的「その頃」回顾（contracts 2.8.1），由 UX 定演出，前端在幕切换的过场里显示。
- `type=correction`：用 `supersedes` 找到被修正的那一条，更新对应的轻量反馈；角色下一句话会在故事里圆回来（后端负责）。

### 9.3 世界时钟与幕

- 时钟只由事件推进（S-005、S-021），前端不自己走时间；收到 `commit.patch.clock` 时做 1〜2 秒的平滑动画（太阳移动、太阳带上的标记移动）；界面不显示刻数（S-037），第四幕的「日没まで、あと二時間ほど」按 UX 4.2 的规则生成，只精确到「ほど」。关键段可以加真实时间的压力演出，但不改世界状态。
- **动作按钮括号里的时间由前端生成**（ux-design 4.3，api-contract 2.3）：数据里的 `label` 只写动作本身。第一〜三幕用 `estimatedMinutes` 加「ほど」：「手伝う（15分ほど）」；第四幕带梅洛斯的动作用 `melosMinutes`（本局此刻的实际值）：正数「（30分遅れる）」，负数「（10分早まる）」，0 写「（変わらない）」且照常能点，null 时退回 `estimatedMinutes` 的写法。数字用半角，不用汉数字（「十分」会读成「じゅうぶん」）；60 分以上用「1時間」「1時間半」「2時間」。`melosInTime`（做了以后梅洛斯还赶不赶得上，ux-design 4.3）只在会翻转时显示，作为按钮的第二行小字（11px），不加图标、不弹确认：`forecast.beforeDeadline` 为 true 且 `melosInTime` 为 false 时写「日没に間に合わなくなる」，用緋（太阳带日没线的颜色）；`beforeDeadline` 为 false 且 `melosInTime` 为 true 时写「日没に間に合う」，用墨；其他情况没有第二行。读屏按一句读：「引き止める、30分遅れる、日没に間に合わなくなる」。路上二选一（`enRoute`）带这个字段时同样处理。
- **到达时刻封顶的提示**（S-066，api-contract 3.4）：`commit.cue = { kind: "arrival_capped", speaker, text }` 一局只出一次。speaker 是梅洛斯时播 manifest 里他的 `prerecorded.cues.arrival_capped`（2.1，场景加载时一起解码；他正在说话就等说完）并出字幕，speaker 为 null 时按叙事显示 text；同时太阳带上的菱形停在 17:30 的位置轻亮一下，只亮一次。断线补发的 commit 按 seq 只演一次。
- **路上的二选一**（ux-design 4.5，api-contract 3.11）：`act_ended.options[]` 里有的去处带 `enRoute { line, choices[{ index, label, afterLine }] }`。玩家选了这个去处以后，过场页先显示 line，再给两个按钮（按钮的括号按 `choices[].melosMinutes` 用上面同样的写法，例「急かす（40分早まる）」，0 写「（変わらない）」；最后一项照原作，为 null，不加括号）；这一页点别处不会过去，只能点按钮。选完马上显示那一项的 `afterLine`（null 就不加，不等服务端），发 `act_choose { clientMsgId, optionId, enRouteChoice }`；不选就往下走时不带 `enRouteChoice`（等于照原作）。选项上的 `tLabel` 只是不改节拍时的时刻，下一幕起点以 `act_transition.snapshot.clock` 为准。收到 `invalid_choice` 时幕末画面不变，按 `pending.actEnd` 重新显示；断线重连后 `pending.actEnd` 也带 enRoute。
- 第四幕的「先に走って知らせる」会让玩家先到刑场：场景要能从进城的路直接切到广场（S-050，广场兼做刑场），按幕末换场景的演出处理。
- 幕结束由叙事者决定：收到 `act_ended { options }` 才显示 `ActEndChoice`，玩家选一个去处，或者用说话 / 打字说出自己的打算（S-031，不限于给定去处）；叙事者按时间、地点、关系判断能不能成行，不能成行时在故事里说明原因，玩家再选。成行后等 `act_transition` 带来新的 `actId`、场景快照和「その頃」（api-contract 3.11）。前端不按刻数自己判断幕结束。幕开始时按 `Act.scenes`（这一幕可能用到的场景）预加载；`act_ended` 的选项就是世界模型的 `ActExit`（`optionId` = `exit.id`，去处地点的 `sceneRef` 就是要加载的场景），选项出现时把还没加载的去处场景补上；玩家说出的打算要去哪个场景，等叙事者结果出来再加载（场景切换演出盖住）。

### 9.4 玩家移动和服务端

- **同一场景里走路**：完全在前端，不发消息、不等服务端。
- **在同一场景里跨地点**（例：从大路走进石工的仕事场）：前端照常走过去，同时发 `action { kind: "move", target: place }`（例：`place.stonemason-workshop`），不等结果；如果服务端回 `action_result.status = refused`（例：门口被警吏拦住），播 `narration`，把玩家停在入口外。已建议后端在快照里直接标出哪些地点现在进不去，前端提前把路挡住（前端评审第 6 条）。
- **换场景**：只通过幕末 `act_choose`，或者场景出口的互动点（这时才「先判后演」，配过场演出）。
- 其他身体动作（递东西、拦路……）都是 `action`，先判后演；动作清单 `kind` 见 api-contract 3.8，带 `estimatedMinutes`。

### 9.5 切后台、页面被回收、关掉再来（S-024）

前提：故事状态全部在服务端，时钟不随真实时间走（S-021），所以离开多久都「回到同一刻」。前端要做的是：离开时干净地停下，回来时尽快接上。

**前端在本地存的东西**（`localStorage`，按 `playthroughId` 分开；读写都包 try/catch，读不到就用服务端的）：玩家在场景里的坐标和朝向、镜头角度、画质档、未发出的输入框草稿、设置。玩家在场景里的精确位置服务端没有（9.4），丢了就站到快照里的 `player.spot`。

**离开**（`visibilitychange` 变成 hidden，以及 `pagehide`；不用 `unload` / `beforeunload`，它们在 iOS 上不可靠，还会让页面进不了前进后退缓存）：

1. 正在按住说话：当作松开，发 `activity_end`；角色正在说：本地停播。
2. 停 3D 渲染循环；保存本地状态；用 `sendBeacon` 补发遥测。
3. `pagehide` 时主动关闭 WebSocket（有的浏览器有打开的 WebSocket 就不把页面放进前进后退缓存）。只是切后台（hidden）时不主动关，iOS 过一会儿会自己断，回来按断线处理。

**回来，页面还在**（`visibilitychange` 变成 visible，或 `pageshow` 且 `persisted`）：

1. WebSocket 断了就重连，发 `hello { lastSeq }`，服务端补发离开期间的事件（一般没有，因为时钟不走）。
2. iOS 回来后 AudioContext 通常处于暂停或中断状态，要一次点击才能恢复：显示 `ResumeGate`「タップして続ける」，这一下点击里 `resume()` AudioContext。
3. iOS 切后台会暂停或结束麦克风采集：回来检查音轨，不能用就在下一次按下说话时重新 `getUserMedia`（在按下的手势里做）。
4. WebGL 上下文可能被系统收回：监听 `webglcontextlost`（阻止默认行为）和 `webglcontextrestored`，恢复后重建渲染器、重新上传贴图（从 Service Worker 缓存读，不走网络）。
5. 离开时正在进行的那一轮可能丢了：人物在画面上时，播这个人物预录的「没听清」那句（例：「……ん、すまぬ。聞きそびれた。」），不用系统文字（UX 评审）；断网超过 30 秒时照常显示横幅。`welcome.lastTurn { turnId, character, status, playerText, characterText }` 带回最后一轮的状态和定稿字幕，前端把字幕补回来；`status: "lost"` 时按上面播「没听清」（api-contract 第 4 节）。

**回来，页面已被系统回收，或者关掉后改天再来**（等于重新打开）：

1. 外壳从 Service Worker 缓存秒开 → `GET /v1/me`（Cookie 还在就不用重新登录；建议有效期 30 天滑动续期）。
2. 有进行中的局：封面直接显示「続きから」（`/v1/me.activePlaythrough`，api-contract 第 1 节）。
3. 玩家点「続きから」：这一下点击同时解锁音频 → `GET snapshot` → 从缓存加载场景（场景 ID 来自快照）→ 玩家站到本地保存的坐标（同一场景、同一 `lastSeq` 时）或快照的 `spot` → 连 WebSocket（`hello { lastSeq }`）→ 能走。
4. 同一局在另一个标签页或另一台设备上打开：服务端以 `4009` 踢掉旧连接，旧页面显示「別のタブで開かれています」和「ここで続ける」。

**断网**：按 9.1 退避重连；断开期间能走动、能看記憶帳的缓存，打字的内容先暂存，连上后再发；超过 30 秒显示横幅。

验收看 2.2「恢复」一行；iPhone 上的实测放进 spike S6。

## 10. 性能预算与加载

### 10.1 预算

| 项 | 预算 | 依据 |
|---|---|---|
| 首屏 JS（外壳） | ≤ 120KB（brotli） | 实测 React 19 + zustand 外壳 58KB |
| 3D 分块 | ≤ 250KB（WebGL）；用 WebGPU 时 ≤ 380KB | 实测 209KB / 349KB |
| 单个场景资源 | 环境 ≤ 10MB（几何 + 贴图 + 各时段光照图 + navmesh），其中进场包 ≤ 8MB；首次进入合计 ≤ 10MB；高档另外在后台下 ≤ 9MB（D-019，10.6.2） | 弱 4G 10Mbps 时 10MB 约 8 秒，首次进入 ≤ 10 秒 |
| 每帧 draw call | ≤ 120（含阴影 pass）；高档 ≤ 140 | 手机 GPU 驱动开销；S1 实测示例机器人方案 340；S7 全开 52〜68 |
| 可见三角形 | ≤ 300k | 写实的感觉主要来自光照图和贴图，不靠面数（10.6）；S7 的广场约 2 万面 + 人物 |
| 角色动画（CPU） | 底线机 ≤ 2ms / 帧（7 个可对话角色 + 背景人群） | 角色自己走动（8.6）；远处降频、画面外只更新位置 |
| 显存（贴图） | ≤ 150MB（标准档估算约 50MB，高档约 110MB） | KTX2 保持压缩 |
| JS 堆 | ≤ 150MB | iOS 标签页内存紧张时会被杀 |
| 长任务 | 单个 ≤ 50ms；大计算分片（`scheduler.yield`，Safari 降级 `setTimeout`）或进 Worker | 前端 knowledge.md |

CI 里卡：打包体积（超了构建失败）、场景资源体积、Lighthouse 移动端 LCP/TBT。帧率在真机上测（S1 自动计测页可复用）。

### 10.2 加载策略

1. 封面只有外壳 + 一张封面图 + 标题字体分片。
2. 封面点「書をひらく」：做音频解锁，开始下载 3D 分块；身份页点「〇〇として、はじめる」开始下载该身份的起点场景。麦克风说明在第一次按说话键时出现（7.6 的 `primer`），不在这里。
3. 选身份期间完成下载和着色器预编译。
4. 进入世界：先能走，再补细节。
5. 静态资源全部 hash 文件名 + `Cache-Control: immutable, max-age=31536000` + 预压缩 br；Service Worker 预缓存外壳、3D 分块、当前场景，幕末选择时把下一幕的场景也放进缓存。第二次进入、页面被回收后重开都几乎不下载（S-024）。

给 UX 定开场动画用的估算（按 D-019 的预算更新）：首次进入合计 ≤ 10MB（进场包 ≤ 8MB + 人物走动版 + 3D 程序），4G 中位约 50Mbps 时下载约 1.6 秒、弱 4G 10Mbps 约 8 秒，手机上预编译着色器再加 0.5〜1 秒；选身份期间已经在下载，起始档的自测（10.6.3）也在这段时间做。建议「翻开书 → 镜头穿进纸面」做成约 4 秒的主动画 + 一段可循环的等待段（资源没好就循环），第二次进入资源已缓存时允许点一下跳过。

### 10.3 自适应画质

按 D-019 定稿，画质分 L0〜L3 四级，起始档靠进场前的加压自测，降档随时、升档只在镜头切换和进出对话时；各级的设置、阈值和规则见 10.6.3。角色动画另按距离降频：远处角色降低更新频率，画面外只更新位置（8.6），和画质级无关。

### 10.4 浮层与 3D

- 全屏浮层（連鎖反応マップ、記憶帳、结局卡）打开时停掉 3D 渲染循环，背景用打开那一刻的画面（可模糊），省电、降温。
- 半屏浮层（对话）不停 3D。
- 关键时刻（UX 8.3）：人物定格，所以停 3D 渲染循环，对定格的画面加 CSS `filter: saturate() brightness()` 做降饱和、变暗，不需要额外的全屏后处理；减少动态效果时只淡入淡出。
- 盖在 3D 上的界面不用 `backdrop-filter`（毛玻璃会让 iPhone 每帧多一次整屏合成），底板用不透明的纸色（UX 7.7）。
- 哪些是全屏、哪些是半屏（UX 评审）：全屏（停 3D）= 連鎖反応マップ、記憶帳、幕末选择、结局页、设置、出戏卡（S-043）；关键时刻叠在定格的 3D 上，同样停渲染循环。半屏或叠在 3D 上（不停 3D）= 对话（字幕、输入区）、「近くの人」、轻提示、意图确认的二选一；「その頃」叠在幕切换的过场上。

### 10.5 结局卡保存为图片（S-026、S-032，P0）

- 卡面内容：称号；世界的去向（一行）；**影响最深的 1〜3 个角色的结局**（S-076，原来是 2〜3 个），每人一行「あなたの世界では…」（S-032，完整的 1〜3 句在结局页展开）；一行「和原作的不同」（例：原作では日没に間に合った。あなたの世界では――）；结局插画；书名和身份。不含玩家原话和记忆（和 P1 分享链接的边界一致）。这些字段由数据工程在 contracts 1.1 的 Ending 里加，「哪 1〜3 人」由服务端按影响程度排好，前端不自己挑。
- **每一局都出卡**（S-076、contracts 1.6 第 5 节）：只排得上 1 个人物时也出，人物区高度不变、行在区域里上下居中；一个也排不上时服务端放梅洛斯一句，所以卡上至少 1 行，前端不另做空的版式。结局校验两次都不过、改用模板尾声的局（S-065 降级）也出卡，句子全是预写的，版式一样。
- 比例：**4:5（1080×1350）**，UX 和前端已定（UX 评审：X、Instagram 帖子、LINE 都完整显示，放进 9:16 的快拍会自动补边），第一版只做这一个。卡上不放链接或二维码（邀请码阶段不开放公开页面，S-026、S-042）。区域：

  | 区域 | 高度 | 内容 |
  |---|---|---|
  | 插画 | 640px | 这一局结局演出里定格的一帧 3D 画面（见下） |
  | 标题 | 约 160px | 称号 + 世界的去向 |
  | 角色 | 约 330px | 1〜3 行：角色名 + 一句话；不满 3 行时上下居中 |
  | 和原作的不同 | 约 130px | 一行，左侧标「原作との違い」 |
  | 页脚 | 约 90px | 『走れメロス』· 身份 · 产品名 |

- **插画从哪里来**（UX 评审的提议，前端确认可行）：用这一局结局演出里定格的那一帧。演出走到定格镜头时，额外渲染一次 1080×640 的离屏目标，读出像素画进卡片的 Canvas，再释放；只多花一帧（几十毫秒，玩家看不出），显存多约 3MB、用完即还。好处是不用生成图像、不花钱（Q-006），画风和游戏一致，画的就是这个玩家自己的结局时刻。截帧失败（上下文丢失等）时用 5 类底线结局各一张预画的静态插画（S-034）。
- **没赶上时的两个镜头**（ux-design 11.4、art-direction 5.7，S-067），都不演处刑本身：身代わり是セリヌンティウス时，人群朝西，最后一缕光离开塔顶，停住；身代わり是玩家时，镜头放在柱上玩家的身后朝西门看，太阳落进门洞，没有人跑进来，停在光消失的那一刻，这一帧也做结局卡插画，卡上不出现玩家的脸。两个镜头都靠 S7 那种实时太阳（太阳方向由时钟算，见 10.6），不需要额外的资产。
- 世界结局由这一局生成（S-031），标题和句子长短不定：每个区域按「先缩小字号、再截断加…」自适应，**最小 28px**（1080 宽时；卡在手机上约 390pt 宽，28px 约 10pt，是还能读的下限）。字数上限和字号按 UX 评审的表：称号 ≤ 14 字（64px 明朝），去向 ≤ 26 字（34px），角色每句 ≤ 40 字（最多两行，30〜34px），原作との違い ≤ 48 字（最多两行，30px），页脚 28px。超长是生成侧不合规，由数据和后端控制，前端只做最后的保险。这张表已由 PM 记为 S-051（S-049 原写的 ≤ 12 / 40 / 30 作废）。
- 画法：屏幕上用 DOM 显示；保存时用 Canvas 2D 按同一份数据重新画，不用 html2canvas 之类的截图库（体积大，日文字体和 `<ruby>` 容易出错）。
  - 插画走同源，画进 Canvas 不会被污染，能导出。
  - 明朝体：画之前 `document.fonts.load()` 把卡面上要用的字加载好（Google Fonts 是按字分片的，卡面文字已经在 DOM 里显示过，分片通常已在缓存）。
- 保存：`canvas.toBlob()` 得到 PNG。手机上用 `navigator.share({ files })` 打开系统分享面板（iOS 里有「画像を保存」，也能直接发到 LINE、X）；不支持时桌面用下载链接，手机退回「长按图片保存」的提示页。
- 结局画面同时放「別の身分でもう一度」（PRD 第 8 节看换身份再玩率）。保存、分享面板打开、再玩一局都上报遥测（S-027 的行为指标）。

### 10.6 写实画风：定稿（D-016、D-019）

zg 定的画风是「高清，惊艳，真实」（D-016）；档位 zg 2026-10-06 22:28Z 选了「档 B 为底，强机自动升级」（D-019）。这一节先写定下来的规格（10.6.1〜10.6.4），后面保留做决定时的依据：各种手段的代价、S7 的两次实测和推算、三档方案的对比。事实和出处在 `frontend/research/realism-facts.md`，测试页是 S7（`frontend/spikes/s7-realism/`）。iPhone 12 的数字都是从 zg 的 iPhone 17 Pro Max 推算的〔推算〕，有旧机再实测。

#### 10.6.1 定下来的事（D-019）

- **两档**：所有手机至少是**标准档**（= 档 B）；加压自测有余量的手机自动升到**高档**（档 C 的效果）。内容、故事、界面两档完全一样，只差清晰度和精细度。
- **底线机** iPhone 12：标准档 p95 ≤ 33ms（30fps）。高档的目标是 p95 ≤ 20ms（约 50〜60fps），达不到就不升。
- **效果两档都全开**：烘焙光照 + 实时太阳和阴影 + 物理天空 + PBR + 雾 + 后处理（泛光、调色、暗角）+ Neutral 色调映射。S7：这些全开时 zg 的手机上一帧 GPU 2.6ms，iPhone 12〔推算〕8.7ms。
- **起始档靠自测，不按机型表**：Safari 认不出具体机型（GPU 名字只有「Apple GPU」，UA 的系统版本也冻结了）。
- **升档只在不显眼的时刻**：镜头切换、进出对话；持续有余量才升，一次升一级。降档随时可以（掉帧比画面跳一下更难受）。
- **高档的资源在后台下**：先用标准档的资源进场，所以两档的首次进入时间一样（≤ 10 秒）。

#### 10.6.3 起始档和升降档怎么定

画质分四级，按「花得多、看得出」排；标准档是 L1，高档是 L2、L3：

| 级 | 解像度 | 后处理 | 阴影 | 对话版人物 | 高档资源 |
|---|---|---|---|---|---|
| L0 兜底 | 1.25 | 关泛光和 MSAA；调色、暗角保留（并进输出那一遍），颜色不变 | 1024 | 1 个 | 不下 |
| L1 标准 | 1.5 | 全开 | 2048 | ≤ 2 | 不下 |
| L2 高 | 2 | 全开 | 2048 软阴影 | ≤ 4 | 下 |
| L3 最高 | 设备原生（≤ 3） | 全开 | 2048 软阴影 | ≤ 4 | 下 |

1. **起始档**：选身份、加载第一个场景期间，用一个固定的测试场景（和 S7 的 b7 同样的材质和后处理，放在屏幕外的渲染目标里）按 S7 的加压法测约 300〜500ms，得到一帧 GPU 耗时 g。按像素比估出每一级的耗时，取「L1 ≤ 25ms、L2 / L3 ≤ 12ms」里最高的一级。测不出（比如页面在后台）就从 L1 开始。
2. **降档**：每 5 秒看一次 p95 帧时间，连续两次超过本级的预算（L0 / L1 33ms，L2 / L3 20ms）就降一级。马上生效的只有解像度（最不显眼）；阴影、泛光、贴图和对话版人物个数留到下一次镜头切换再换（UX art-direction 9.5）。
3. **升档**：只在镜头切换、进入或离开对话的那一刻检查，说话中途、关键时刻（ux-design 8.3）、幕末页、结局演出期间不升也不换资源（这些时候必须降档也只降解像度）；条件是最近 30 秒 p95 都在预算内，并且在切换的黑场或过渡帧里做一次 30 帧的 2 倍加压，帧间隔仍在 16.7ms 左右（说明还有一倍以上余量）。一次只升一级；降档后 60 秒内不升；一局里降过两次就锁住上限（多半是发热）。
4. **低电量模式**：Safari 会把帧率锁在 30（帧间隔稳定在 33ms 而 GPU 很空），这时按 30fps 的预算算，不升档。
5. **高档资源**：到 L2 才开始在后台下；按进场包实测的下载速度判断，低于约 1MB/s 时不下，留着走标准档的贴图。下完在下一次镜头切换时替换。2048 和 1024 由流水线从同一张源图缩出，平均颜色和粗糙度一致，换的那一下只是更清楚（UX art-direction 9.5；CI 比较两档的平均颜色）。
6. 每局的起始级、升降次数、最后停在哪一级进遥测（第 11 节），用来校准阈值和 3.4 这个推算系数。

#### 10.6.5 做决定时的依据

**评估结论**（D-019 之前写的）

1. **手机上的写实感，主要靠提前算好的光和真实的材质，不靠实时特效。** 烘焙光照、HDR 天空光、照片扫描的 PBR 贴图、保留颜色的色调映射（Neutral），这几样花的是下载量，几乎不花帧时间。屏幕空间 AO、反射、透射这类实时特效在 iPhone 12 上太贵，第一版不用。
2. **按现在的 S-014，环境可以做到写实，人物只能做到「中景写实」。** 广场、石头、夕阳的光在 4MB 里能做好（档 A）。但对话时人物的脸在画面上三分之一，8k 面、2 个材质做不出接近真人的脸。
3. **前端推荐档 B 为底 + 强机自动升级（已定为 D-019）**：底线机仍是 iPhone 12，单场景放宽到 10MB、首次进入放宽到 10 秒，效果全开（包括后处理），可对话的人物在对话特写时用 2〜3 万面、4〜5 个材质的高精度版本；强机自动提高解像度、换 2048 贴图和更精细的对话人物。S7 在 zg 的 17 Pro Max 上实测，所有配置一帧 GPU 耗时 1〜4ms，推到 iPhone 12 是 4〜10ms〔推算〕，GPU 不是限制。
4. **Gaussian Splatting 不做主环境。** 它把拍摄时的光照固定在里面，和「太阳就是时钟」、第四幕的归途连续走过几个时段冲突；每个时刻要一整套数据（压缩后每套约 7〜14MB）；iPhone 15 Pro Max 跑 100 万个点只有 20〜26fps，iPhone 12 更低。最多用在某个固定时刻的远景。

**各种手段的代价**

（帧时间一栏的「S7 bX」是测试页里对应的计测项，实测数字见下面「从 zg 的手机推到 iPhone 12」）

| 手段 | 对写实的作用 | 帧时间 | 下载 | 首次进入 | 结论 |
|---|---|---|---|---|---|
| PBR 材质（颜色、法线、粗糙度贴图） | 石头、布、陶的质感和凹凸 | 每像素多 1〜2 次贴图采样（S7 b1→b2） | 每种材质 1024 颜色图 JPEG 约 150〜250KB，KTX2 约 200KB；法线 512 KTX2 约 300KB | 贴图解码和上传；KTX2 要在 Worker 里转码 | 必用 |
| HDR 天空光（IBL） | 天空颜色的环境光和反射，阴影里不再是死黑 | 很小（S7 b2 含） | 1k HDR 约 1.1MB；Ultra HDR JPEG 约 0.1MB | 生成环境贴图一次（S7 记 `pmremHdrMs`） | 必用；天空用物理模型生成，烘焙和页面用同一张，光才对得上；正式版用 Ultra HDR 省下载 |
| 烘焙光照（lightmap） | 柔和的反射光、接触阴影，最像照片 | **最省**：全烘焙后环境几乎不用算光（S7 b5） | S7 的广场每套（地面 + 建筑 2 张）：1024 约 0.35MB，2048 约 1.1MB | 只是多几张图 | 必用，但见下面「时刻」 |
| 实时太阳阴影 | 人物和建筑的影子跟着太阳走 | 多画一遍投影的几何；用低模代理投影（S7 约 2,700 面）很便宜（S7 b2→b3：+0.9ms） | 无 | 无 | 用；两档都 2048 |
| KTX2 贴图 | 不直接加写实，但让高清贴图放得进手机显存 | 略好（带宽小） | 和 JPEG 相近；法线用 UASTC 会大一些 | 多一个 0.5MB 的转码 wasm（缓存后为 0）；转码耗时 | 必用：2048² 贴图显存从 21MB 降到 2.7〜5.3MB |
| 色调映射（AgX / ACES / Neutral） | 高光怎么过渡；颜色保留多少 | 0 | 0 | 0 | 用 Neutral（Khronos PBR Neutral）。S7 对比：AgX 把夕阳照亮的石墙冲成浅米色，Neutral 保住了橙金色（UX 评审第 1 条）；夜里 Neutral 没有 AgX 那样抬亮暗部，所以夜间把曝光提高（S7 可切换对比） |
| 雾（空气透视），朝太阳的方向变暖 | 远景变淡，有纵深；逆光看城门大街时，远处的城门和山融进夕阳里 | 几乎为 0（每像素多一次点积） | 0 | 0 | 用 |
| 太阳本身（光盘 + 光晕） | 逆光时画面有主角；配合泛光最像照片 | 1 个面片 | 0 | 0 | 用 |
| 后处理（泛光、暗角、调色、抗锯齿） | 夕阳和亮面的光晕，电影感 | 每个全屏 pass 都要过一遍所有像素（S7 b4→b7：+0.4ms） | 约 20KB 代码 | 无 | 两档都开（D-019） |
| 解像度（DPR） | 清晰度 | 影响最大，和像素数成正比：DPR 1 / 1.5 / 2 → 1.0 / 2.6 / 4.3ms（S7 b9、b7、b8） | 0 | 0 | 标准档 1.5，高档 2〜3 |
| 屏幕空间 AO、反射（SSR）、透射 | 角落变暗、地面倒影、玻璃 | 贵：每个都多一个全屏 pass，透射要多渲染一遍整个场景 | 0 | 0 | 不用：AO 用烘焙的代替 |
| Gaussian Splatting | 照片级的真实 | 1M 点在 iPhone 15 Pro Max 上 38〜50ms | 每个时刻一套，压缩后 7〜14MB | 排序和上传 | 不做主环境（见上） |

**光照怎么随时刻变（和「太阳就是时钟」的关系）**

UX 的 art-direction v1.0 定了：王城墙上的阴影线往上爬就是时钟，所以**太阳和影子必须实时**，只烘焙和时刻无关或变化慢的部分（遮蔽、天空光）；要按时段烘的话，优先顺序是日没 > 夜 > 正午 > 早上。S7 按这个做了三种，玩家看到的差别和代价：

| 方式（S7 的光照切换） | 时刻能不能变 | 画面 | 代价 |
|---|---|---|---|
| A 全烘焙（太阳、反射光、阴影都烘进图里） | 不能，固定 18:30 | 最像照片；但石头的凹凸在光里看不出来，影子不会动 | 帧时间最省；每个时刻一套图。只做对照，不用 |
| B 烘天空光和反射光 + 实时太阳（默认） | 太阳和影子实时；反射光是 18:30 的 | 接近全烘焙，凹凸和高光是实时的 | 多一个阴影 pass；每个时段一套反射光图 |
| C 只烘遮蔽 + 实时太阳 + 物理天空 | 能连续变（时刻滑块、「等日没」） | 阴影里缺少暖色的反射光，偏冷、偏平；夜里用蓝调 | 改时刻时要重新生成环境光（S7 记 `pmremSkyMs`） |

前端建议（和 UX 一致）：**正式版以 C 为底**，太阳、影子、天空、雾都按时刻实时算，所以任何时刻都对；**再给关键时段各烘一套天空光和反射光（B）**，从日没开始，时段之间混合。第四幕的归途连续走过「雨后的昼前 → 午後的烈日 → 斜陽」（UX art-direction 3.1、3.5），就是 C 的太阳加上这几个时段的反射光图依次混合；最后回到广场是日没。S7 里「等日没」按钮演示的就是最后这段：18:00 到 19:10，影子线爬上王城的墙，最后从塔顶消失。

**三档方案**（给 zg 选档时的对比；定下来的是档 B 为底 + 强机升到档 C 的效果，规格见 10.6.2）

**从 zg 的手机推到 iPhone 12〔推算〕**

zg 的手机是 **iPhone 17 Pro Max**（zg 2026-10-06 说的）。之前从 S1 记下的 UA（iOS 18.7）和屏幕（440×956 pt）推成 16 Pro Max 是错的：iOS 26 起 Safari 的 UA 把系统版本冻结在 iOS 18 的最后一个版本号，17 Pro Max 的屏幕也是 440×956 pt。它不是底线机，而且 Safari 把帧率锁在 60，所以只看帧时间看不出离上限还有多少余量。

- **第一次实测（2026-10-06 14:31Z，12 项）**：解像度 1.5 时 11 项的中位帧时间都是 17ms（顶在 60 帧上限），包括 7 个人物 × 28k 面、后处理、阴影 2048（b11，47 万面）；p95 除 b1（21ms）和 b10 / b11（23ms）外都是 17ms；draw call 27〜68。只有 b8（b7 解像度提到 2）掉到 40 帧：中位 25ms、p95 32ms。首次进入：第一帧 13.5 秒，下载 9.05MB。
- **原来的 `finishMs` 不能用**：每 12 帧调一次 `gl.finish()` 量出来全是 1〜3ms，连正在掉帧的 b8 也只有 3ms，说明 iPhone 上 `gl.finish()` 不等 GPU 做完。已从测试页去掉。
- **改用加压**（S7 第二版）：每种配置先照常沿路线走 6.5 秒记帧时间，再停在一个固定机位，把同一帧连画 N 遍（N = 2、4、8、16、32），直到平均帧间隔 T ≥ 45ms。这时 GPU 一直在忙，**一帧的 GPU 耗时 g ≈ T / N**。帧间隔会被凑到 16.7ms 的整数倍，所以真实值在 (T − 16.7) / N 和 T / N 之间，取中间，两头都记下。同时记每遍的 CPU 提交时间，CPU × N ≥ 0.8T 时标为 CPU 先到上限。32 遍还在 60 帧时只记上限（≤ 16.7 / 32 ≈ 0.5ms）。
- GPU 性能比：3DMark Wild Life Extreme，iPhone 12 是 2131 分，iPhone 17 Pro Max 是 5405 分，约 **2.5 倍**（UL 官方数据库，见附录）。
- 长时间玩会降频：iPhone 12 的 Wild Life Extreme 压力测试稳定度是 74%，持续玩时只剩约四分之三的性能，再乘 **1.35**。zg 的手机这次只跑几分钟，按满速算。
- 像素：同样 DPR 1.5 时，iPhone 12 的像素约是 17 Pro Max 的 78%，只让全屏的 pass 变便宜；推算时不打这个折扣，当作余量。
- 合起来：**iPhone 12 一帧的渲染耗时〔推算〕≈ zg 手机上加压测出的 g × 3.4**。33ms 一帧里给动画、逻辑和语音留约 8ms，渲染耗时上限按 25ms 算，所以：
  - zg 手机上 g ≤ 7.3ms：iPhone 12 上能过〔推算〕；
  - 7.3〜9.8ms：不确定（不算降频时能过，算降频时过不了），要旧机实测；
  - 超过 9.8ms：iPhone 12 上过不了〔推算〕。
- **第二次实测（加压，2026-10-06 14:55Z，suiteId `muwsw58a`，用电池）**〔实测〕和 iPhone 12〔推算〕：

  | 配置 | zg 手机上一帧 GPU 耗时 g | iPhone 12〔推算〕g × 3.4 |
  |---|---|---|
  | b1 基线（无烘焙、半球光、无法线、无阴影） | 2.0ms | 6.6ms |
  | b2 HDR 环境光 + 法线（只烘遮蔽） | 1.7 | 5.8 |
  | b3 b2 + 实时太阳阴影 2048 | 2.6 | 8.9 |
  | b4 烘间接光 + 阴影 2048 | 2.1 | 7.2 |
  | b5 全烘焙（人物阴影 1024） | 2.3 | 7.9 |
  | b6 全烘焙 + 后处理 | 2.3 | 7.9 |
  | b7 烘间接光 + 阴影 + 后处理 | 2.6 | 8.7 |
  | b8 b7，解像度 2 | 4.3 | 14.6 |
  | b9 b7，解像度 1 | 1.0 | 3.5 |
  | b10 b7 + 7 个人物 12k 面 | 2.8 | 9.5 |
  | b11 b7 + 7 个人物 28k 面（47 万面） | 2.9 | 9.7 |
  | b12 全烘焙 + 7 个人物 8k 面 | 2.5 | 8.6 |

  - 不加压时 12 项全部 60 帧，p95 都是 17ms，draw call 28〜68。0.5ms 以内的差别在误差内。耗时和像素数成正比（解像度 1 / 1.5 / 2 → 1.0 / 2.6 / 4.3ms）；阴影 2048 约 +0.9ms，后处理约 +0.4ms，7 个人物约 +0.3ms。
  - 首次进入：第一次 13.5 秒，第二次 8.5 秒（着色器已缓存，编译从 1.2 秒降到 0.04 秒；资源 8.2 秒，主要是 Artifact 里 base64 资源的下载和解码）。
  - 第一次实测里 b8 掉到 40 帧，这次没有复现，多半是第一版每 12 帧调一次 `gl.finish()` 打断了流水线。以第二次为准。
- **结论**：iPhone 12 上所有项目都在 25ms 以内〔推算〕，解像度 1.5 的各项甚至在 60 帧的预算内。写实的这些手段在帧时间上都不贵，**限制写实程度的是首次进入时间和下载量、内存、美术工作量**，不是 GPU。所以下面档 B 的后处理改为底线机也开；档 C「排除 iPhone 12〜14」的前提不成立，档 C 的大部分效果改为按机型自动给强机（见下一段）。17 Pro Max 用原生解像度 3 时 b7 约 9.7ms〔按像素比推算〕，仍在 60 帧以内。
- 局限：3DMark 是原生 Metal 测试，不是浏览器里的 WebGL；加压量的是一个机位，不是整条路线；连画 N 遍时阴影也重画 N 遍，和真实的一帧一样。所以 3.4 只是量级。给 zg 的选择卡里「实测」（zg 的手机）和「推算」（iPhone 12）分开写。能借到 iPhone 12〜14 的话以实测为准。

**按机型分级（zg 2026-10-06 提出，D-019 采用；定稿的做法见 10.6.3）**

zg 问「不同 iPhone 不同配置不同效果，17 Pro Max 可以高一点」。前端的做法：同一套内容，按手机实际能力自动升降画质，三档方案从「三选一」变成「底线机按档 B，强的手机自动升到档 C 的效果」。

- 浏览器认不出具体机型：Safari 只告诉网页「Apple GPU」，UA 的系统版本也被冻结。所以不按机型表，而按实测：进入第一个场景时，在封面和加载期间用上面的加压方法测几百毫秒，定一个起始档；玩的过程中每几秒看一次帧时间，连续掉帧就降一级，持续有余量（按加压估算）就升一级。升降只在镜头切换、进出对话这些不显眼的时刻做，避免画面突然跳。
- 能升降的项，按「花得多、看得出」排：解像度（1.25 / 1.5 / 2 / 3）→ 后处理（关 / 泛光 + 调色 / 全开）→ 阴影（1024 / 2048、软阴影）→ 同时用对话版的人物数（1 / 2 / 4）→ 对话特写的人物精度（2〜3 万面 / 4 万面）→ 贴图（1024 / 2048）。前四项不用多下载；后两项要下载高档资源，只有升到那一档的手机才下。
- 代价：美术按最高档做，再导出低档版本（人物两个 LOD 变三个，贴图多一套 2048），工作量和高档的下载量增加；测试要覆盖每一档。给选择卡的两个数〔估算〕：
  - **强机多下载**：环境只给占画面最多的 4〜6 种材质（地面、主要石墙、王城）换 2048 颜色图 + 1024 法线图，每种约 +1.5MB，每个场景 **+6〜9MB**（所有材质都换约 +15MB，不建议；S7 的全部材质 1024 KTX2 是 5.5MB）。对话人物换 4 万面、脸和皮肤 2048 贴图，每个角色比档 B 的对话版多约 **+2.5MB**；角色跨场景缓存，6〜8 个主要角色一局共多约 15〜20MB，按出场分批下。光照图不变（档 B 已是 2048）。**先用档 B 的资源进场，高清资源在后台下完再替换**，所以强机的首次进入时间和档 B 一样（≤ 10 秒），多下的量只在 Wi-Fi / 5G 上才明显用得上。
  - **多出的美术工作量（相对档 B 本身）**：合计约 **+25〜40%**。环境 +10〜20%：照片扫描的 PBR 素材本来就是 2K〜4K，低档由流水线自动缩小（gltf-transform），多出的是每一档的检查。人物 +30〜50%：对话版要按 4 万面、2048 贴图做足脸的细节，再减到 2〜3 万面和 8k 面两个版本；人物是美术量的大头。对照：档 C 给所有人是「再翻倍」，自动升级在 B 和 C 之间。另外前端要写自动分级和每一档的测试，这部分不算美术量。

**人物预算（PM 的第 3 个问题；定稿见 10.6.2）**

- 现在的预算（1 个蒙皮网格、≤ 2 材质、≤ 8k 面）**对中景够，对对话特写不够**。S7 的「对话特写」可以直接切 8k / 12k / 28k 面对比面数的代价（人物是灰色假人，只看轮廓和帧时间）：8k 面时头、肩、手的轮廓已经有棱角；写实的脸还要皮肤、眼睛、头发分开的材质，2 个材质做不出来。
- 建议改成每个可对话角色两个版本：
  - **对话版**（LOD0）：2〜3 万面，4〜5 个材质，头发用 alpha test 的发片，面部 ARKit 52 个表情形变 + 日语元音口型；同一时间最多 1〜2 个角色用这个版本（正在说话的人和旁边的人）。
  - **走动版**（LOD1）：8k 面，2 个材质，沿用现在的预算。
  - draw call：对话版 5 个材质 × 2（含阴影）= 10，加 6 个走动版 × 4 = 24，环境约 25，合计约 60，在 120 以内。
- 人物资产的来源：Ready Player Me 已于 2026-01-31 停服；MakeHuman / MPFB 的基础模型是 CC0，可以商用；MetaHuman 授权允许用在别的引擎，但没有官方 glTF 导出，手机用的 LOD 没有表情形变。建议 UX 和美术用 MPFB 做基础，在 Blender 里改脸和衣服，Blender 已装在 zg 的 Mac 上。

## 12. 安全与隐私

- 前端没有任何密钥或令牌。邀请码登录后，会话凭证是 `HttpOnly; Secure; SameSite=Lax` 的 Cookie（S-020）；WebSocket 握手自动带 Cookie，服务端校验 `Origin`。如果 S2 发现某个 App 内浏览器握手不带 Cookie，再用后端预留的票据接口。
- 会改数据的 REST 要求 `Content-Type: application/json`，服务端也校验 `Origin`（已向后端建议）。
- 麦克风只在按住期间上传；不在前端存录音；界面明确告诉玩家什么时候在发送。
- 严格 CSP：`default-src 'self'`；`connect-src 'self'`（含同源 `wss:`）；`img-src 'self' data: blob:`（结局插画由前端离屏渲染成 blob，截帧失败时的兜底图走同源 `/assets/endings/…`，不放行外部图片域名）；`font-src` / `style-src` 只加 Google Fonts；Trusted Types；不引入第三方分析或广告脚本。
- 所有服务端返回的文字（角色台词、摘要、记忆）都按纯文本渲染（`textContent`），不当 HTML。
- 自伤信号（S-043、S-069，api-contract 3.12）：`safety_pause` 暂停故事，出全屏的出戏卡（10.4）；`safety_hint`（无字段，一局最多一次，重连不重推）不暂停、不停人物的声音、不打断按住说话，只在画面边上显示一条安静的小提示，点开是和出戏卡同一个相谈窗口；界面按 ux-design 14.2：竖屏是贴右边缘的纸色小条（宽 ≤ 52vw，下沿在字幕面板上沿往上 12px，跟着面板高度动），横屏是操作行右边一行「つらいときの相談窓口」+ ✕；不计时，✕ 或到幕末页前收起；`role="status"`、`aria-live="polite"`，不抢焦点；减少动态时只淡入；点开是底部面板，故事不暂停，人物这句照常说完。服务端重连不重推，所以刷新后自然不再出，前端不另存状态。第二次拿不准直接来 `safety_pause`：先收起小提示再出卡；出戏卡用界面黑体（14.1），窗口列表按 14.3，电话号码是可选中的文字、不折行（`white-space: nowrap`）；横屏（landscape 且高 ≤ 520px）三个窗口排成一行三列、按钮在各自名字下面，竖屏 375×667 和横屏都不滚动（ux-design 14.3，原型 v8）；文案（含〔物語に戻る〕下面那行小字）照 UX 的文案表。書 → 設定最下面常驻「話を聞いてくれる窓口」，打开同一面板（S-070）。文案在前端的文案表里，不从服务端下发。两种情况前端都不记原话，点没点开、看了多久都不进埋点（S-057、S-069 ③、S-070 ③）。
- **收到 `safety_pause` 时怎么收**（ux-design 14.1，原型状态 27）。分类器约 1 秒出结果，人物多半已经说了一两个词，所以前端自己收，不等服务端停流：
  1. 人物声音：人声总线的 GainNode 0.2 秒线性降到 0（和打断停播同一预算，S-014），降完清空 AudioWorklet 的播放缓冲；之后到的同一 `turnSeq` 的音频包直接丢。相槌和预录走同一总线，一起淡出。
  2. 字幕：这一轮不再排新的分片，停在已经出的地方，**不加「——」**（那是玩家打断的标记）。
  3. 人物：口型跟音量合上，再强制回闭嘴；手上的动作 0.3 秒混回待机，不播吃惊、回头这类反应。
  4. 玩家正按着说话键：停止发麦克风帧，本地录音丢掉；什么都不用发：服务端推 `safety_pause` 时直接丢掉这一轮，之后这个 `turnId` 的音频帧和 `activity_end` 都忽略；恢复后用新的 `turnId`（api-contract 3.12）。卡片期间说话键不可用；麦克风默认释放（橙点还亮着会让人觉得还在被听，ux-design 14.1）；如果 S2 测出重新取得会再弹授权，就不释放、只停发帧（回到故事时马上弹系统框更糟，也违反 UX 7.2「中间不重复申请」）。
  5. 同时：环境音和音乐各自的总线 0.6 秒降到 0.25（−12dB），不全静。
  6. 0〜0.4 秒 DOM 压暗层淡入，小提示、候选、轻反馈收起。压暗完成后，在暗处清掉这一轮的两句字幕（玩家那句和人物说了一半的那句），停 3D 渲染循环（全屏卡），卡片 0.3 秒淡入，焦点移到卡片（`role="dialog"`、`aria-modal`，读屏先读第一行）。同时从本地对话记录和续玩缓存里删掉这一轮的文字（原话立即清空，S-057）。
  7. 「物語に戻る」：发 `safety_resume`；卡片收起，压暗 0.4 秒退去，恢复渲染循环；环境音和音乐 1 秒回到原来的音量；字幕区回到这一轮之前人物的上一句（前端在每轮开始时记下，没有就只出名字）；收到 `safety_resumed` 后重新 `focus`，会话重建期间是 `preparing`。
  - 没有人物在说话（对叙事者说、幕末说打算、打字）：跳过 1〜3。人物已经说完才收到：一样，这一句的字幕在暗处去掉。减少动态时不变（本来只有淡入淡出）。
- 静态资源和 API 同源（Q-B7，前端已确认）：带 hash 的文件 `immutable` 长缓存，`index.html` `no-cache`，`/v1/*` 不经 CDN 缓存。

## 13. 无障碍

- 字幕始终可见；文字输入能完整玩通一局（PRD 7.2）。
- 说话按钮支持「按一下开始、再按一下结束」的切换模式（按住对部分人有困难）。
- `prefers-reduced-motion`：关闭镜头晃动和大幅转场。
- DOM 层所有控件可用键盘和读屏操作；3D 里的可交互角色在 DOM 层有对应的列表入口。
- 文字和背景对比度按 WCAG 2.2 AA；字号可调。
