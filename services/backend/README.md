# services/backend

Backend: a Python package `zoujin_backend` with three entry points (gateway, narrator, and mock service); deployed as two Cloud Run services (dev-plan 2.1). Owned by backend. For design see `docs/backend/`.

バックエンド：Python パッケージ `zoujin_backend`。ゲートウェイ、語り手、モックサービスの3つのエントリポイントを持ち、デプロイ時は2つの Cloud Run サービスになる（dev-plan 2.1）。バックエンドが担当する。設計は `docs/backend/` を参照。

## Mock service / モックサービス (B-1)

For the frontend's offline development and the frontend CI's end-to-end tests: it serves the api-contract REST and WebSocket from the same origin and replays sessions according to scripts. It uses no database, calls no model, and needs no credentials.

フロントエンドのオフライン開発とフロントエンド CI のエンドツーエンドテスト用。api-contract の REST と WebSocket を同一オリジンで提供し、台本に従ってセッションを再生する。データベースは使わず、モデルも呼ばず、認証情報も不要。

```sh
uv run zoujin-mock                 # http://127.0.0.1:8787, default script "tour" / デフォルト台本「導覧」
uv run zoujin-mock --speed 0       # no waiting (CI) / 待たない（CI）
uv run zoujin-mock --scenario confirm --allow-origin http://localhost:5173
docker compose up mock             # the same program, in a container / 同じプログラムをコンテナで
```

- Invite code `mock`. The session cookie is `zj_session`, without `Secure` over local http.
  招待コードは `mock`。セッション Cookie は `zj_session` で、ローカルの http では `Secure` を付けない。
- Ideally the frontend goes through the dev server's proxy to be same-origin with the mock; when cross-origin, use `--allow-origin` to allow the dev server's Origin (REST that changes data and the WebSocket handshake both check Origin, section 0).
  フロントエンドは開発サーバーのプロキシ経由で mock と同一オリジンにするのが望ましい。別オリジンの場合は `--allow-origin` で開発サーバーの Origin を許可する（データを変更する REST と WebSocket のハンドシェイクはどちらも Origin を検査する。第0節）。
- Every message and response sent is first constructed with the pydantic types generated by `packages/contracts` and then validated against the JSON Schema; if it fails, it is not sent and an error is reported in the terminal.
  送信するメッセージとレスポンスはすべて、まず `packages/contracts` が生成した pydantic 型で構築し、次に JSON Schema で検証する。通らなければ送信せず、ターミナルにエラーを出す。
- Scripts and how to write them: `fixtures/sessions/README.md`. REST fixed data and the `/__mock/*` control endpoints: `fixtures/mock/rest/README.md`.
  台本とその書き方：`fixtures/sessions/README.md`。REST の固定データと `/__mock/*` 制御エンドポイント：`fixtures/mock/rest/README.md`。
- Code: `src/zoujin_backend/mock/` (`rest.py` REST, `ws.py` handshake and the responses fixed by the protocol, `live.py` script advancement, `state.py` per-playthrough state, `schemas.py` self-check). It does not import database or narrator code.
  コード：`src/zoujin_backend/mock/`（`rest.py` が REST、`ws.py` がハンドシェイクとプロトコルで固定された応答、`live.py` が台本の進行、`state.py` が1周回の状態、`schemas.py` が自己検査）。データベースと語り手のコードは import しない。
- Tests: `tests/test_mock.py` starts a real uvicorn, runs all scripts with a Python client at `--speed 0`, then runs the tour once more at 0.04x time (timing of interruption, retraction, confirmation, and ending, and the coverage check of server messages), plus the 16 REST endpoints and the control endpoints.
  テスト：`tests/test_mock.py` は本物の uvicorn を起動し、Python クライアントで `--speed 0` のもと全台本を実行し、さらに 0.04 倍の時間で導覧を一周する（割り込み、取り消し、確認、結末のタイミングとサーバーメッセージの網羅検査）。加えて REST の16エンドポイントと制御エンドポイントも検査する。

## Gateway and narrator / ゲートウェイと語り手 (B-0)

Skeleton: accounts and invite codes, REST (section 1), WebSocket (section 2), the narrator's single-transaction commit, and replay. In threads and CI the model is only fake or replay (`ZJ_MODEL=fake`, the default; `replay` reads `fixtures/model-replays`), and Live is always fake. The real text-model client is described below in "Narrator pipeline (B-2)" and runs only on zg's Mac.

骨格：アカウントと招待コード、REST（第1節）、WebSocket（第2節）、語り手の単一トランザクションでのコミット、リプレイ。スレッドと CI ではモデルは偽物とリプレイだけを使い（`ZJ_MODEL=fake`、デフォルト。`replay` は `fixtures/model-replays` を読む）、Live は常に偽物。本物のテキストモデルのクライアントは下の「語り手パイプライン（B-2）」を参照し、zg の Mac でのみ動かす。

```sh
docker compose up gateway          # db, create tables, narrator, gateway; gateway at http://127.0.0.1:8001 / db、テーブル作成、narrator、gateway。ゲートウェイは http://127.0.0.1:8001
```

Without containers (needs a PostgreSQL; `docker compose up db` provides one):

コンテナを使わない場合（PostgreSQL が必要。`docker compose up db` で用意できる）：

```sh
export DATABASE_URL=postgresql://zoujin:zoujin@127.0.0.1:5432/zoujin ZJ_DEV=1
uv run alembic -c services/backend/alembic.ini upgrade head
uv run zoujin-narrator             # 127.0.0.1:8002, called only by the gateway / ゲートウェイからのみ呼ばれる
uv run zoujin-gateway              # 127.0.0.1:8001
uv run zoujin-admin invite create --count 3   # plaintext printed only this once, only hashes are stored in the DB / 平文はこの一度だけ表示し、DB にはハッシュだけを保存する
uv run zoujin-admin replay pt_…    # rebuild world state from events and compare with the cache: exit 0 if equal, 1 if different, 2 if no such playthrough / イベントから世界状態を再構築してキャッシュと比較する：同じなら終了コード 0、違えば 1、その周回がなければ 2
```

- Environment variables: `DATABASE_URL` (required), `ZJ_MODEL` (`fake` / `replay`), `ZJ_DEV=1` (cookie without `Secure`; narrator does not check OIDC, local use only), `ZJ_NARRATOR_URL` (default `http://127.0.0.1:8002`), `ZJ_ALLOW_ORIGINS` (Origins allowed besides same-origin, comma-separated), `ZJ_SPEED` (interval multiplier for fake Live, 0 = no waiting), `ZJ_WORLD` (absolute path of the world.json used to start new playthroughs; if unset it is `worlds/hashire-merosu/1.0.0-draft`; existing playthroughs use the version locked at their start; `eval_api` reads it on every `setup()`), `ZJ_RELEASE` (the manifest emits identities whose `release` is not greater than this, default 1), `ZJ_SCENE_PACKS` (absolute path of the scene pack directory, default the repo's `assets/scenes`; at deployment point it at the build output), `ZJ_WEB_DIST` (the vite build's dist: the gateway serves the frontend and the scene packs at `/scenes/<version>/…` from the same origin, for deployment, B-23), `ZJ_NARRATOR_AUTH` (`none` / `iam`: `iam` means on Cloud Run only the gateway service account may call the narrator and the gateway carries an OIDC token, B-23, see `infra/deploy/README.md`). The manifest is generated once when the gateway process starts (`manifest.py`, B-7); if the world model lacks fields or the voice manifest is malformed, the gateway will not start, and the error says which file and which field.
  環境変数：`DATABASE_URL`（必須）、`ZJ_MODEL`（`fake` / `replay`）、`ZJ_DEV=1`（Cookie に `Secure` を付けない。narrator は OIDC を検査せず、ローカル専用）、`ZJ_NARRATOR_URL`（デフォルト `http://127.0.0.1:8002`）、`ZJ_ALLOW_ORIGINS`（同一オリジン以外で許可する Origin、カンマ区切り）、`ZJ_SPEED`（偽 Live の間隔の倍率、0 = 待たない）、`ZJ_WORLD`（新規周回に使う world.json の絶対パス。未設定なら `worlds/hashire-merosu/1.0.0-draft`。既存の周回は開始時にロックされたバージョンを使う。`eval_api` は `setup()` のたびに読む）、`ZJ_RELEASE`（manifest はこれ以下の `release` の ID を出す。デフォルト 1）、`ZJ_SCENE_PACKS`（シーンパックのディレクトリの絶対パス。デフォルトはリポジトリの `assets/scenes`。デプロイ時はビルド出力を指す）、`ZJ_WEB_DIST`（vite build の dist：ゲートウェイが同一オリジンでフロントエンドと `/scenes/<バージョン>/…` のシーンパックを配信する。デプロイ用、B-23）、`ZJ_NARRATOR_AUTH`（`none` / `iam`：`iam` は Cloud Run 上で語り手の呼び出しをゲートウェイのサービスアカウントだけに許し、ゲートウェイが OIDC トークンを付ける。B-23、`infra/deploy/README.md` 参照）。manifest はゲートウェイのプロセス起動時に一度生成される（`manifest.py`、B-7）。ワールドモデルにフィールドが欠けていたり、音声一覧の形式が不正だったりするとゲートウェイは起動せず、エラーにどのファイルのどのフィールドかが書かれる。
- On SIGTERM the gateway sends `goaway` to every connection, closes them with 1012, and exits. After the narrator commits it does `NOTIFY zoujin_commit`; the gateway, having done `LISTEN`, reads the new events of that playthrough from the DB and pushes them to those connected.
  ゲートウェイは SIGTERM を受けると、全接続に `goaway` を送り、1012 で閉じてから終了する。語り手はコミット後に `NOTIFY zoujin_commit` を行い、`LISTEN` しているゲートウェイが DB からその周回の新しいイベントを読んで接続中の人へ送る。
- Logs and traces record only IDs and counts, never original words (data-design section 8).
  ログとトレースには ID と件数だけを書き、原文は書かない（data-design 第8節）。
- Code: `gateway/` (`auth.py` invite codes and sessions, `rest.py`, `ws.py`, `hub.py` receives commit notifications, `core.py` assembles pushes), `narrator/` (`core.py` takes tasks and does the single-transaction commit, `pipeline.py` the pipeline, `rules.py` the rules of step 3, `view.py` the state and characters sent to the model, `app.py` the internal API), `db/` (tables, migrations, event rows, `store.py` small DB write functions), `models/` (fake model, replay, real client, ledger, prompts), `eval_api.py` (evaluation entry), `s2.py` (S-2 run script), `trace.py` (Span), `admin.py`.
  コード：`gateway/`（`auth.py` が招待コードとセッション、`rest.py`、`ws.py`、`hub.py` がコミット通知の受信、`core.py` がプッシュの組み立て）、`narrator/`（`core.py` がタスクの取得と単一トランザクションのコミット、`pipeline.py` がパイプライン、`rules.py` が第3ステップのルール、`view.py` がモデルに渡す状態と人物、`app.py` が内部 API）、`db/`（テーブル、マイグレーション、イベント行、`store.py` が DB 書き込みの小さな関数）、`models/`（偽モデル、リプレイ、本物のクライアント、台帳、プロンプト）、`eval_api.py`（評価の入口）、`s2.py`（S-2 の実行スクリプト）、`trace.py`（Span）、`admin.py`。

## Narrator pipeline / 語り手パイプライン (B-2)

A turn of dialogue (voice transcription, or a `text`) follows backend-design 2.4: routing → extraction → step 3 deterministic rules (R1–R7, `narrator/rules.py`, cross-checked against `judge()` in `evals/s2_check.py`) → step 4 model check → rewrite, degrade, or reject → single-transaction commit.

1ターンの対話（音声の文字起こし、または `text`）は backend-design 2.4 に従う：振り分け → 抽出 → 第3ステップの決定的ルール（R1〜R7、`narrator/rules.py`。`evals/s2_check.py` の `judge()` と照合）→ 第4ステップのモデル検査 → 書き直し、降格、または拒否 → 単一トランザクションのコミット。

- Time limits: 5 seconds for routing; 15 seconds each for extraction, check, and rewrite. Timeouts, output failing the Schema, and call failures are each retried once; if the second attempt still fails, routing is treated as "maybe", and for the others this turn commits only the clock event, candidates are discarded, and `turns_timed_out` is incremented. 429 (`RateLimited`) and hitting the cap (`BudgetStop`) are not retried: the whole turn is put back in the queue and the error is raised upward.
  時間制限：振り分けは5秒、抽出・検査・書き直しは各15秒。タイムアウト、スキーマに通らない出力、呼び出し失敗はそれぞれ一度再送する。2回目も駄目なら、振り分けは「可能性あり」とし、それ以外はこのターンでは時計イベントだけをコミットして候補を破棄し、`turns_timed_out` を1増やす。429（`RateLimited`）と上限到達（`BudgetStop`）は再送せず、ターン全体をキューへ戻して上へ投げる。
- Candidates that extraction marked as needing confirmation and are irreversible (making a beat `prevented` / `altered`, changing a hostage's or the player's identity or situation): those from dialogue are saved as drafts and the player is asked (B-4, see below); those from actions are dropped and `candidates_confirm_dropped` is incremented.
  抽出が確認要と印を付け、かつ不可逆な候補（ビートを `prevented` / `altered` にする、人質やプレイヤーの身分・境遇を変える）：対話からのものは下書きとして保存しプレイヤーに尋ねる（B-4、下記参照）。動作からのものは破棄し、`candidates_confirm_dropped` を1増やす。
- `playthrough_metrics` gained the cost of each kind of prompt and these counts: routing skipped, timeout degraded, rewrite, degrade, reject, dropped because confirmation was needed (migration `0002_b2_metrics`).
  `playthrough_metrics` に、各種プロンプトのコストと次の件数が加わった：振り分けスキップ、タイムアウトによる降格、書き直し、降格、拒否、確認が必要なための破棄（マイグレーション `0002_b2_metrics`）。
- Prompts: `models/prompts.py` defines the Schema and version numbers, and the text is in `models/prompt_texts/*.txt`. Changing the text changes the version number, and replays become stale accordingly (`fixtures/README.md`).
  プロンプト：`models/prompts.py` がスキーマとバージョン番号を定義し、本文は `models/prompt_texts/*.txt` にある。本文を変えるとバージョン番号が変わり、リプレイもそれに伴って古くなる（`fixtures/README.md`）。
- Span (`trace.py`, data-design section 8): one per text-model call, with attributes limited to whitelisted IDs, counts, rule names, and duration, written to the log `zoujin.trace`.
  Span（`trace.py`、data-design 第8節）：テキストモデルの呼び出しごとに一つ。属性はホワイトリストにある ID、件数、ルール名、所要時間だけで、ログ `zoujin.trace` に書く。

### Real models (only on zg's Mac, after PM's notice) / 本物のモデル（zg の Mac でのみ、PM の通知後）

```sh
uv sync --all-packages --extra real      # anthropic, google-auth; CI's lint job installs it too so that mypy checks the real client / CI の lint ジョブにもインストールし、mypy が本物のクライアントを検査できるようにする
```

From B-8 on, which provider and which tier each prompt uses is written in `config.TEXT`: `reply` (standing in for Live as the character in evaluations) goes to Google, the rest to Claude (D-028). `ZJ_MODEL=real` splits between the two clients accordingly; runs that call only Claude (S-2, the probe) do not require Vertex environment variables.

B-8 以降、各プロンプトがどのプロバイダのどの段階を使うかは `config.TEXT` に書く：`reply`（評価で Live の代わりに人物を務める）は Google、それ以外は Claude（D-028）。`ZJ_MODEL=real` はこれに従って2つのクライアントに振り分ける。Claude だけを呼ぶ実行（S-2、小テスト）では Vertex の環境変数は不要。

- **Claude** (`models/claude.py`): zg's Anthropic API quota. The key is read from the keychain into an environment variable of **this one terminal only**, the SDK reads it itself, and it never goes into logs, traces, replays, the ledger, or exception messages; model IDs likewise live only in environment variables (the repo writes only the tier name plus version), and if the recognized tier name plus version differs from `config.TEXT`, no call is made:
  **Claude**（`models/claude.py`）：zg の Anthropic API 枠。キーはキーチェーンから**この一つのターミナル**の環境変数にだけ読み込み、SDK が自分で読む。ログ、トレース、リプレイ、台帳、例外メッセージには入れない。モデル ID も環境変数にだけ置き（リポジトリには段階名とバージョンだけを書く）、認識した段階名とバージョンが `config.TEXT` と違えば呼び出さない：

  ```sh
  export ANTHROPIC_API_KEY="$(security find-generic-password -s zoujin-claude -w)"
  export ZJ_CLAUDE_HAIKU=… ZJ_CLAUDE_SONNET=…      # model IDs, not written into the repo / モデル ID。リポジトリには書かない
  export ZJ_LEDGER=~/.zoujin/ledger.jsonl ZJ_MAX_CLAUDE_USD=100   # D-029: Claude's ledger accumulates across all runs / D-029：Claude の台帳は全実行にまたがって累計する
  ```

  Temporarily switching tiers to measure Haiku (S-085 ③): `ZJ_TEXT_MODELS=check=haiku-5.5` (comma-separate to switch several kinds; only Claude kinds can be switched, thinking and effort unchanged; replay keys, the ledger, and `check.checker` change accordingly).

  Haiku を測るため一時的に段階を切り替える（S-085 ③）：`ZJ_TEXT_MODELS=check=haiku-5.5`（カンマ区切りで複数の種類を切り替えられる。切り替えられるのは Claude のものだけで、思考と effort はそのまま。リプレイのキー、台帳、`check.checker` がそれに伴って変わる）。

- **Google** (`models/vertex.py`): Gemini on Vertex AI, via REST, authenticated with the application default credentials from gcloud login on the Mac, with no API key. The project ID and location are read **only** from `ZJ_VERTEX_PROJECT` and `ZJ_VERTEX_LOCATION`, checked only when a Google kind is actually called; if unset it exits without sending a request; gcloud's default project is not used. The project ID never goes into logs, traces, replays, or the ledger. The cap is `ZJ_MAX_GOOGLE_USD` (D-027).
  **Google**（`models/vertex.py`）：Vertex AI 上の Gemini。REST 経由で、認証は Mac で gcloud ログインしたアプリケーションのデフォルト認証情報を使い、API キーはない。プロジェクト ID とリージョンは `ZJ_VERTEX_PROJECT`、`ZJ_VERTEX_LOCATION` **からのみ**読み、Google の種類を実際に呼ぶときだけ検査する。未設定なら終了し、リクエストは送らない。gcloud のデフォルトプロジェクトは使わない。プロジェクト ID はログ、トレース、リプレイ、台帳に入れない。上限は `ZJ_MAX_GOOGLE_USD`（D-027）。
- Ledger (`zoujin_llm.Ledger`, shared with data's reviewers): two ledgers in the same file, one line per call, with `provider` and `use` (the narrator's steps are `product`; reviewers and the AI player are `eval`). The overall cap counts only its own provider; `ZJ_MAX_ITEM_USD` and `ZJ_LEDGER_ITEM` are the per-item cap and which item to record under, and the per-item cap sums both ledgers of the same item. Before a call the decision is made on estimated cost, and on reaching the cap it raises `BudgetStop`; calls cancelled by a time limit are booked at the estimated cost, and calls with unacceptable output (including Claude's `refusal` and `max_tokens`) are booked at the actual cost, and both are also counted into this turn's cost at that same figure. (B-5) Each line also has `ms` (from sending to receiving fully; for timeouts, until cancellation) and `status` (`ok` / `timeout` / `bad-output` / `error`; no response is recorded as `error` with cost 0), and within an evaluation playthrough calls carry `playthroughId`; calls wrapped in `Ledger.timed()` record these automatically. The calls that were not committed (retracted turns, retries after failure) are also recorded in this playthrough's `playthrough_metrics`.
  台帳（`zoujin_llm.Ledger`。データ側のレビュアーと共用）：2つの台帳が同じファイルにあり、1呼び出しが1行で、`provider` と `use` を持つ（語り手の各ステップは `product`、レビュアーと AI プレイヤーは `eval`）。総上限は自分のプロバイダ分だけを数える。`ZJ_MAX_ITEM_USD` と `ZJ_LEDGER_ITEM` は項目ごとの上限と記録先の項目で、項目ごとの上限は同じ項目の2つの台帳を合算する。呼び出し前に見積もりコストで判定し、上限に達したら `BudgetStop`。時間制限で取り消された呼び出しは見積もりコストで記帳し、出力が不合格（Claude の `refusal`、`max_tokens` を含む）のものは実コストで記帳する。この2種も同じ値でこのターンのコストに計上する。（B-5）各行には `ms`（送信から受信完了まで。タイムアウトは取り消しまで）と `status`（`ok` / `timeout` / `bad-output` / `error`。応答がなければ `error`、コスト 0）もあり、評価の周回内での呼び出しは `playthroughId` を持つ。`Ledger.timed()` で包んだ呼び出しはこれらを自動で記録する。コミットされなかった呼び出し（取り消されたターン、失敗後のやり直し）もこの周回の `playthrough_metrics` に記録する。
- 429, 529: runs on the Mac stop at the first one (exit code 3); the narrator serving players (`narrator/app.py`) treats it as a failure of that call and handles it per the time-limit rules (`Pipeline.on_rate_limit`).
  429、529：Mac での実行は最初の一件で停止する（終了コード 3）。プレイヤーに応対する語り手（`narrator/app.py`）はその呼び出しの失敗として扱い、時間制限の規則で処理する（`Pipeline.on_rate_limit`）。
- `ZJ_RECORD_REPLAYS=<directory>`: every call from fake and real is recorded as a line in replay format (`<directory>/<prompt kind>.jsonl`, key `<provider>|<model>|<prompt version>|<sha256 of the request>`). `ZJ_REPLAYS=<directory>` makes `replay` read a different directory (e.g. the holdout set's replays, not in the repo).
  `ZJ_RECORD_REPLAYS=<ディレクトリ>`：fake と real の呼び出しをすべてリプレイ形式で一行ずつ記録する（`<ディレクトリ>/<プロンプトの種類>.jsonl`、キーは `<provider>|<モデル>|<プロンプトのバージョン>|<リクエストの sha256>`）。`ZJ_REPLAYS=<ディレクトリ>` で `replay` に別のディレクトリを読ませる（例：リポジトリに入れない留保セットのリプレイ）。

### S-2 run script / S-2 の実行スクリプト

```sh
uv run zoujin-s2 evals/s2/s2_dev.jsonl --out out/s2-dev            # fake model, free / 偽モデル、無料
uv run zoujin-s2 <annotated-set.jsonl> --out <dir> --resume                # continue after interruption / 中断後に続行
```

  各エントリで周回を開始して `check(model_checks="all")` を呼び、`--runs` 回（デフォルト 3）実行する。結果は `results.jsonl` に一行ずつ書き、完了または停止時に `report.json` と `report.md` を書く（エントリ ID、判定、ルール、理由、トレース ID だけで、原文と要約は写さない）。

Hitting the cap or the first 429/529 exits with code 3; missing replays or wrong configuration exits with code 2. To measure Haiku again: prefix the same command with `ZJ_TEXT_MODELS=check=haiku-5.5` and use a different `--out`.
  本物のモデルには `ZJ_MODEL=real`、`ZJ_EVAL_LIVE=1`、`ZJ_LEDGER`、Claude のキーと2段階のモデル ID、`--max-item-usd`、`--max-claude-usd`、`--confirm` がすべて必要。一つでも欠けると見積もりコストとコマンドを表示するだけで呼び出さない。上限到達または最初の 429、529 で終了コード 3、リプレイ欠落または設定不備で終了コード 2。Haiku を再測定するには、同じコマンドの前に `ZJ_TEXT_MODELS=check=haiku-5.5` を付け、`--out` を変える。
- There is no default path for the annotated set. For the rules about the holdout set see `docs/tasks/m2/B-2.md`.
  注釈付きセットのデフォルトパスはない。留保セットの規則は `docs/tasks/m2/B-2.md` を参照。

### Probe / 小テスト (B-8, `zoujin-probe`)

Measures the time to first token, total latency, and tokens for each prompt kind that goes to Claude. Requests are taken from the replays recorded by the fake model (holdout samples are not touched):

Claude に回す各プロンプトの種類について、最初のトークンまでの時間、全体の遅延、トークン数を測る。リクエストは偽モデルが録画したリプレイから取る（留保サンプルには触れない）：

```sh
docker compose up -d db
export DATABASE_URL=postgresql://zoujin:zoujin@127.0.0.1:5432/zoujin
uv run --all-packages --extra real alembic -c services/backend/alembic.ini upgrade head    # create tables first on a new DB, otherwise every case cannot connect / 新しい DB はまずテーブルを作る。さもないと全ケースが接続できない
ZJ_RECORD_REPLAYS="$PWD/out/probe-requests" uv run --all-packages --extra real zoujin-eval --mode fake --deterministic-only --slice --quiet --out out/probe-e0
uv run --all-packages --extra real zoujin-probe --requests out/probe-requests --out out/probe --max-item-usd 2 --max-claude-usd 100    # only prints the estimated cost and the command / 見積もりコストとコマンドを表示するだけ
```

- It takes `--per-kind` samples of each kind (default 20; identical requests count once, and if there are not enough they are used in rotation), calls serially, and records in Claude's ledger with item `b8-probe`. After zg approves, add `--confirm` to the printed command, with the environment variables as above.
  各種類から `--per-kind` 件（デフォルト 20。同じリクエストは一件と数え、足りなければ順に使い回す）を取り、直列で呼び出し、Claude の台帳に item `b8-probe` で記録する。zg の了承後、表示されたコマンドの後ろに `--confirm` を付ける。環境変数は上記のとおり。
- To rerun only certain kinds: add `--kind plan` (can be given several times).
  特定の種類だけ再実行するには `--kind plan` を付ける（複数回指定できる）。
- It stops at the first 429, 529, or hitting the cap (exit code 3); other HTTP errors skip the rest of that prompt kind and print the status code, the API's error type, and a hardcoded class name (e.g. the prompt `schema-too-complex` message); the original message is not printed. The results `probe.jsonl` and `summary.json` contain only numbers (kind, tier name plus version, milliseconds, tokens, cost), to be copied into the project folder by the coordinator.
  最初の 429、529 または上限到達で停止する（終了コード 3）。その他の HTTP エラーはその種類の残りをスキップし、ステータスコード、API のエラー種別、固定のクラス名（例：`提示 schema-too-complex`）を表示する。元のメッセージは表示しない。結果の `probe.jsonl` と `summary.json` には数字（種類、段階名とバージョン、ミリ秒、トークン、コスト）だけが入り、コーディネーターがプロジェクトフォルダへコピーする。

### Simulated playthroughs and the S-5 report / 模擬周回と S-5 のレポート (B-5, `zoujin-s5`)

- The evaluation entry `setup({"role": …, "persona": …, "seed": …})` starts a playthrough just like a real start; the AI player (data's runner) sees only `view()`, `manifest()`, and what the player can hear and see in each step's result, and each step carries `elapsedMs` (api-contract section 7).
  評価の入口 `setup({"role": …, "persona": …, "seed": …})` は、正式な開始と同じように周回を開始する。AI プレイヤー（データ側のランナー）は `view()`、`manifest()`、および各ステップの結果のうちプレイヤーが聞こえ見えるものだけを見て、各ステップに `elapsedMs` が付く（api-contract 第7節）。
- S-5 runs on the Mac using data's runner (live, `--slice`, `item` set to `s5`; commands and personas are matched with data in the PR), and after the run the report is produced:
  S-5 は Mac でデータ側のランナーを使って実行する（live、`--slice`、`item` は `s5`。コマンドとペルソナは PR でデータ側と突き合わせる）。実行後にレポートを出す：

```sh
uv run zoujin-s5 --ledger ~/.zoujin/ledger.jsonl --runs <runner's report.json> --out <dir>    # DATABASE_URL is the DB that ran the simulated playthroughs / DATABASE_URL は模擬周回を実行した DB
```

- It reads the rows with `item: "s5"` in the ledger (change with `--item`), the test DB's `playthrough_metrics` and the times of dialogue turns, and each run's `playthroughId`, `persona`, `seed`, `steps[].elapsedMs` in the runner's `report.json`. It writes `report.json` and `report.md`, numbers only: each playthrough's product cost (excluding `reply`, reviewers, and the AI player; differences over 1% from `playthrough_metrics` are flagged); when per-turn cost rises with the number of turns, an extrapolation along the trend to 40 and 60 turns and the stress tier (world advancement listed separately); the number of turns at which 240 and 300 yen is exceeded and 350 yen is reached, and the total when world advancement is halved (a few options of Q-B8); the cache read ratio; per-kind call latency and the time-limit recommendation; the time taken by each step; the narrator's counts. Kinds not yet in Live or the slice are [estimate]; the parameters are written in `params` of `report.json`.
  台帳の `item: "s5"` の行（`--item` で変更可）、テスト DB の `playthrough_metrics` と対話ターンの時刻、ランナーの `report.json` にある各実行の `playthroughId`、`persona`、`seed`、`steps[].elapsedMs` を読む。`report.json` と `report.md` を書き、数字だけを含む：各周回のプロダクトコスト（`reply`、レビュアー、AI プレイヤーは除く。`playthrough_metrics` と1%超ずれたものは印を付ける）。ターンごとのコストがターン数とともに上がる場合は、傾向に沿って 40 ターン、60 ターン、負荷段階（世界の進行は別枠）まで外挿する。240 円、300 円を超える時点と 350 円に達する時点のターン数、世界の進行を半分にしたときの合計（Q-B8 のいくつかの選択肢）。キャッシュ読み取りの割合。種類ごとの呼び出し遅延と時間制限の推奨。各ステップの所要時間。語り手の件数。Live やスライスにまだない種類は〔推算〕で、パラメータは `report.json` の `params` に書く。
- The two tiers (Sonnet or Haiku for extraction and check, S-090 ③) get separate reports: each tier's runner writes its own `report.json`, and the ledger uses a separate `item` for each (e.g. `s5-sonnet`, `s5-haiku`); run `zoujin-s5 --item … --runs … --out <each directory>` once for each. Mixing the playthroughs of both tiers into one report would count them into the same trend.
  2つの段階（抽出と検査に Sonnet か Haiku、S-090 ③）は別々にレポートを出す：各段階のランナーがそれぞれ `report.json` を書き、台帳もそれぞれ別の `item`（例：`s5-sonnet`、`s5-haiku`）を使い、`zoujin-s5 --item … --runs … --out <各ディレクトリ>` をそれぞれ一度実行する。両方の段階の周回を同じレポートに混ぜると、同じ傾向として計算されてしまう。

## Retraction and intent confirmation / 取り消しと意図の確認 (B-4)

- Commit window: when the gateway hands a turn to the narrator it writes `turns.commit_after` (3 seconds after `turn_complete` or after the plan is finalized, multiplied by `ZJ_SPEED`; at speed 0 there is no window). The narrator waits until this time after settling before committing, and during this period `turn_retract` can change the turn to `retracted` (`store.retract_queued`); at commit the narrator only recognizes `leased`, and whoever takes the row lock first counts.
  コミットウィンドウ：ゲートウェイが語り手にターンを渡すときに `turns.commit_after` を書く（`turn_complete` または意向の確定の3秒後に `ZJ_SPEED` を掛ける。速度 0 ではウィンドウなし）。語り手は判定後この時刻まで待ってからコミットし、その間は `turn_retract` でそのターンを `retracted` に変えられる（`store.retract_queued`）。語り手はコミット時に `leased` だけを認め、先に行ロックを取った方が有効になる。
- Retracting a turn still in connection memory (the character has not finished speaking): stop forwarding, write a `retracted` row, and do not hand it to the narrator. After a dialogue turn is retracted, the session of that character is rebuilt, and the new session carries only the recent turns of this connection that were not retracted (in memory only).
  まだ接続のメモリ内にあるターン（人物がまだ話し終えていない）の取り消し：転送を止め、`retracted` の行を一つ書き、語り手には渡さない。対話のターンが取り消された後、その人物のセッションを再構築し、新しいセッションにはこの接続の直近のターンのうち取り消されていないものだけを持たせる（メモリ内のみ）。
- Intent confirmation (`narrator/confirm.py`): candidates that need confirmation and passed the check are saved into `drafts` (migration `0004_b4_confirm`), and this turn commits as usual; after the gateway pushes that turn's result it asks back, pushes `confirm`, and starts the timer (30 seconds times `ZJ_SPEED`). The button, voice, and timeout each write a task row with `kind: "confirm"`; the narrator re-checks and then commits or discards, and pushes `confirm_closed`. Before taking a task the narrator writes timeout tasks for expired drafts (the gateway's timer is absent during a disconnect).
  意図の確認（`narrator/confirm.py`）：検査を通った要確認の候補は `drafts` に保存し（マイグレーション `0004_b4_confirm`）、このターンは通常どおりコミットする。ゲートウェイはそのターンの結果を送った後に聞き返し、`confirm` を送ってタイマーを開始する（30秒に `ZJ_SPEED` を掛ける）。ボタン、音声、タイムアウトはいずれも `kind: "confirm"` のタスク行を書き、語り手は再検査してからコミットまたは破棄し、`confirm_closed` を送る。語り手はタスクを取る前に、期限切れの下書きのタイムアウトタスクを書く（切断中はゲートウェイのタイマーがない）。
- Evaluation entry: `say(hold=True)` does not commit yet, `retract(n)`, `confirm(answer)` (api-contract section 7).
  評価の入口：`say(hold=True)` はまだコミットしない。`retract(n)`、`confirm(answer)`（api-contract 第7節）。

## Prerecorded lines / 録音済みの台詞 (B-6)

```sh
uv run zoujin-voice                                        # fake model: synthesized voice, to see the flow and output, free (needs ffmpeg) / 偽モデル：合成音声で流れと出力を確認する。無料（ffmpeg が必要）
uv run zoujin-voice --resume out/b6/<timestamp> [--only <key> …]  # continue; re-read only certain lines / 続行。特定の台詞だけ読み直す
```

- Source file `voice/<book>.json`: each speaker's voice (D-025), character direction `direction`, the character's 6 lines (ux-design 16.2), `cues`, scene directions `scenes`, and reading substitutions `readings`; lines for fixed set pieces and the text of `arrival_capped` are read from the world model. To change a voice, edit here and rerun that character with `--only`. Direction for one particular line of one person only (e.g. a long-ish backchannel) goes in the speaker block's `scenes`, keyed by slot (`"aizuchi/3"`), whereas the top-level `scenes` is not per person; after editing, `--resume <directory> --only <recording ID>` re-reads only those lines and the others are reused. The speaker block's `loudness` is the target loudness (voiced RMS, dBFS, the same character's free dialogue as measured by UX), and the whole line is adjusted to it at build time; changing it needs no re-recording, just `--resume <directory>` to re-emit the release; `pieceLoudness` (fixed set piece ID → dBFS) makes this person use a different target in certain pieces (bringing several people in the closing sequence to the same level); `loudnessOffset` (key → dB) additionally lowers lines the source work specifies as quiet. When the backfilled transcription always gets one line wrong ("ちと" written as "ちょっと"), the top-level `heardAs` adds an alternative spelling counted as correct for that line, affecting only that line and not loosening the 20% threshold; changing it needs no re-recording either.
  ソースファイル `voice/<book>.json`：各話者の声（D-025）、人物の説明 `direction`、人物の6つの台詞（ux-design 16.2）、`cues`、場面の説明 `scenes`、読みの置換 `readings`。固定演出の台詞と `arrival_capped` の文字はワールドモデルから読む。声を変えるにはここを直し、`--only` でその人物を再実行する。特定の人物の特定の台詞だけに演じ方を加える場合（例：長めの相槌）は、話者ブロックの `scenes` に書き、キーはスロット（`"aizuchi/3"`）。トップレベルの `scenes` は人物を区別しない。直したら `--resume <ディレクトリ> --only <録音 ID>` でその台詞だけを読み直し、他はそのまま使う。話者ブロックの `loudness` は目標ラウドネス（有声 RMS、dBFS、UX が計測した同一人物の自由対話）で、ビルド時に台詞全体をそこへ調整する。変えても再録音は不要で、`--resume <ディレクトリ>` で release を出し直すだけでよい。`pieceLoudness`（固定演出 ID → dBFS）はこの人物が特定の場面で別の目標を使うようにする（幕を閉じる連続で複数の人物を同じレベルに揃える）。`loudnessOffset`（キー → dB）は、原作で声が小さいと明記された台詞をさらに個別に下げる。文字起こしの補完がある台詞をいつも書き間違える場合（「ちと」が「ちょっと」になる）は、トップレベルの `heardAs` でその台詞に正解として扱う別の書き方を追加する。その台詞だけに効き、20% の線は緩めない。これも変えて再録音は不要。
- Each line is read 3 times (3 sessions); after automatic checks (length, truncation, backfilled transcription against the original text; backchannels additionally need voiced ≤ 0.5 seconds, trimmed ≤ 0.6 seconds, and pitch) one take is picked, leading and trailing silence is trimmed (silence is padded when under 80 ms), adjusted to the target loudness, true peak held below −1 dBTP, and converted to AAC. If a backchannel fails all three takes, run again with `--resume <directory> --only <recording ID>` without loosening. Output is in `out/b6/<timestamp>/release/`: `.m4a`, `voices.json` (the two blocks `characters[].prerecorded` and `setPieceVoices` of the manifest), `audit.md`, `ref/`, plus a zip and a printed sha256.
  各台詞は3回（3セッション）読み、自動検査（長さ、途切れ、文字起こしの補完と原文の照合。相槌はさらに有声 0.5 秒以下、トリム後 0.6 秒以下、ピッチあり）の後に1回を選び、頭と末尾の無音をトリムし（80 ミリ秒に満たなければ無音を補う）、目標ラウドネスに調整し、真のピークを −1 dBTP 未満に抑え、AAC に変換する。相槌が3回とも不合格なら `--resume <ディレクトリ> --only <録音 ID>` でもう一度実行し、基準は緩めない。出力は `out/b6/<timestamp>/release/` にある：`.m4a`、`voices.json`（manifest の `characters[].prerecorded` と `setPieceVoices` の2ブロック）、`audit.md`、`ref/`。さらに zip を作り、sha256 を表示する。
- Real models (only on the Mac): `ZJ_MODEL=real`, `ZJ_LEDGER`, `ZJ_VERTEX_PROJECT`, `ZJ_VERTEX_LOCATION` (backfilled transcription), `--max-google-usd`, and `--confirm`; Live's location defaults to us-central1 (change with `ZJ_LIVE_LOCATION`). If any is missing it only prints the estimated cost and the command. This run's cap `--max-usd` defaults to $1. Hitting the cap, the first 429, or a connection failure exits with code 3 (`--resume` continues).
  本物のモデル（Mac のみ）：`ZJ_MODEL=real`、`ZJ_LEDGER`、`ZJ_VERTEX_PROJECT`、`ZJ_VERTEX_LOCATION`（文字起こしの補完）、`--max-google-usd`、`--confirm`。Live のリージョンはデフォルト us-central1（`ZJ_LIVE_LOCATION` で変更）。一つでも欠けると見積もりコストとコマンドを表示するだけ。この実行の上限 `--max-usd` はデフォルト $1。上限到達、最初の 429、接続失敗で終了コード 3（`--resume` で続行）。
- After the run: the release zip and sha256 are handed to the coordinator, who copies them to `/mnt/project-files/app-team/backend/b6/`; after backend verifies the sha they go to UX for measurement and zg for listening (B-6 card, "actually generate").
  実行後：release の zip と sha256 をコーディネーターに渡して `/mnt/project-files/app-team/backend/b6/` にコピーしてもらう。バックエンドが sha を照合した後、UX が計測し、zg が聴く（B-6 カード「実際に生成する」）。
- The mock's manifest reads `assets/voice/<book>/voices.json` (if present), and `/assets/voice/<book>/<file>` serves only files in that list.
  mock の manifest は `assets/voice/<book>/voices.json` を読み（あれば）、`/assets/voice/<book>/<ファイル>` は一覧にあるファイルだけを配信する。
